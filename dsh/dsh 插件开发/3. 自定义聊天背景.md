## 我们的目标

写一个插件，把一张本地图片设为 DSH 的聊天背景。

## 这个插件要打通两条路

hello world 只是打印一句话，而这个插件要"动 UI"。页面是 DSH 自己渲染的，插件想影响它，需要打通两条路：

1. **让浏览器能拿到图片**：图片在插件目录里，浏览器可访问不到你的磁盘。所以我们 要在 DSH 的 webServer 上注册一个 HTTP 路由：浏览器请求某个地址时，服务器把图片文件返回给它。
2. **让页面穿上背景**：页面不知道"背景长什么样"。DSH 提供了一个钩子 `webserver/index-inject`，允许插件往每个页面的 `<head>` 里注入一段 `<style>`。

```mermaid
flowchart LR
    A["浏览器打开页面"] --> B["请求 /dsh-chat-background/image.jpg"]
    B --> C["webServer 路由<br/>（插件注册的）"]
    C --> D["读取插件目录里的<br/>image.jpg 并返回"]
    A --> E["页面 HTML 里已被注入 &lt;style&gt;"]
    E --> F["CSS 把背景图铺在布局根"]
    D --> F
```

## 目录结构

```text
dsh-chat-background/                    ← 插件包（bundle）
├── src/                                ← 源码目录
│   ├── dsh-chat-background.ts          ← 插件本体：name + apply
│   └── style.css                       ← 背景样式（独立文件，方便改）
├── image.jpg                           ← 你的背景图片
├── package.json                        ← 身份 + dsh.bundle 声明
├── patch.yaml                          ← 挂载指令
└── tsconfig.json                       ← 类型配置（让编辑器认识 node:fs）
```

## 第一步：准备图片

把想用的背景图放到插件根目录，本教程用 `image.jpg`。

> 为什么图片不能写进代码？一是几 MB 的图会让代码文件爆炸；二是浏览器根本读不到你磁盘上的文件，必须走 HTTP 路由，这是唯一的正规通道。

## 第二步：写插件本体

```ts
// src/dsh-chat-background.ts
import { readFileSync } from 'node:fs'
import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'

export const name = 'dsh-chat-background'

// 图片在插件根目录（../），样式表与源码同目录；都用 import.meta.url 解析
const IMAGE_PATH = new URL('../image.jpg', import.meta.url).pathname
const IMAGE_URL = '/dsh-chat-background/image.jpg'
const STYLE = readFileSync(new URL('./style.css', import.meta.url), 'utf8')

export function apply(ctx: Context): void {
    // 1. 注册路由：浏览器请求 IMAGE_URL 时返回图片
    ctx.inject(['webServer'], (serverCtx) => {
        const webServer = (serverCtx as any).webServer
        ctx.effect(() => webServer.register({
            kind: 'exact',
            path: IMAGE_URL,
            handler: async (_req: any, res: any) => {
                res.writeHead(200, { 'content-type': 'image/jpeg' })
                res.end(await readFile(IMAGE_PATH))
            },
        }))
    })

    // 2. 注入样式：把 style.css 内容原样注入每个 index 响应
    ctx.events.on('webserver/index-inject', (table: any) => {
        table.push({ kind: 'style', text: STYLE })
    })
}
```

这段代码做了两件事：第 1 段注册图片路由，第 2 段注入样式。我们按顺序拆开讲。

### 第 1 段：注册图片路由

```ts
ctx.inject(['webServer'], (serverCtx) => {
    const webServer = (serverCtx as any).webServer
    ctx.effect(() => webServer.register({
        kind: 'exact',
        path: IMAGE_URL,
        handler: async (_req: any, res: any) => {
            res.writeHead(200, { 'content-type': 'image/jpeg' })
            res.end(await readFile(IMAGE_PATH))
        },
    }))
})
```

表面看只是"注册一个路由"，其实是**三层嵌套**，每一层解决一个问题。

- 最外层 `ctx.inject(['webServer'], ...)`：声明"我依赖 webServer"

`webServer` 是 DSH 内置的 HTTP 服务器服务（Cordis Service）。它自己也有启动过程——要监听端口、准备就绪。**插件执行到 `apply()` 时，webServer 很可能还没准备好**。`ctx.inject` 就是告诉 Cordis："我依赖 webServer，等它可用了再叫我"。Cordis 会替我们排好插件的加载顺序，依赖就绪后才执行里面的回调。

还有一层深意：**可选注入**。不是所有 DSH 都有 web 服务——桌面版 Electron 走 file:// + IPC，没有 webServer。这时 `inject` 的回调不会执行，插件照常加载其余部分，不会因为"找不到 webServer"而崩溃。图片路由只对 web 版生效，这是合理的降级。

- 中间层 `webServer.register({...})`：往路由表里加一条

`register` 接收一个路由描述对象：

- `kind: 'exact'`：路径**逐字匹配**。浏览器请求的地址必须和 `path` 一模一样（`/dsh-chat-background/image.jpg` 一个字符都不能差）。另一个可选值是 `'prefix'`，匹配 `path` 和 `path/<任意内容>`，适合托管一个目录。
- `handler`：**拥有响应的完整生命周期**。服务器把请求交给 handler，写什么状态码、返回什么内容都由它决定（甚至可以挂起连接做 SSE）。所以我们必须自己 `res.writeHead(...)` 声明状态码和类型，`res.end(...)` 结束响应。
- 重复注册同一条 (kind, path) 会直接抛错——DSH 认为路由是"组合级契约"，撞了就是配置错误。

`handler` 内部就三行：`res.writeHead(200, { 'content-type': 'image/jpeg' })` 告诉浏览器"这是张 JPEG 图片"；`await readFile(IMAGE_PATH)` 把插件目录里的图片读进内存；`res.end(...)` 把字节流发给浏览器。

`register` 还有返回值：一个**注销函数**（把这条路由从表里删掉）。这个返回值是留给最内层用的。

- 最内层 `ctx.effect(...)`：把注销函数绑进插件生命周期

```ts
ctx.effect(() => webServer.register({ ... }))
```

`ctx.effect` 接收一个"效果体"：立即执行，并把执行结果当作**清理函数**收集起来。等插件被卸载（禁用、移除、重载）时，Cordis 会**逆序执行**所有清理函数。

于是 `register` 返回的注销函数就有了归属：插件活着，路由在；插件卸载，路由自动消失。如果不包这一层直接调 `register`，插件卸载后路由会残留在表里，下次再启用插件时 `register` 就会抛"duplicate route"异常。

> 记忆口诀：`inject` 等就绪，`register` 进表，`effect` 管清理。

#### 为什么是 `(serverCtx as any).webServer`

`webServer` 的类型声明（`Context.webServer`、`webserver/index-inject` 事件）来自一个**没有发布到 npm** 的私有包 `@deepseek-ai/dsh-host-webserver`，它通过 TypeScript 的 module augmentation 挂在 Cordis 类型上。我们的插件只依赖 `@deepseek-ai/cordis`，编译时 TypeScript 根本不认识 `ctx.webServer`——`as any` 是绕开这个类型缺口的写法，**运行时没有任何影响**（服务真实存在，只是类型上没声明）。

同样的原因，第 2 段监听事件用的是 `ctx.events.on` 而不是 `ctx.on`：`ctx.on` 是泛型约束的，只接受它认识的事件名；`ctx.events.on` 是宽泛重载，接受任意字符串，两者走的是同一个事件总线。

另外注意回调参数用的是 `serverCtx` 而不是外层 `ctx`：`inject` 回调拿到的是 Cordis 为这个依赖组创建的**子上下文**，它的存活范围与这段代码绑定，是标准写法。

#### 请求来了会发生什么

```mermaid
sequenceDiagram

    participant W as webServer
    participant P as 我们的 handler

    B->>W: GET /dsh-chat-background/image.jpg
    W->>W: 查路由表（exact 命中）
    W->>P: 调用 handler(req, res)
    P->>P: readFile(图片文件)
    P-->>B: 200 + image/jpeg + 图片字节
```

### 第 2 段：注入样式

```ts
ctx.events.on('webserver/index-inject', (table: any) => {
    table.push({ kind: 'style', text: STYLE })
})
```

`webserver/index-inject` 是 DSH 的"往页面里塞东西"事件：每次渲染页面 HTML 时，DSH 发出这个事件，`table` 就是要注入的内容列表。我们 push 一条 `style`，内容就是 style.css 的全文，DSH 会把它渲染成 `<style>...</style>` 放进每个页面的 `<head>`。

`new URL('./style.css', import.meta.url)`：以**插件源码文件自己的位置**为基准找文件，不依赖你从哪个目录启动 DSH（这是比写相对路径更稳的写法）。

## 第三步：写样式（核心思路：透出，而不是各铺各的）

```css
/* src/style.css */
/* 布局根（AppFrame.frame）铺一张背景图，同时覆盖侧边栏与聊天区 */
div:has(> [data-shell-overlay]) {
  background-image: url('/dsh-chat-background/image.jpg');
  background-size: cover;
}

/* 侧边栏列：局部置空 fill 变量，透出布局根背景 */
div:has(> [data-shell-overlay]) > div:first-child {
  --dsw-specific-sidebar-fill: transparent;
}

/* 聊天列根：背景置透明，透出布局根背景 */
div:has(> [data-shell-overlay]) [data-slot='conversation'] > [data-phase] {
  background: transparent;
}
```

三个规则各司其职：

1. **背景图只铺一次**——铺在布局根（整个界面的最外层容器）上。
2. 侧边栏和聊天区**各自的背景改成透明**，让底下的图"透出来"。
3. 聊天列根那条要"穿过"一层 `[data-slot='conversation']` 包装——DSH 渲染每个区域 时都会包一层 `data-slot` 标记（样式上不影响布局，但 DOM 上是真实存在的），选择器要认准它。

> 为什么选择器这么"绕"？DSH 的界面元素没有稳定的 class 名（编译后是随机 hash），但保留了稳定的 `data-*` 属性。`div:has(> [data-shell-overlay])` 的意思是："找一 个 div，它的直接子元素里有 `data-shell-overlay`"——用子元素反推祖先，就锁定了布局根。这就是 `:has()` 的妙用。

## 第四步：bundle 三件套

### package.json —— 身份 + 声明

```json
{
  "name": "dsh-chat-background",
  "version": "0.1.0",
  "type": "module",
  "dependencies": {
    "@deepseek-ai/cordis": "^4.0.1"
  },
  "dsh": {
    "bundle": {
      "patch": "./patch.yaml"
    }
  }
}
```

### patch.yaml —— 说明书（注意指向 src 目录）

```yaml
- insert:
    - id: dsh-chat-background
      name: '/你的插件绝对路径/dsh-chat-background/src/dsh-chat-background.ts'
```

### tsconfig.json —— 让编辑器认识 Node

```json
{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "target": "es2022",
    "lib": ["es2022", "dom"],
    "types": ["node"],
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true
  },
  "include": ["src/*.ts"]
}
```

关键是 `"types": ["node"]`：代码里用了 `node:fs`，没有它 TypeScript 会报"找不到 模块"。

## 第五步：安装、启动、验证

```bash
cd 你的插件目录
dsh plugin --profile test add link:.
dsh --profile test --dump-config   # 插件树里应出现 dsh-chat-background
dsh --profile test --no-open       # 启动，web 端口 3080
```

先验证图片路由通不通（不开浏览器就能测）：

```bash
curl -sI http://127.0.0.1:3080/dsh-chat-background/image.jpg
```

看到 `HTTP/1.1 200 OK` 和 `content-type: image/jpeg` 就成功了。再验证样式有没有 注入页面：

```bash
curl -s http://127.0.0.1:3080/ | grep "data-slot='conversation'"
```

最后浏览器打开 http://127.0.0.1:3080 —— 侧边栏和聊天区应该是同一张连续的背景图。

## 常见小坑

- **patch.yaml 的 name 必须是绝对路径**：DSH 加载器的基准目录是 profile 目录，相对路径会找不到文件。
- **改完样式要重启 DSH 再刷新页面**：样式是服务端注入 HTML 的，不重启服务端就不 会带上新内容。
- **背景"断成两块"**：别给侧边栏和聊天区各铺一张图（各自 cover 会各自裁剪），要 用"铺一层 + 其余透明"的思路。
- **透明不要全局覆盖**：比如侧边栏的填充色 token `--dsw-specific-sidebar-fill`  是多个组件共用的，要在侧边栏这一列上局部覆盖，而不是全局改，否则会误伤其他组件。

## 延伸练习

1. 换一张图：直接替换 `image.jpg`，不用改任何代码。
2. 改效果：`background-size: cover` 改成 `contain`，或加一个半透明遮罩 `background-color: rgba(0, 0, 0, 0.3)` 让文字更清晰。
3. 练手 `index-inject`：试试 push 一条 `{ kind: 'script', text: 'console.log("hi")' }`，感受往页面注入脚本的通道。
