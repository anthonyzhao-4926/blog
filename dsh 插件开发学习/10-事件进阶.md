09 篇用三个事件就把计数做出来了，但那只覆盖了"量一次工具调用"。DSH 内部有近百个事件，它们不是一张平铺的表，而是一条有嵌套、有循环、有分支的链。这篇讲这条链的结构；每个事件的名字、时机和监听写法放在上面那份 HTML 里查，正文不重复罗列。

## 两种东西

先把容易混的两种东西分开，这是踩坑最多的地方。

**Cordis 事件**是运行期的协调接口。某个组件在一个明确的时刻派发它，谁想插手谁监听，管道模式的事件还能改写结果。你用它做拦截、注入、统计。

**会话日志记录**是已经写进会话文件的一条事实。它也能被观察到，但只能通过 `session/event` 这一个入口，再看 `event.type` 分辨是哪一种。它记录的是"发生过什么"，改不了。

名字长得很像——`tools/execute` 是事件，`tool/call` 是记录；`approval/request` 是事件，`approval/decided` 是记录。监听前者能改变这次调用，监听后者只能事后知道结果。判断办法只有一个：去源码里搜 `interface Events`，搜得到的是事件，只在 `SessionEventMap` 里出现的是记录。

## 一条对话的生命周期

真正的主线在 `packages/core/agent-loop/src/agent.ts` 里，`turn()` 和 `step()` 两个函数把顺序定死了。下面按它讲。

### 进程启动

进程起来时，插件树按 fiber 逐个装配，每个 fiber 建立和销毁都派发同名的 `internal/plugin`；配置解析、热重载各有自己的事件。这一段和"跑哪一轮对话"无关，进程活着就一直有效。它们属于 Cordis 框架，不属于 harness，但排查"插件到底装上没有"时最直接。

### 会话建立

一个会话先被公告，随后 agent 发布到注册表。`agent/session-start` 在第一个 turn 之前派发，一个会话只有一次，适合做会话级初始化——但要注意源码里有它、某些运行时版本并不派发（见文末）。

### turn 循环

一轮对话由 `turn()` 打开。它先写一条 `turn/start` 记录，然后进入 `while (true)`：每一步先经过准入，通过就跑一个 step，跑完判断收件箱里还有没有待处理的东西——有就再跑一步，没有就关闭这一轮。

准入那一步（`preStep()`）里其实叠着好几件事：先从收件箱认领这一步要用的消息，再组装系统提示（这里派发 `system-prompt/assemble`，是往提示词里加东西的地方），最后才派发 `agent/pre-step` 决定这一步进不进。**`agent/pre-step` 是唯一能拦住某一步的地方**：返回 reject，这一步就不发生。

所以这里有个容易记错的嵌套关系：`system-prompt/assemble` 发生在 `agent/pre-step` **里面**，不是和它并列。

一个 step（`step()` 函数）内部又是另一层：先冻结这次调用的配置（`agent/request`，可以在这里换 provider 或 model），把系统提示（`system/message`）和用户消息（`user/message`）落进日志，然后开始流式请求（`llm/stream`）。**这一层要调用的模型和参数，在 `agent/request` 之后就定死了。**

### 工具执行

模型如果决定调工具，整段工具执行发生在 `step()` 里面、模型输出之后——它不是独立的一步，而是这一步的一部分。

工具执行本身是四步管线，顺序固定：`tools/pre-execute` 决定批不批（允许、拒绝、还是转人工审批），`tools/execute` 是唯一包着工具本体的一层，`tools/post-execute` 决定结果要不要改写或拦掉，`tools/result` 是冻结之后的只读广播。想拦危险调用就挂第一个，想统计耗时挂第二个，想改结果挂第三个。

时间上还有个细节值得记住：`tool/call` 这条记录出现在 `tools/pre-execute` **之前**。DSH 先把"模型要调这个工具"写进日志，再去走审批——哪怕审批被拒，日志里也不缺这一笔。

### 派生

子代理和工作流是"另开一条线去跑"：派出去建一个子运行，跑完再收回来，start 和 end 成对。工作流还会按脚本里的阶段派发进度事件。它们不改变主线的顺序，只是在某个时刻分叉。

### 收尾

`agent/turn-stopping` 在 turn 即将关闭时派发，是最后的挽回机会——可以在这里让 agent 再读一次收件箱接着跑。之后写 `turn/end`，agent 回到空闲。会话与 agent 被回收时各有对应的事件，最后进程退出。

## 两处循环

这条链上有两段会重复，读事件顺序时别把它当成一次走完：

- **每个 step 重复一次**：准入 → 请求 → 模型 →（可能）工具执行。
- **每轮对话重复一次**：一轮结束后收件箱里还有消息，就回到 turn 起点再开一轮。

除此之外都是一次性的：进程启动、会话建立、派生、收尾、进程退出。

## 事件会挑听众

多数 agent 相关的事件带作用域标签，只派发给"和这个 agent 有关"的监听器——注册在别的作用域里就收不到。反过来，没有作用域标签的监听器（比如直接挂在进程根上的插件）能收到全部。

09 篇那个统计插件能统计整进程，就是这个原因。想按 agent 分开算，就得进到那个 agent 的作用域里注册。

## 为什么要在意顺序

理解了结构，三件事就顺了：

**别监听记录当事件用。** `turn/end`、`tool/call` 这些名字读起来就像事件，但直接 `ctx.on` 永远不会触发，而且类型检查抓不到——`ctx.on` 接受任何字符串。要读它们只有 `session/event` 一条路。

**选对拦截点。** 想拦一次工具调用，挂 `tools/pre-execute`；挂 `tools/result` 只能看到它已经跑完了。想知道"这一步会不会发生"，只有 `agent/pre-step` 能回答。

**接纳嵌套关系。** 在一个 step 里，模型参数在请求阶段就冻结了，想换模型得在 `agent/request`，而它已经被包在准入之后。晚一步就没有机会。

## 注意事项

- **源码、文档、运行时可能三个版本三样。** 本篇的结构读自仓库里的 `local/deepseek-harness/`，你机器的 `dsh --version` 很可能不同。已知两处差异：`agent/created` 源码声明 `emit`、实测按 `serial` 派发；`agent/session-start` 源码里有派发点，实测那次运行没有触发。跨版本时以 `node_modules/@deepseek-ai/*` 的类型声明为准。
- **事件顺序靠实测校，别只信声明。** 声明只写签名和模式，不写"谁先谁后"。上面每条顺序关系都是从 `agent.ts` 的调用结构里读出来的，个别还对照过一次 headless 运行的时间戳。
- **一个事件名只有一种分发模式。** `emit` 的用 `ctx.emit`，`waterfall` 的必须接 `next`。给自己的插件加事件时照抄旁边声明的 `@mode`，别自创。
- **监听器要短。** 准入、请求、工具执行都在热路径上，你的监听器慢一点，模型每一步都慢一点。
