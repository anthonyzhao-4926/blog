> MCP 工具的错误信息是写给谁看的?传统 API 是写给开发者看,而 MCP 的调用方是 LLM——它会实时读错误信息,然后决定下一步动作:换参数重试、告知用户、还是放弃。错误信息写得好不好,直接影响 AI 的决策质量。

# 服务端返回失败,分两类

MCP 协议里的失败分成两类,选错类型客户端会误判:

1. **协议错误**:请求本身不合法,或服务端处理不了(工具不存在、参数不符合 schema、内部严重故障)。客户端表现为 `CallTool()` 返回非 nil error,result 不可信。
2. **工具业务错误**:请求合法、工具也正常执行了,只是执行的结果是失败(cursor 过期、下游超时、业务规则不满足)。JSON-RPC 层面是成功响应,但结果里 `isError: true`,content 中带着错误描述——LLM 能读到,并据此决定怎么补救。

工具代码里对应两种返回方式:

```go
// 普通 error → 业务错误:SDK 自动把 CallToolResult.IsError 置为 true
return nil, out, fmt.Errorf("查询日志失败: %w", err)

// *jsonrpc.Error → 协议错误:客户端 CallTool 返回非 nil error
return nil, out, &jsonrpc.Error{
	Code:    jsonrpc.CodeInvalidParams,
	Message: "start_time 不能晚于 end_time",
}
```

怎么选?判断标准是:**客户端不修正输入,重试还有没有意义**。有意义(上游超时、下游抖动),返回普通 error,把情况说清楚,让 LLM 自己重试或换参数;没意义(参数组合本身就非法,怎么重试都一样),返回 `*jsonrpc.Error`,比如「开始时间晚于结束时间」这种跨字段约束——schema 表达不了字段之间的关系,只能在 handler 里拦:

```go
import "github.com/modelcontextprotocol/go-sdk/jsonrpc"

func myTool(_ context.Context, req *mcp.CallToolRequest, in myInput) (*mcp.CallToolResult, myOutput, error) {
	if in.StartTime.After(in.EndTime) {
		return nil, myOutput{}, &jsonrpc.Error{
			Code:    jsonrpc.CodeInvalidParams,
			Message: "start_time 不能晚于 end_time",
		}
	}
	// ...
}
```

还有一点容易误解:协议错误并不是都要你亲手处理。工具名不存在、参数不符合 schema、prompt 名不存在,这类请求 SDK 在进 handler **之前**就拦掉了——你要做的只是把工具名和 schema 设计对,代码层面不用写任何东西。

# 参数校验,SDK 已经帮你做了

泛型 `mcp.AddTool` 在调用你的 handler 之前会自动做两件事:按 `InputSchema` 校验参数(字段类型、必填、枚举),以及给带 `default` 的字段填充默认值。校验不过,handler 根本不会被执行,客户端直接收到 `InvalidParams`(-32602)。

所以格式层面的约束(类型、必填、枚举)不用在 handler 里重复校验;你只负责 schema 表达不了的业务约束。

# 资源与提示词的错误处理

资源 handler 的失败分两种,记一个区分就行:

**URI 不匹配(资源不存在),用 `mcp.ResourceNotFoundError`**,别用 `fmt.Errorf`。前者带标准错误码 -32002,并且把请求的 URI 放进 `data.uri`,客户端才能分清「没找到」和「内部错误」:

```go
func readDemoMarkdown(_ context.Context, req *mcp.ReadResourceRequest) (*mcp.ReadResourceResult, error) {
	if req.Params.URI != demoResourceURI {
		return nil, mcp.ResourceNotFoundError(req.Params.URI)
	}
	// ...
}
```

**读文件、网络请求这类 IO 失败,返回普通 error 就行**,SDK 会把它作为协议错误传给客户端:

```go
data, err := os.ReadFile(demoMarkdownFile)
if err != nil {
	return nil, fmt.Errorf("读取 %s: %w", demoMarkdownFile, err)
}
```

提示词(prompt)没有 isError 那套机制:handler 返回的任何 error 都会变成 JSON-RPC 协议错误,客户端只能从 err 感知失败。未知的 prompt 名同样由 SDK 在进 handler 前拦下,返回 InvalidParams。

# 客户端怎么接错误

客户端要分三层判断,缺一层都可能丢信息:

```go
// 第 1 层:连接失败——session 都没有,直接退出
session, err := client.Connect(ctx, transport, nil)
if err != nil {
	log.Fatalf("connect: %v", err)
}

// 第 2 层:协议错误(工具不存在、schema 校验失败等),res 不可用
res, err := session.CallTool(ctx, &mcp.CallToolParams{
	Name:      "query_log",
	Arguments: args,
})
if err != nil {
	log.Fatalf("CallTool protocol error: %v", err)
}

// 第 3 层:业务错误——RPC 成功但 isError=true,content 里是可读的错误描述
if res.IsError {
	log.Printf("tool reported failure: %+v", res.Content)
	// 到这里 LLM 还能决定重试或换参数,别直接当崩溃处理
}

// 三层都过了,res.Content 才是正常数据
```

如果服务端想在中间件里统一记录业务错误,`AddReceivingMiddleware` 包一层、对结果做类型断言就行:

```go
srv.AddReceivingMiddleware(func(next mcp.MiddlewareHandler) mcp.MiddlewareHandler {
	return func(ctx context.Context, req *mcp.Request) (any, error) {
		res, err := next(ctx, req)
		if toolRes, ok := res.(*mcp.CallToolResult); ok && toolRes.IsError {
			log.Printf("tool business error: %v", toolRes.GetError())
		}
		return res, err
	}
})
```

`GetError()` 只在服务端中间件里有意义,客户端收到的 CallToolResult 没这个方法。

# 错误码速查

| 常量 | 值 | 典型场景 |
| --- | --- | --- |
| `CodeParseError` | -32700 | 请求体不是合法 JSON |
| `CodeInvalidRequest` | -32600 | 不符合 JSON-RPC 2.0 格式,缺 method/jsonrpc 字段 |
| `CodeMethodNotFound` | -32601 | 打错 MCP 方法名 |
| `CodeInvalidParams` | -32602 | 工具/prompt 名不存在、schema 校验失败、参数语义非法 |
| `CodeInternalError` | -32603 | 服务端内部错误,如模板渲染失败、未捕获 panic |
| `CodeResourceNotFound` | -32002 | 资源未找到(`mcp.ResourceNotFoundError`) |

# 写错误信息的几个习惯

- **带上下文**:`fmt.Errorf("查询日志失败 service=%s range=%s: %w", svc, timeRange, err)`,别只回一个 "error"——LLM 没有别的渠道了解现场。
- **包装用 `%w`**,保留 `errors.Is` / `errors.As` 可解包的能力。
- **别在 handler 里 panic**:SDK 不保证所有传输方式都能帮你 recover,可预见的错误都以 error 形式返回。
- **进程级错误不归 MCP 协议管**:`http.ListenAndServe`、`gin.Run` 失败,log.Fatal 处理即可,此时会话已不可能建立,谈不上发协议错误;HTTP 层鉴权失败(401/403)也一样,在 MCP handler 之前就被拦掉,不产生任何 MCP 消息。
