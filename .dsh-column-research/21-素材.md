# 第 21 篇素材包：关键一步让人拍板

对象：审批 seam（`ctx.approval`）、提问 seam（`ctx.userQuestions` + `ask_user_question`）、plan mode 的「先方案后执行」。
仓库：`local/deepseek-harness/`。所有 `path:line` 相对该仓库根。

## 机制说明

本篇要讲清：**在 DSH 里「让人拍板」不是一个弹窗，而是一条有契约、有审计、且有明确失败方向的问答通道**。12 篇（[[12-拦住模型乱来]]）只说了「pre-execute 返回 `ask`，然后由 `ctx.approval.request()` 处理」，并把 `ApprovalRequest`/answerer/会话级策略明确留到本篇；20 篇讲了「能不能」（沙箱）。本篇补齐「该不该」。

三个子机制，边界要一次说清：

1. **审批（approval）——针对「一次具体动作」的是非题。**
   `ctx.approval` 是 `ApprovalService`（`packages/interaction/user-approval/src/index.ts:143`）。它回答的问题只有一个：这个特定的动作能不能做。契约是「一次性」的：`ApprovalOutcome` 的四个取值 `'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'`，**只有 `allowed-once` 是放行**，另外三个都必须当成拒绝（`packages/interaction/user-approval/src/types.ts:28-32`）。它自带审计：每一次问都会在会话日志里落一对 `approval/asked` + `approval/decided`，两个事件用同一个 `ApprovalRequestId` 配对（`types.ts:34-59`）。
2. **提问（user-questions）——针对「人要选/要答」的问答题。**
   `ctx.userQuestions` 是另一条 seam：问题带 id、可选选项、可选多选、可选自定义文本，还带一个「展示意图」（目前只有 `plan-review`）让能识别的界面把它渲染成方案评审而不是普通选项列表（`packages/interaction/user-questions/src/types.ts:21-48`）。模型侧的使用者是 `ask_user_question` 工具（`packages/interaction/tool-ask-user/src/index.ts:20-100`）。
3. **plan mode——把「先方案、后执行」变成会话状态。**
   `ctx.planMode` 是**软约束**：`docs/subsystems/plan.md:5` 原文就是 `Plan mode is **soft guidance**`。它不禁任何工具，只是给每次模型请求加一段部署自己写的指导语，并提供一个 `exit_plan_mode` 工具把完整方案交给人评审。沙箱模式和审批策略各自独立，谁也不读写 plan 状态（`packages/plan/plan-mode/src/index.ts:1-7`）。**这一条要重点纠偏**：读者很容易以为 plan mode 是「执行被拦住了」，实际拦住的是模型自己的分寸，真正的硬边界仍然来自审批与沙箱。

三条 seam 的关系用一句话钉住：**审批是「这次动作准不准」的闭集判定；提问是「人要给信息/做选择」的开放问答；plan mode 用提问 seam 实现「方案先过目」，自己不产生任何强制力。**

接线（12 篇的表格往下一层）：

```
tools/pre-execute 返回 { kind: 'ask' }
  → ToolRuntime.serviceAsk()            packages/core/tools/src/index.ts:1679
  → ctx.approval.request({ agent, toolName, callId, reason, signal })
  → 服务先套会话策略（never 直接 rejected）
  → 再走 approval/request 瀑布，交给已装配的 answerer
  → 结局写回 approval/decided，并把 isError 结果交回模型
```

无人能答时必须 fail-closed，这是本条通道最要紧的性质：没有 answerer、没有 approval 服务、没有 agent、answerer 抛错、answerer 返回词表外的值——全部落到拒绝或 `'unavailable'`，绝不默认放行（工具侧 `packages/core/tools/src/index.ts:1679-1719` 的 `serviceAsk`；审批侧 `packages/interaction/user-approval/src/index.ts:273-285`）。

**2. 一次问的三个动作：先问、再判、后记账**（`packages/interaction/user-approval/src/index.ts:208-227`）

```ts
  async request(req: ApprovalRequest): Promise<ApprovalOutcome> {
    const session = req.agent.session
    if (!hasOpenTurn(session)) {
      throw new Error(
        'approval.request() outside an open turn: the approval/asked + approval/decided audit pair '
        + 'must be turn-enclosed (a bare event between turns is crash-tail garbage on reload). '
        + 'Ask from inside the turn that needs the decision.',
      )
    }
    const id = ApprovalRequestId(randomUUID())
    session.append('approval/asked', {
      id,
      toolName: req.toolName,
      ...req.callId !== undefined ? { callId: req.callId } : {},
      ...req.reason !== undefined ? { reason: req.reason } : {},
    })
    const outcome = await this.decide(req, session)
    session.append('approval/decided', { id, outcome })
    return outcome
  }
```

**3. 会话策略先于任何 answerer，且一切都 fail-closed**（`packages/interaction/user-approval/src/index.ts:260-285`）

```ts
  private async decide(req: ApprovalRequest, session: Session): Promise<ApprovalOutcome> {
    const signal = req.signal
    if (signal?.aborted) return 'cancelled'
    // The 'never' policy is decided HERE, before any dispatch: a listener
    // registered with `prepend: true` after this service mounts would sit
    // ahead of any gate LISTENER, so a listener-shaped gate cannot keep the
    // documented promise that 'never' rejects deterministically regardless
    // of registration order — only the service's own request path can.
    if (this.effectivePolicy(session) === 'never') return 'rejected'
    // Enter the promise chain BEFORE dispatching: a listener that throws
    // SYNCHRONOUSLY (before its first await) must land in the same rejection
    // path as an async one — `Promise.resolve(call())` would let it escape
    // the containment into the caller.
    const answer: Promise<ApprovalOutcome> = Promise.resolve().then(
      () => this.ctx.waterfall(
        scopeTarget(req.agent, req.agent), 'approval/request', req,
        () => Promise.resolve<ApprovalOutcome>('unavailable'),
      ),
    ).then(
      // Normalize a rogue (non-vocabulary) answerer return to the fail-closed
      // outcome instead of leaking it into callers' closed-union switches.
      outcome => OUTCOMES.includes(outcome) ? outcome : 'unavailable',
      // A throwing answerer must fail the QUESTION closed, not the caller's
      // tool call open — the seam contains its callbacks.
      () => 'unavailable',
    )
```

  async ask(request: AskUserQuestionRequest): Promise<AskUserQuestionAnswer> {
    if (request.signal?.aborted) {
      throw abortedQuestion()
    }
    if (request.questions.length === 0) {
      throw new UserQuestionError('ask_user_question requires at least one question', 'EMPTY_QUESTIONS')
    }
    const agent = request.agent
    if (agent !== undefined) {
      const agents = this.ctx.get('agents')
      if (agents === undefined || agents.get(agent.id) !== agent) {
        throw new UserQuestionError(
          'human interaction requires the exact live calling agent when an agent is supplied',
          'CALLER_NOT_LIVE')
      }
      if (!agents.roots().includes(agent)) {
        throw new UserQuestionError(
          'human interaction is unavailable while the calling agent is owned by another live agent; '
          + "include the unresolved question or decision in the child agent's final result",
          'DELEGATED_CALLER')
      }
    }

## 内置消费者

- **工具运行时**（`packages/core/tools/src/index.ts:1679-1719`）：`ask` 的唯一内置消费者。它用 `ctx.get('approval')` 机会式获取服务——没有审批服务时降级为 deny，而不是报错（:1683-1689）。取消（`cancelled`）会额外标 `approvalCancelled`，管线据此把结果归因成「调用方取消」而不是普通拒绝（:1709-1712，`prepareExecution` 里 :1473-1475 会用到）。
- **沙箱升级的三个工具**：`tool-bash`、`tool-pwsh`、`tool-fs`。它们不直接调 `ctx.approval`，而是把 `ctx.get('approval')` 作为 `EscalationApprover` 交给 `approveEscalation`（`packages/sandbox/sandbox/src/escalation.ts:157-189`；fs 侧装配见 `packages/fs/tool-fs/src/sandbox.ts:97-106`）。这是「审批」与「沙箱」的交界，也是 12 篇那张表的真实实现。
- **ACP 桥**（`packages/acp/acp/src/index.ts:152-173`）：机器回答方。它只向 ACP 客户端要一次性选择（`allow-once` / `reject-once`），且注释明确「绝不从未知客户端响应推断持久授权」。
- **`api-remotes`**：把 `approval/request` 与 `user-questions/request` 两条瀑布登记为可转发到客户端的远程事件（`packages/api/remotes/src/remote-events.ts:18`、`:35`）；Web 侧由此挂上 `ui-approval`、`ui-user-questions`（`packages/bundle/web-app/cordis.patch.yml:195-196`、`252-253`、`345-346`）。
- **`tool-ask-user`**：`ctx.userQuestions` 的模型侧消费者，工具名 `ask_user_question`；把 `multi_select` 映射成 `multiSelect`，并把 `exec.agent`、`exec.signal` 透传（`packages/interaction/tool-ask-user/src/index.ts:80-99`）。
- **`plan-mode`**：`ctx.userQuestions` 的另一个消费者，用 `plan-review` 意图把方案交人评审（`packages/plan/plan-mode/src/index.ts:298-330`）；同时注册 `exit_plan_mode` 工具与 `/plan` 命令（:273-361、:225-271）。
- **`permission-presets`**：审批策略是它打包的两个旋钮之一，切换时用 `ctx.approval.setPolicy(agent, policy)`（活会话）或 `setApprovalPolicy(session, policy)`（新会话初始化），见 `packages/interaction/permission-presets/src/index.ts:273`、:382、:417、:429。
- **子代理继承**：测试证据显示派生的子代理会被种上 `approval/policy` 的 `never` 覆盖（`source: 'delegation'`），父会话仍是 `undefined`（`packages/subagent/subagent/tests/continuation-inheritance.spec.ts:85-115`）。这是「无人能答的子代理自动收紧」的现行行为。

## 失败模式与坑

- **在 turn 外问会直接抛**：`approval.request() outside an open turn: the approval/asked + approval/decided audit pair must be turn-enclosed (a bare event between turns is crash-tail garbage on reload). Ask from inside the turn that needs the decision.`（`packages/interaction/user-approval/src/index.ts:211-215`）。原因在 :70-76 的注释里：turn 是可重放日志的提交边界，两条 turn 之间的事件会被当成崩溃残尾丢掉。插件想在「打开前」问人，必须借一个正在进行的工具调用，或在 prompt 阶段问。
- **没人答 = 拒绝，不是等待**：瀑布的 no-answer 兜底是 `'unavailable'`（`index.ts:275-277`），工具侧文案是 `tool "<name>" requires approval, but no approval channel is available`（`packages/core/tools/src/index.ts:1713-1716`）。headless 就是这种情形：它只叠在 base 上，不装配 `api-remotes` 与任何 UI answerer，而 base 的审批默认是 `ask`（`packages/bundle/headless/cordis.patch.yml:1-31`；`packages/bundle/base/cordis.patch.yml:224-227`）。
- **`never` 策略的模型可见文案**：`Approval prompts are disabled in this session: actions that require approval are rejected automatically — do not request sandbox escalation (do not set `sandbox_permissions`).`（`packages/interaction/user-approval/src/index.ts:66`）。这句会作为运行上下文进模型请求，所以模型会「知道」不要去申请升级。用户在会话里看到这句话，就是 `approval/policy = 'never'` 的直接表象。
- **`never` 无法被 listener 越过**：注释明确，即便有人在服务之后用 `prepend: true` 注册监听器，`never` 也在分发之前于服务内部判掉（`index.ts:263-268`）。想「临时放行一次」不能靠挂监听器。
- **返回值异常一律当无人应答**：answerer 返回非词表值时被归一化成 `'unavailable'`；answerer 抛错（含同步抛）也被兜成 `'unavailable'`（`index.ts:273-285`）。作者不要指望「返回 undefined 表示默认允许」。
- **取消有两条路**：`signal` 已中止 → 立刻 `'cancelled'`；分发中中止 → 竞速取胜，迟到的回答被丢弃（`index.ts:287-299`）。工具侧把这类拒绝标成 `approvalCancelled` 并归因给调用方取消（`packages/core/tools/src/index.ts:1709-1712`、:1473-1475）。
- **审计成对是不变量，不是惯例**：`approval/asked` 在 turn 外、toolName 为空、同 id 重复开启，都会让不变量失败；`approval/decided` 没有配对的 asked、或 outcome 不在词表内，同样失败（`packages/interaction/user-approval/src/invariant.ts:32-49`）。写调试代码手工 append 这两个事件时会撞上。
- **`approval/*` 不进模型对话**：`approval/asked` 与 `approval/decided` 都是 log-only（`types.ts:36-43`、:50-54），模型看到的是工具结果 + 运行上下文快照。**审计在会话记录里**：要查「谁在什么时候问了什么、结论如何」，读会话日志的这两类事件即可，用同一个 `ApprovalRequestId` 把问答配上（会话日志本身可用 `dsh` 的会话查看能力或直接读 JSONL，未在本次调研中执行验证）。
- **文档与代码不一致（写文章时别照抄文档）**：`docs/subsystems/approval.md:33` 写「消费方用 `ctx.approval.effectivePolicy(session)` 读有效策略」，但源码里 `effectivePolicy` 是 **private**（`packages/interaction/user-approval/src/index.ts:236`），仓库内调用点只有本类自己（:151、:178、:268）。插件要读有效策略只能自己折叠：`ctx.approval.overrideOf(session) ?? ctx.approval.config.policy ?? 'ask'`。
- **子代理问不了人**：`ctx.userQuestions.ask` 带 agent 时要求它是「注册表里同一个活实例」且是运行根，否则分别抛 `CALLER_NOT_LIVE` 与 `DELEGATED_CALLER`；后者的报错文本本身就是给模型的建议（`packages/interaction/user-questions/src/index.ts:94-106`）。这是「子代理不该卡在等人」的现行设计。
- **展示意图有前置断言**：`intent: { kind: 'plan-review', approve }` 里的 `approve` 必须是该问题自己的选项之一，且该问题必须带 `detail`，否则 `ask()` 抛 `BAD_INTENT`（`packages/interaction/user-questions/src/index.ts:108-129`）。理由注释写得很清楚：否则会把「提问者从没提供过的选项」或「对不可见内容的批准」摆到用户面前。
- **plan mode 的四个失败面**（`packages/plan/plan-mode/src/index.ts`）：没有 `ctx.userQuestions` → 抛 `no user-questions channel is available to review the plan…`（:298-301）；评审期间插件被重载 → 抛 `the plan-mode service was reloaded while the plan was under review; present the plan again`（:331-335）；用户选择「继续规划」→ 是一次失败调用，携带反馈（:336-343）；用户直接关掉评审 → 转成 `The user dismissed the plan review to speak instead…`（:319-330）。另有 `exit_plan_mode` 在非 plan mode 下调用直接抛错（:292-294），以及方案必须以 `#` 开头（:295-297）。
- **plan mode 有一个真实的持久化缺口**：在「某轮最后一个被接受的 pre-step 之后」做出的选择只存在于进程内，进程若在此之前退出就丢了（`docs/subsystems/plan.md:17` 的 README limitation 链接）。**未确认**具体 README 锚点内容（本次只读到文档里的链接文字）。
- **`--dump-config` 相关**：审批策略的默认值在配置目录里可查（`docs/config-catalog.md:1597-1634` 是 `permission-presets` 的 `presets` 与 `defaultPreset`；`approval` 服务的 `policy` 定义在 `packages/interaction/user-approval/src/index.ts:128-136`）。CLI 的 `--dump-config` 会把装配后的配置转储（`apps/cli/tests/args.spec.ts:72-87`）。**未确认**：转储里 approval 段的实际键名与嵌套层级。

## 外部插件可行性

**结论：完全可行，而且这两条 seam 是外部插件最容易上手的「深挖」对象——因为它们都是纯 host 侧服务，没有任何浏览器/构建管线依赖。**

证据：

1. 相关包 `package.json` 均为 `publishConfig: { "access": "public" }`，**无 `private: true`**：`@deepseek-ai/dsh-user-approval`（exports 含 `.`、`./invariant`、`./types`）、`@deepseek-ai/dsh-user-questions`、`@deepseek-ai/dsh-tool-ask-user`、`@deepseek-ai/dsh-plan-mode`、`@deepseek-ai/dsh-permission-presets`。
2. 已有外部插件实测从 npm 装过这些包：`code/dsh_plugin/dsh-event-log/` 的依赖里就有 `@deepseek-ai/dsh-user-approval: ^0.1.7-rc.1`，其 `node_modules` 里落的版本是 `0.1.7-rc.2`（exports 里 `./types`、`./invariant` 都在）。
3. 三条 seam 的扩展点都是公开机制：审批用 `ctx.approval.request()`；回答方用 `ctx.on('approval/request', …)` 的 waterfall；提问用 `ctx.userQuestions.ask()` 或 `ctx.on('user-questions/request', …)`。这些都是普通 Cordis 事件/服务，`apply(ctx)` 里就能用。

需要哪些依赖（按用法）：

- 只想挂一层拦截、返回 `ask`：`@deepseek-ai/dsh-tools`（`PreToolDecision` 类型）。
- 想直接问人：`@deepseek-ai/dsh-user-approval` + `inject: ['approval']`（`ApprovalOutcome`、`ApprovalRequest` 类型）。
- 想自己当回答方（自动化批准/拒绝）：`@deepseek-ai/dsh-user-approval`，挂 `approval/request` 瀑布。
- 想问开放性问题/带选项：`@deepseek-ai/dsh-user-questions` + `inject: ['userQuestions']`。
- 想读写 plan 状态：`@deepseek-ai/dsh-plan-mode`。

**限制与注意**：

- 这些服务是「可能没装配」的可选依赖。`ctx.get('approval')` 返回 `undefined` 是正常情形（headless/纯 SDK 装配），必须处理；用 `inject: ['approval']` 写死会让插件在那些 profile 下一直挂起。
- `approval.request()` 的成功前提是**当前处于打开的 turn**，所以它只能从工具执行内部（或别的 turn 内回调）调用；插件在 `apply()` 阶段或会话空闲期问人一定抛错。
- plan mode 的 `./client`、permission-presets 的 `./client` 是浏览器半入口（给客户端聚合用）；本篇 demo 用不到，**不构成限制**。14 篇遇到的 `ctx.remote` 那类「只有仓库内构建管线才走得通」的问题，在本篇的两个 seam 上不存在——**依据**：两者的核心 API 都在 host 侧的 `src/index.ts` 里，且已发布的 `lib/index.js` + `lib/types/*.d.ts` 正是外部插件消费的产物（`packages/interaction/user-approval/package.json` 的 `files` 字段）。

## demo 设计建议

插件名：`dsh-ask-before-bash`（`dsh-` 前缀）。

目录结构：

```
dsh-ask-before-bash/
├── package.json      # private，dsh.bundle.patch -> ./patch.yaml，依赖 @deepseek-ai/cordis、@deepseek-ai/dsh-tools
├── patch.yaml        # - insert: - id: dsh-ask-before-bash name: '<绝对路径>/src/dsh-ask-before-bash.ts'
├── install.sh        # dsh plugin --profile test add "link:$PWD"
└── src/
    └── dsh-ask-before-bash.ts
```

核心骨架（约 75 行）：对匹配危险模式的 `bash` 调用返回 `ask`，并订阅审计对把「谁问了什么、结论如何」打出来——正好把 12 篇的挂点接上本篇的两条 seam。

```ts
/**
 * 危险 bash 调用先问人：`tools/pre-execute` 返回 `{ kind: 'ask' }`，
 * 剩下的路由、判定、审计全部交给 `ctx.approval`。
 *
 * 审计对（approval/asked + approval/decided）是 log-only 的会话事件，
 * 不进模型对话，这里只是顺手把它们打印出来，方便对着日志讲。
 *
 * @module dsh-ask-before-bash
 */
import type { Context } from '@deepseek-ai/cordis'
import type {} from '@deepseek-ai/dsh-user-approval'

export const name = 'dsh-ask-before-bash'
export const inject = ['tools']

/** 需要人拍板的命令模式，理由写给用户也写给模型。 */
const NEEDS_APPROVAL: readonly { pattern: RegExp; reason: string }[] = [
    { pattern: /\bgit\s+push\b/, reason: '这条命令会推送到远端仓库，请确认目标和分支。' },
    { pattern: /\b(rm|mv)\s+-[a-zA-Z]*r/, reason: '递归删除或移动，确认路径无误再继续。' },
    { pattern: /\bnpm\s+publish\b|\bpnpm\s+publish\b/, reason: '这会发布一个包，无法撤回。' },
]

export function apply(ctx: Context): void {
    // 返回 { kind: 'ask' } 只表示「这事要问人」；谁来问、怎么问是审批服务的事。
    ctx.on('tools/pre-execute', (exec, next) => {
        if (exec.name !== 'bash') return next()
        const command = (exec.arguments as { command?: unknown }).command
        if (typeof command !== 'string') return next()
        const hit = NEEDS_APPROVAL.find(entry => entry.pattern.test(command))
        return hit === undefined ? next() : { kind: 'ask', reason: hit.reason }
    })

    // 问与答各落一条事件，用同一个 id 配对；会话日志里能查到完整审计。
    ctx.on('session/event', (session, event) => {
        if (event.type === 'approval/asked') {
            console.log(`[${name}] 问：${event.data.toolName}（${event.data.reason ?? '无理由'}）`)
        }
        if (event.type === 'approval/decided') {
            console.log(`[${name}] 答：${event.data.outcome}`)
        }
    })
}
```

装法与验证：

```sh
cd code/dsh_plugin/dsh-ask-before-bash
pnpm install
dsh plugin --profile test add "link:$PWD"
# 让模型执行 git push（或临时把模式改成匹配 ls 的正则），界面上应出现审批卡；
# 拒绝后模型收到的失败原因是 the user rejected tool "bash"
```

验证点（三条正好对应三个机制）：① 批准一次后**同一命令再次执行仍会问**（`allowed-once` 只作用于这一次）；② 切到 `never` 策略后不再弹卡，模型直接收到自动拒绝，且系统提示里出现 `Approval prompts are disabled in this session…`；③ 换成 `--profile headless` 跑同一命令，得到 `no approval channel is available`——fail-closed 的现场。

## 与其他篇的交界

**12 篇（[[12-拦住模型乱来]]）已经讲过的**：`tools/pre-execute` 这个钩子本身；`ask` 是四个拦截点之一；「返回 `ask` 之后由 `ctx.approval.request()` 处理」这句挂点说明；以及 `unavailable` 是 fail-closed 的结果（那篇是从 09 篇的事件统计里顺带提到的）。本篇**不重复**那张三行表和 guard 的用法。
