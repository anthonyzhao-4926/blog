## 机制说明

### 1.1 这篇要讲清的三件事，以及它们为什么是三件事

读者说的「花了多少」，拆开是三个不同的问题，落在三个互不依赖的机制上：

| 问题 | 机制 | 一句话 |
| --- | --- | --- |
| 这个会话/这次请求压着多少 token？ | `ctx.tokenMeter`（`@deepseek-ai/dsh-token-meter`） | 重放会话日志折出「压力」与「表面价格」；不是计数器累加 |
| 这个会话花了多少时间、多少步？ | `ctx.sessionProjections` 的 `sessionStats` 单元（`@deepseek-ai/dsh-session-stats`） | 一个纯函数把 `step/end`、`tool/call→tool/result`、组装好的 assistant 消息折成墙钟时长 |
| 这些数据会不会被发出去？发之前脱敏脱什么？ | `ctx.sessionTelemetry`（`@deepseek-ai/dsh-session-telemetry` + `-otel`） | seam 自己**不脱任何东西**；默认连发都不发（只在用户显式提交 feedback 时发） |

再外加一件小事：`time-context`（`@deepseek-ai/dsh-time-context`）给模型塞一个时钟，让「三天前」这种说法有个锚。它跟前三者无关，是**注入类**插件，放在同一篇只因为它也在回答「这一趟到底过了多久」。

### 1.2 「可重放计量」到底是什么意思（本篇的核心）

先破一个直觉：**它不是计数器累加。**

一个计数器（`total += usage`）在下列任一情况下会算错：

- 会话被 resume 到新进程 —— 内存里的累加值没了；
- 发生 compaction，表面被替换 —— 被遮蔽的内容不该再算进「下一次请求有多大」；
- 同一步里发生过失败重试，authoritative 的 attempt 被替换过。

DSH 的答案是：**把计量做成会话日志上的一个可续跑的折叠（fold），日志是唯一真相，任何时刻都能从零重算出同一个数。**

`TokenMeter` 每个 session 存一份极小的游标状态（`packages/llm/token-meter/src/index.ts:107`）：

```ts
  private readonly states = new WeakMap<Session, ReplayState>()
```

`ReplayState` 只有五个字段（`index.ts:61-67`）：`consumedEvents`（已消费到第几个持久事件）、`header`（最近的规范请求信封）、`surface`（已计价的表面节点）、`stepStart`（当前开着的 step）、`anchor`（最近一次成功调用的锚）。每次 `measure()` 先 `_sync()` 把游标推到日志尾（`index.ts:231-237`）：

```ts
    while (state.consumedEvents < session.seq) {
      const event = session.eventAt(SessionSeq(state.consumedEvents))!
      this._foldEvent(state, event)
      state.consumedEvents = SessionLogOffset(state.consumedEvents + 1)
    }
```

「可重放」的三个具体含义：

1. **游标式**：`consumedEvents` 是持久 seq，进程重来就从日志重新折一遍，不依赖任何内存累加值。返回的 `TokenMeasurement.logRevision` 就是「这次测量消费了多少个持久事件」——等于下一个未读事件的 seq（`index.ts:183`，`src/types.ts:15`）。
2. **锚 + 有符号增量**：不是「累加所有 usage」，而是「拿最近一次成功调用的 provider usage 当锚，再按当前表面相对锚的重定价算一个有符号的增量」（`index.ts:155-180`）。所以模型换了、上下文缩了，数字会**减**。
3. **锚只在与当前信封完全一致时才用**：锚只有在 `optionalHeaderEquals(anchor.header, header)`（同 provider/model/参数）**且** provider 报的总量不低于同一调用的完整启发式价格时才成立；否则退回纯启发式（`index.ts:157-180`）：

```ts
      baseline = usage !== undefined && usageTokens(usage) >= estimatedAnchorTokens
        ? { kind: 'usage', tokens: usageTokens(usage), usage }
        : { kind: 'estimated', tokens: estimatedAnchorTokens }
      surfaceDeltaTokens = surface.surfaceTokens - anchorSurfaceTokens
```

最终 `totalTokens = Math.max(0, baseline.tokens + surfaceDeltaTokens)`（`index.ts:186`）——**夹到 0**，因为增量是有符号的。

**没有精确 tokenizer。** 固定启发式就是 `CHARS_PER_TOKEN = 4`、每块结构开销 4、每条消息角色开销 4（`packages/llm/token-meter/src/estimate.ts:12,15,18`）。README 自己承认「reach for a provider tokenizer when a deployment needs exact billing-grade counts」，并且把「不引入 per-provider 精确 tokenizer」列为**明确的已知取舍**（`packages/llm/token-meter/README.md:32,151`）。这条务必写进正文 —— 否则读者会拿它当账单。

**为什么是「廉价的近似」而不是「精确账单」**：因为这份数字的消费者是**压缩策略和占用率显示**（`docs/subsystems/compaction.md:69` 原文：「The seam owns no pricing API: the singleton `ctx.tokenMeter` directly owns estimation and replay」）。压缩要的是「离阈值还有多远」，不是「这次调用多少钱」。CJK 和 JSON schema 会被系统性低估，`ContextPressureProjection` 的注释专门点了这件事（`packages/llm/token-meter/src/projection.ts:54-60`）。

### 1.3 「脱敏脱什么」的正确答案

**seam 自己不脱任何东西。** 这句话有两份原文证据：

- `packages/session/session-telemetry/README.md:116`（Known Limitations 原文）：
  > **No built-in redaction rules** — with no `sessionTelemetry/record` listener mounted, records leave the process exactly as captured, including any credentials embedded in file contents or command output; a deployment exporting to a shared collector owns its rule set.
- `docs/subsystems/session-telemetry.md:142`：
  > The seam ships NO rules of its own: with no listener mounted, records reach the backend exactly as captured, so exported data is precisely as clean as the rules a deployment mounts.

所以「脱敏」是**部署方挂规则**：在 `session-telemetry/record` waterfall 上挂一个监听器，对每条出站记录做变换。仓库里唯一的现成范例是测试夹具 `packages/session/session-telemetry-otel/tests/fixtures/telemetry-redact-rule.ts`（用正则把形如 `sk-e2efixture<数字>` 的凭据替换成 `[E2E-REDACTED]`）。

**但还有一层比脱敏更强的保护**：出厂后端 `session-telemetry-otel` 默认 mode 是 `FEEDBACK_ONLY`（`packages/session/session-telemetry-otel/src/index.ts:52`），也就是**普通活动根本不会被捕获**。只有会话日志里出现本会话自己的 `feedback/record`（或本会话的 `feedback/message-put` / `feedback/message-delete`）时，才会把「到那条 seq 为止的完整前缀」交出去（`index.ts:57-66` 的 `isFeedback`、`:246-255`）。base bundle 的注释也写得很直接：

> OTel releases a Session-log prefix only after explicit user feedback, regardless of model provider. **Ordinary activity never triggers capture.**

（`packages/bundle/base/cordis.patch.yml:171-173`。）另外 `DSH_TELEMETRY_DISABLED`（任意非空值，含 `'0'`/`'false'`）会让启动器把这一行 patch 成 `disabled` —— 注意是**启动器 patch 行**，不是靠 config 关，注释原话：「config cannot disable a row」（`cordis.patch.yml:174-176`）。

出厂上传端点与参数（`cordis.patch.yml:186-196`）：`url: !!js process.env.DSH_TELEMETRY_OTLP_URL ?? 'https://harness-telemetry.deepseeksvc.com/v1/logs'`、`compression: gzip`、`timeoutMillis: 1000`、`scheduledDelayMillis: 10000`、`maxQueueSize: 2048`、`maxExportBatchSize: 2048`、`exportTimeoutMillis: 1500`、`shutdownTimeoutMillis: 3000`。

### 1.4 time-context 到底给模型注入什么

**一条 `user/message`，三行文本**，插在 `agent/pre-step` 的返回消息列表末尾。三行原文（`packages/context/time-context/src/index.ts:105-107`）：

```ts
  return `Time sampled while preparing turn ${turn}, step ${step}: ${formatTimestamp(now, formatter, timeZone)}\n`
    + `${browserText}\n`
    + `Elapsed since the preceding ${baseline}: ${elapsed}.`
```

三行分别是什么：

1. **时间戳**：ISO 形状 + 数字偏移 + 方括号里的 IANA 时区，例如 `2026-09-12T18:04:31+08:00[Asia/Shanghai]`（`packages/context/time-context/src/timestamp.ts` 的 `formatTimestamp` 最后一个模板字符串）。
2. **浏览器时区策略**（`request-zone.ts:66-78` 的三种渲染）：
   - 唯一：`` `Browser time zone for this request: ${timeZone}. ` + 'Interpret otherwise-unqualified dates and times in this zone.' ``
   - 混合：`` `Browser time zone for this request: mixed ${JSON.stringify(timeZones)}. ` + 'Ask the user to clarify otherwise-unqualified dates and times.' ``
   - 缺失：`'Browser time zone for this request: unavailable. ' + 'Ask the user to clarify otherwise-unqualified dates and times.'`
3. **距上一条的时间**：紧凑整秒单位（`${d}d ${h}h ${m}m ${s}s`，`index.ts:63-77` 的 `formatDuration`）。基线怎么选很关键（`index.ts:103`、`:196-198`）：**step 1** 从「最近一条模型可见消息」算起（baseline 文案 `'model-visible message'`）；**step ≥ 2** 从本轮里上一次 time-context 注入算起（baseline 文案 `'step context'`）。没有基线时字面量就是 `unavailable`。

几个容易漏掉的事实：

- 它在 `agent/pre-step` 上注册时用了 `{ prepend: true }`（`index.ts:221`），并且是**先 `await next()` 拿到下游决定**，只有决定不是 `reject` 且没被 abort 才追加（`index.ts:181-186`）。所以它读得到本轮已进入/已提议的全部 user 消息（`index.ts:80-91` 的 `requestMessages`）。
- 注入消息的来源标记是 `{ kind: 'plugin', plugin: 'time-context', form: 'snapshot', sections: [{ name, text }] }`（`index.ts:217`，README「The model gets」一节也写了同一串）。
- 它默认**根本不在装配里**。README 原文：「The plugin is opt-in: default compositions leave it disabled, and the Schedule Web overlay mounts it」（`packages/context/time-context/README.md:13`）。全仓检索 `dsh-time-context`，唯一的装配点是 `apps/cli/config/examples/schedule/cordis.yml:4-7`。
- 刷新节流：`refreshIntervalMs` 省略或 `0` 就是**每个合格 step 都注入**（README 的配置表；`index.ts:189-194` 是那段节流判断）。
- 时区优先级：本轮所有 `user-rpc` 消息里那个**唯一**的浏览器时区 → 否则用配置的 `timeZone` → 否则进程时区（加载时解析一次，`index.ts:132-141`）。

### 1.5 挂到读者已有心智模型上

- **09 篇订阅 `session/event`** → `TokenMeter` 的构造函数里就有一句 `ctx.on('session/event', session => { if (this.states.has(session)) this._sync(session) })`（`packages/llm/token-meter/src/index.ts:119-121`）。这是「读者已经会写的东西，内置实现也在写」的最好例证：**读数改由事件驱动地追平游标**，而不是在测量时仓促补算。注意它只在 `states` 里已经有这个 session 时才追 —— 没被读过的会话不产生状态。
- **10 篇会话事件 vs Cordis 事件** → 这里全是会话事件（`assistant/message`、`step/start`、`step/end`、`request/header`、`tool/result`、`llm/retry`），没有一个是 Cordis 总线事件。
- **08 篇服务定义 / provider / 消费者** → `ctx.tokenMeter` 是 `Service`；`Plugin` 形态是**服务包**（`export class TokenMeter extends Service`，`export default TokenMeter`），而不是函数插件。这跟读者写过的工具插件不同，值得点一句。
- **06 篇 `Config`** → token-meter **没有配置项**：`TokenMeterConfig = Record<string, never>`（`packages/llm/token-meter/src/types.ts:13`），而且**写了键会抛**（`index.ts:87-91`）。这是「配置项该不该有」的一个反例：它是 fixed heuristic，就干脆一个旋钮都不给。
- **15 篇 slot / 客户端** → `tokenUsage` / `contextPressure` / `contextBreakdown` 三个 key 都在 `SessionProjectionMap`（wire 侧）里，所以客户端能直接读到；`sessionStats` 也是。这正是 15 篇「在界面上看自己的数据」在内置功能里的同一条路。

### 3.2 折叠里唯一会抛的地方（fail-closed）

`packages/llm/token-meter/src/index.ts:241-273`（节选）

```ts
  /**
   * Run every fallible step — surface plan and anchor validation — before
   * mutating replay state, so a malformed event remains unread on every
   * retry instead of half-applying.
   */
  private _foldEvent(state: ReplayState, event: SessionEvent): void {
    let nextHeader = state.header
    let nextStepStart = state.stepStart
    let nextAnchor = state.anchor

    switch (event.type) {
      case 'request/header':
        nextHeader = canonicalHeader(event.data.header)
        break
      case 'step/start':
        if (state.stepStart !== undefined) {
          throw new Error(
            `token meter: step/start at seq ${event.seq} arrived before turn ${state.stepStart.turn}/step ${state.stepStart.step} ended`,
          )
        }
        nextStepStart = { ...event.data }
        break
      case 'step/end':
        if (state.stepStart === undefined
          || state.stepStart.turn !== event.data.turn
          || state.stepStart.step !== event.data.step) {
          throw new Error(`token meter: step/end at seq ${event.seq} has no matching step/start event`)
        }
        nextStepStart = undefined
        break
      default:
        break
    }
```

讲法：所有会失败的步骤先在局部变量上跑完，再一次性提交（`index.ts:310-315`）。README 的原话是「The fold is total and allocation-fresh: a malformed event throws before any mutation, so the same log fails identically on every retry」（`packages/llm/token-meter/README.md:80`）。这条跟 23 篇的「检查点 fail-closed」是同一个思路：**坏数据不许半应用**。

/**
 * Deployment-style redaction rule for the telemetry e2e: scrubs the fixture

 * own rules on the `session-telemetry/record` waterfall.

function scrub(value: unknown): unknown {

### 5.2 invariant / fail-closed / fail-soft

**token-meter：坏事件一律抛，且不许半应用。**

- `_foldEvent` 的全部可失败步骤（surface plan、anchor 校验）先在局部变量上跑，最后才提交（`packages/llm/token-meter/src/index.ts:241-246,310-315`）。
- README 原文：「The fold is total and allocation-fresh: a malformed event throws before any mutation, so the same log fails identically on every retry」（`packages/llm/token-meter/README.md:80`）。
- 后果：**一条坏日志会让所有 token 读者一起失败**，而且每次重试都同样失败。这是有意的 —— 数字宁可不出，也不许出一个跟别人不一致的。

**session-telemetry：捕获侧全部 fail-open（不拖累主循环），脱敏侧 fail-closed（宁可扣下这条）。**

- `emit()` 抛异常不会传到循环：`contain()` 包住每一步并只 `logger.warn`（`coordinator.ts:243-249`）。cordis 的 `emit` 是 stop-on-throw，所以「一个失败的订阅者会饿死它之后注册的所有订阅者」—— 这是必须包起来的理由（`coordinator.ts:238-242` 的注释）。
- 但**脱敏监听器抛异常那一整条记录会被扣下**（fail-closed）：`docs/subsystems/session-telemetry.md:142`、`:185`。因为 `redact()` 和 `captureEvent()` 都在同一个 `contain()` 里，所以是「这一条不发、后面的继续」——containment 是 **per-event**（`coordinator.ts:154-155` 注释）。
- `shutdown()` 失败只 `logger.warn`，**永不失败应用拆除**（`docs/subsystems/session-telemetry.md:129`）。
- 交付是 best-effort：游标标记的是 `handed-off` 不是 `delivered`；崩溃（reload window）会丢队列里的记录，新对象重放或 SDK 重试会重复。**接收方必须按 `(session.id, session.format_version, event.seq)` 去重**（`docs/subsystems/session-telemetry.md:58`）。
- ops 记录**故意不带** `event.seq` 身份：它们是用来告警的信号，不是用来求和的条目（同上）。

**time-context：加载期就失败，不做运行期降级。**

- `refreshIntervalMs` 与 `timeZone` 的校验都在 `apply()` 开头（`index.ts:131-140`），注释 `Invalid values fail plugin load`（`index.ts:48`、`docs/config-catalog.md` 同名条目）。
- 注入只在下游决定是 `enter` 且未 abort 时发生（`index.ts:185-186`）；一次注入记录的是「进入了 step」，不是「请求成功发出」—— 后续准备失败可能让它留在历史里（README「Main flow」）。

### 5.3 常见误用

1. **把 token 数当账单。** 它是固定启发式（4 字符 = 1 token）+ provider 锚的混合，README 明确列为已知取舍（`:151`），并且 CJK / JSON schema 会被系统性低估（`projection.ts:54-60`）。
2. **以为 token-meter 有「手动记一笔」的 API。** 没有。公开面只有 `measure()` 与 `estimateMessage()`；`grep` 出来的其它成员全是 `private`。想记自己的数只能自己注册投影单元。
3. **以为 `contextPressure` 三个字段是一次原子观测。** 不是，它是三个不同时刻的 last-wins：`jsc` 注释明说「Switching models can therefore pair a fresh capacity with the previous route's pressure until the next request reports usage」（`projection.ts:26-38`）。
4. **以为 `contextBreakdown` 三项加起来是总量。** 不是，注释明确「they will not sum to the provider-anchored `projectedTokens`」（`projection.ts:54-60`）。
5. **以为 session-stats 能告诉你「失败几次」。** 不能 —— 见 5.4。
6. **以为 telemetry 会脱敏。** seam 不带任何规则（`session-telemetry/README.md:116`）。
7. **以为 `DSH_TELEMETRY_MODE` 能关掉上传。** 它能改 mode（`!!js process.env.DSH_TELEMETRY_MODE || 'FEEDBACK_ONLY'`），但真正的「关掉这一行」只有启动器 patch + `DSH_TELEMETRY_DISABLED`；注释原话「config cannot disable a row」（`cordis.patch.yml:174-176`）。
8. **以为 time-context 出厂就在。** 不在，唯一装配点是 Schedule overlay。
9. **拿 `steps` 当「成功步数」。** 它含 failed 与 cancelled（`session-stats/src/types.ts:25`）。
10. **在 `--dump-config` 里找 token-meter 的配置。** 它没有配置项；`--dump-config` 里只会看到那一行插件，没有 `config` 块。

### 5.4 与规划不符的发现（重要）

**规划写「失败几次」，但内置没有任何「失败计数」投影。**

- `SessionStatsProjection` 的八个字段里没有失败计数器（`packages/session/session-stats/src/types.ts:20-38`）；`grep -rn "failure|failed|errorCount" packages/session/session-stats/src/*.ts` 只命中注释里对 `step/end` 语义的描述，没有任何计数逻辑。
- 失败信号确实**存在**，但分散在三处、都要自己折：
  1. `tool/result` 的 `content[0].isError === true` —— telemetry 用它定 severity（`coordinator.ts:269-270`），但没人拿它做投影计数；
  2. `turn/end` 的 `reason.kind === 'error'`（同上 `:271-272`）；
  3. `llm/retry` 事件带着完整 `failure: LlmFailure`（`packages/llm/llm-retry/src/types.ts:19-42`），这是 provider 层重试的权威记录。
- 所以正文如果要给「失败几次」，**必须把它写成一个自定义投影单元的练习**，而不是引用内置字段。这恰好是 demo 的好素材（见 §7）。

### 5.5 `--dump-config` 与日志里能看到的表象

- `--dump-config` 能证实的东西：token-meter 那一行有没有挂（`cordis.patch.yml:317-318`）、telemetry 那行的 `mode` 与 `exporter.url` 是什么（`:184-196`）、`session-stats` 是否只在 web-app 层（`packages/bundle/web-app/cordis.patch.yml:86-87`）、time-context 那一行在不在（`apps/cli/config/examples/schedule/cordis.yml:4-7`）。既有 demo 的验证命令就是 `dsh --profile test --dump-config | grep -A3 'id: dsh-xxx'`（`code/dsh_plugin/dsh-note-search/install.sh`）。
- `--dump-config` **不能**证实的东西：`ctx.tokenMeter` 的读数、`sharing` 的实际取值（那要问服务）、time-context 到底注入了什么。
- 日志表象：`telemetry: capture step failed: …`、`telemetry: backend shutdown failed: …`（`coordinator.ts:133,247`）、`OpenTelemetry session upload is DISABLED; …`、`session telemetry ignored an event absent from the canonical session log`。
- **token-meter 没有 logger 调用**（在 `packages/llm/token-meter/src/index.ts` 里 grep 不到 `ctx.logger`）—— 它的失败方式是**抛异常给调用方**，不是打日志。这一点跟 compaction-basic（打 warn 继续）形成对照，值得在正文里比一句。

### 6.2 有没有「只有仓库内构建管线才走得通」的限制

逐条排查，**没有发现 14 篇 `ctx.remote` 那种硬限制**，但有三处要注意：

1. **`./src/*` 导出不能当契约用。** 所有包 `exports` 里都有 `"./src/*": "./src/*"`，但 `files` 只发布 `lib/*`。例如 `@deepseek-ai/dsh-session-telemetry` 的 `files` 是 `['lib/index.js','lib/types/**/*.d.ts']`、`@deepseek-ai/dsh-time-context` 是 `['lib/index.js','lib/invariant.js','lib/types/**/*.d.ts']`。**外部插件绝不能写 `@deepseek-ai/dsh-xxx/src/...`** —— 仓库内部到处这么写，是最容易被误抄的坑。
2. **声明合并要能解析到那个包的类型出口。** 三个 package 都有 `./types`（`dsh-session-projection`、`dsh-session-stats`、`dsh-compaction`）。token-meter 的用法是 `import type {} from '@deepseek-ai/dsh-session-projection'` + `declare module '@deepseek-ai/dsh-session-projection/types'`（`packages/llm/token-meter/src/projection.ts:65-72`）。这套在外部完全可复制。
3. **`peerDependencies` 里全是 `workspace:^`。** 这是仓库内写法；外部装包时解析到的是发布版。仓库里那批包的版本都写 `0.1.5-rc.2`（例如 `packages/llm/token-meter/package.json` 的 `version`），属于 **pre-stable / RC**，`AGENTS.md` 原文：「Public APIs are pre-stable; update every consumer」。**这是给读者的真实约束：内置服务名和类型可能在小版本之间变。**

### 6.3 一条给读者的提醒

`token-meter` 的 `package.json` 里有一条**跟其他包不一样**的 peer 依赖：`@deepseek-ai/dsh-compaction`。也就是说，**你只想要「读 token」这个能力，也会被牵进 `dsh-compaction` 的依赖**（因为 `compaction/prune` 的标价协议是双向的）。这不是外部插件专属的限制，但会让「我就读个数」的最小安装变大一圈 —— 值得在正文里如实提一句。

## demo 设计建议

### 7.1 选型理由

- 不重复 09 篇（订阅事件做统计）、11 篇（`defineTool` 基础）、15 篇（`/api` + slot）、16 篇（卡片）。
- 这篇的三个机制里，**最适合做成 demo 的是 token-meter + session-stats 的「读取方」**：读者只需要会 `ctx.sessionProjections.stateOf()`，就能一次拿到用量与时长；再叠一个 `deriveTurnTokenUsage` 补齐「本轮」的粒度。
- 关键取舍：**要「失败几次」就必须自己折**（见 5.4）。所以 demo 顺手注册一个 host-only 的失败计数单元 —— 一次同时示范「读内置单元」和「写自己的单元」，正好把 23 篇教的写方与 24 篇的读方接上。
- 不做客户端那一半（14/16 篇的地盘）：`sessionStats` / `tokenUsage` 已经是 wire key，客户端本来就能读；demo 只开一个工具，让模型也能读。

### 7.2 包结构与定位

### 7.3 核心代码骨架（约 80 行）

```ts
/**
 * 报一本「这一趟花了多少」的账：内置的用量/时长单元 + 自己折的失败计数。
 *
 * 读内置单元用 ctx.sessionProjections.stateOf()；
 * 失败次数内置没有，得自己注册一个 host-only 单元来折。
 */
import type { Context } from '@deepseek-ai/cordis'
import { z } from 'zod'
import type { SessionEvent } from '@deepseek-ai/dsh-session'
import type {} from '@deepseek-ai/dsh-session-projection/types'
import type {} from '@deepseek-ai/dsh-token-meter'
import type {} from '@deepseek-ai/dsh-session-stats'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'dsh-turn-cost'

/** sessionProjections 是必需依赖；没有投影注册表本插件不启动。 */
export const inject = ['tools', 'sessionProjections']

const failuresSchema = z.object({
    toolErrors: z.number().int().nonnegative(),
    turnErrors: z.number().int().nonnegative(),
    providerRetries: z.number().int().nonnegative(),
})

type FailuresState = z.infer<typeof failuresSchema>

declare module '@deepseek-ai/dsh-session-projection/types' {
    interface SessionProjectionStateMap {
        /** 本会话的失败次数。内置没有这个单元，所以自己折。 */
        failureCounts: FailuresState
    }
}

const zero: FailuresState = { toolErrors: 0, turnErrors: 0, providerRetries: 0 }

const failureCounts = {
    key: 'failureCounts' as const,
    stateVersion: 1,
    stateSchema: failuresSchema,
    init: (): FailuresState => zero,
    // 纯函数：不关心的事件必须返回同一个引用。
    apply: (state: FailuresState, event: SessionEvent): FailuresState => {
        if (event.type === 'tool/result' && event.data.message.content[0].isError === true) {
            return { ...state, toolErrors: state.toolErrors + 1 }
        }
        if (event.type === 'turn/end' && event.data.reason.kind === 'error') {
            return { ...state, turnErrors: state.turnErrors + 1 }
        }
        if (event.type === 'llm/retry') {
            return { ...state, providerRetries: state.providerRetries + 1 }
        }
        return state
    },
}

export function apply(ctx: Context): void {
    ctx.sessionProjections.register(failureCounts)

    ctx.tools.register(defineTool({
        name: 'turn_cost',
        description: 'Report this session\'s token usage, wall time, step counts, and failure counts.',
        parameters: {},
        output: {
            schema: { type: 'string' as const },
            render: (_args: unknown, value: string) => [{ type: 'text' as const, text: value }],
        },
        isConcurrencySafe: () => true,
        execute: (_args, exec) => {
            const session = exec.agent?.session
            if (session === undefined) return 'no agent-bound caller'
            const read = (key: 'tokenUsage' | 'sessionStats' | 'contextPressure' | 'failureCounts') =>
                ctx.sessionProjections.stateOf(session, key)
            return JSON.stringify({
                usage: read('tokenUsage'),
                time: read('sessionStats'),
                pressure: read('contextPressure'),
                failures: read('failureCounts') ?? zero,
            }, null, 2)
        },
    }))
}
```

> 依赖：`@deepseek-ai/cordis`、`@deepseek-ai/dsh-session`、`@deepseek-ai/dsh-session-projection`、`@deepseek-ai/dsh-token-meter`、`@deepseek-ai/dsh-session-stats`、`@deepseek-ai/dsh-tools`、`zod`、`@deepseek-ai/schemastery`。
> 那三行 `import type {} from '…'` 不是废行 —— 它们是把对应包的类型合并（key 声明）拉进本程序的开关，去掉就编译不过。这正是 `packages/llm/token-meter/src/index.ts:25-26` 里同一手法的原因（那里注释写的是「Type-only: activates the `ctx.sessionProjections` Context declaration」）。

### 7.4 装法与验证

```sh
# 装（沿用 08/09 篇的 test profile，脚本照 dsh-note-search/install.sh 的写法生成 patch.yaml）
bash code/dsh_plugin/dsh-turn-cost/install.sh

# 1) 装配对不对
dsh --profile test --dump-config | grep -A3 'id: dsh-turn-cost'

# 2) 跑一轮会失败的活：让模型读一个不存在的文件，再跑一个正常工具
dsh --profile test "读一下这个仓库里根本不存在的文件，然后告诉我当前目录有几个文件"

# 3) 让模型读账本
dsh --profile test "调 turn_cost，把结果原样贴给我"
```

预期第 3 步返回四块：`usage`（四个互斥桶）、`time`（`turns` / `steps` / `llmMs` / `toolMs` / `ttftMs` / `decodeMs` / `decodeTokens`）、`pressure`（`pressureTokens` / `projectedTokens` / `contextWindow`，模型没报 usage 时这几个字段可能缺失）、`failures`（至少 `toolErrors ≥ 1`）。

对照实验建议（正文里值得写）：把 `tokenUsage` 与 `sessionStats` 在**同一个会话**里连续读两次，中间不做任何事 —— 两次数字必须完全相同。这就是「可重放」的可观测证据；如果是计数器累加，重读反而会漂。

### 7.5 讲课时要点的三个「原来如此」

1. `stateOf()` 会**当场把该单元补算到会话当前游标**（懒建 cell），所以哪怕单元注册晚于事件发生，读到的也是对的。
2. `tokenUsage` 的四桶是**互斥**的：`reasoning` 已经含在 `outputTokens` 里，不会重复累加（`packages/llm/token-meter/src/projection.ts:6-10` 与 `index.ts:69-75` 的 `usageTokens` 都强调了这点）。
3. `sessionStats` 的 `steps` 数的是 `step/end`，**失败和取消的步也算**；想区分就得自己折（demo 里的 `failureCounts`）。
