## 1. 机制说明

### 1.1 hook 协议是什么，为什么存在

`packages/hooks/` 这个组的存在理由写得很直白（`packages/hooks/README.md:12`）：**让 agent 运行能复用为 Claude Code 或 Codex 写的 shell hooks**——把既有的 `hooks.json` 指过来，就能在会话开始、prompt 到达、工具执行、运行停止这些时刻跑你已有的命令。

它不是插件机制的替代品，而是一个**兼容适配器**。两个包的 README 用几乎同样的句子划边界：

- `packages/hooks/hook-protocol/README.md:32`：「Avoid the whole group for bespoke behavior with no reference-tool equivalent: **a native Cordis plugin has the full harness API with no hook protocol in between.**」
- `packages/hooks/hooks-claude-code/README.md:103`：「**A compatibility adapter, not a power tool.** The bridge exists to run the explicitly supported command-hook subset of an existing Claude Code config; bespoke behavior belongs in a native plugin on the same extension points.」

所以这个组有三个包，而且**你永远不会直接装中间那个**（`hook-protocol/README.md:12`、`:28`）：

| 包 | 角色 | 形状 |
| --- | --- | --- |
| `dsh-hook-protocol` | 两个桥共用的引擎：匹配、执行、解码、合并、事件、拆卸 | library，不直接配置 |
| `dsh-hooks-claude-code` | 跑你已有的 Claude Code `hooks.json` | plugin |
| `dsh-hooks-codex` | 跑你已有的 Codex `hooks.json` | plugin |

### 1.2 协议由哪些部分组成

`hook-protocol/src/` 九个文件，职责一一对应（`hook-protocol/README.md:82-92` 的 source map，加上实际源码）：

| 文件 | 职责 | 关键事实 |
| --- | --- | --- |
| `src/types.ts` | 方言中立的词汇与 `hook/*` 事件声明 | `HookDialect = 'claude-code' \| 'codex'`（`types.ts:48`）；`HookOutput` 的每个字段都可选（`:89`） |
| `src/matcher.ts` | 匹配：match-all 哨兵、字面量 vs 正则、校验与运行期匹配 | 缺省 / `''` / `'*'` 都是 match-all（`:14-16`）；CC 的纯词字符+`|` 模式按**字面量交替**，其它按正则（`:19`、`:58-61`）；Codex 永远是**非锚定正则** |
| `src/runner.ts` | 通过 `ctx.shell` 执行命令 | `DEFAULT_HOOK_TIMEOUT_MS = 600_000`（`:22`）；`timeoutSec * 1000` 覆盖默认（`:76`）；executor 拒斥 → 无 exitCode 的**非阻断**结果（`:98-105`） |
| `src/codec.ts` | exit code + stdout JSON + stderr → `HookOutput` | **exit 2 = block，stderr 作为 reason**（`:11`、`:66-69`）；结构化 stdout **只在 exit 0 时解析**（`:72`） |
| `src/merge.ts` | 多个命中 hook 折叠成一个「最严格」结果 | `deny > ask > allow`（`:19-20` 的 rank）；第一个 `continue:false` 是 sticky（`:32`）；context 按 hook 顺序累积 |
| `src/events.ts` | `hook/*` 事件的声明与追加帮手 | `DEFAULT_STDERR_SUMMARY_MAX_CHARS = 500`（`:52`）；`appendHookResult` 负责 invoked/result 配对规则 |
| `src/detached.ts` | emit 型 hook 运行的静止追踪 | 拆卸时先 abort signal 再 drain 所有被追踪的链（`:5-19`） |
| `src/invariant.ts` | 不变式伴生：配对、turn 包裹、方言、时长 | 逐条拒绝文案见 §5 |
| `src/index.ts` | 公开导出 | 25 行，导出上面的全部原语与事件帮手 |

**一条值得单独记住的工程选择**（`hook-protocol/README.md:74`、`:63`）：命令跑在 `dsh-shell` 的 executor 上，而不是自己 `spawn`。理由是 executor 已经提供「洗过但可覆盖的环境、进程组取消、超时」这三件事——协议不需要再实现一遍。**永不向循环抛异常**（`:75`）：畸形 JSON、非法正则、executor 拒斥，全都降级成「被容纳的结果」或「不匹配」，所以一个 hook 永远不能让当前 turn 崩掉。

### 1.3 一条 Claude Code hook 从配置到执行的完整轨迹

以 `PreToolUse` 为例，逐跳（行号都是 `packages/hooks/hooks-claude-code/src/index.ts`，下文简称 CC）：

1. **装载时读一次配置**（CC `:100-115`）：`JSON.parse(readFileSync(config.configPath, 'utf8'))`。读或解析失败就 `logger.warn(...)` 后 `return`——**一条 hook 都不注册，agent 照常启动**。
2. **解析成事件→matcher 组**（`hooks-claude-code/src/config.ts:78-122`）：只认 `CLAUDE_EVENTS` 里那 7 个事件（`config.ts:11-19`）；每个组里只有 `type === 'command'` 的 hook 会留下，其它类型进 `skipped`（`:98-101`）；命令字符串在**解析期**做 `${CLAUDE_PLUGIN_ROOT}` / `${CLAUDE_PROJECT_DIR}` 替换（`:104`、`:57-62`）；`UserPromptSubmit` 与 `Stop` 的 `matcher` 被丢弃，因为这两个事件没有匹配主体（`:109-111`）；有 matcher 的组如果正则非法，**抛 `SyntaxError`**，让桥在注册监听器之前拒掉整份配置（`:113`）。
3. **注册监听器**（CC `:205-296`）：`agent/session-start`（emit 型，detached）、`agent/pre-step`（waterfall → `PreStepDecision`）、`tools/pre-execute`（waterfall → `PreToolDecision`）、`tools/post-execute`（waterfall → `PostToolDecision`）、`agent/turn-stopping`（serial，可 `steer`）、`subagent/start`、`subagent/end`。
4. **构造 stdin 载荷**（CC `:337-339`）：`base + tool_name: exec.name + tool_input: exec.arguments + tool_use_id: exec.callId`。base 含 `session_id`、`transcript_path`、`cwd`、`hook_event_name`；**`transcript_path` 永远是空串**（CC README:91）——持久化 seam 不暴露产物路径，而且默认会话日志是 zstd 压缩的、脚本读不了。
5. **匹配 + 串行执行**（CC `:151-184`）：`matchesMatcher(group.matcher, matchQuery, 'claude-code')` 逐个组判；命中的 hook **按配置顺序串行**跑，这样一个 hook 的 `hook/invoked` / `hook/result` 在日志里相邻（CC README:95）。工作目录是 **agent 的 session workspace**（`opts.agent?.session.header.cwd`，`:146`），`CLAUDE_PROJECT_DIR` 显式配置优先、否则默认同一个目录（`:149-150`）。
6. **写日志对**（CC `:156-161`、`:180-182`）：在 turn 打开时先 `appendHookInvoked`，跑完再 `appendHookResult`；`handlerId` 形如 `claude-code:PreToolUse:<n>`（`:81-83`）。
7. **解码与折叠**（`hook-protocol/src/runner.ts:88-97` → `codec.ts:59-89` → `merge.ts:60-96`）：得到 `{ output, durationMs }`，逐 hook push 进 `outputs`，最后 `mergeHookOutputs(outputs)`。
8. **映射成类型化 Decision**（CC `:240-242`）：`deny → { kind: 'deny', reason }`、`ask → { kind: 'ask', reason? }`、否则 `next()` 委派。**context-only 的 hook 一定先 `next()` 再把自己的消息折进下游决定**（CC README:104），所以后面还有监听器的话仍然可以拒绝或改写。

### 1.4 两个桥各自能承接什么

`hooks-claude-code/src/config.ts:11-19` 的 `CLAUDE_EVENTS` 是 CC 桥的**权威事件集合**（7 个）；Codex 桥的五个与之对应。

| Claude Code 事件 | Codex 事件 | 运行时机 | 桥接后能做什么 | 依据 |
| --- | --- | --- | --- | --- |
| `SessionStart` | `SessionStart` | 会话开始 | 注入模型在该会话见到的上下文（**detached**，可能错过第一个请求） | CC README:58、:175；Codex README:56、:171 |
| `UserPromptSubmit` | `UserPromptSubmit` | agent 收到 prompt | 阻断 prompt，或附加上下文 | CC README:59；Codex README:57 |
| `PreToolUse` | `PreToolUse` | 工具执行前 | **CC**：阻断工具，或要求先审批；**Codex**：只能阻断（没有 `allow`/`ask`） | CC README:60；Codex README:58；`hooks-codex/README.md:83` |
| `PostToolUse` | `PostToolUse` | 工具执行后 | 带反馈阻断结果，或附加上下文 | CC README:61；Codex README:59 |
| `Stop` | `Stop` | 运行即将停止 | 带 reason 强制再走一步 | CC README:62；Codex README:60 |
| `SubagentStart` | — | 子 agent 开始 | 给**仍在运行的进程内子 agent** 注入上下文 | CC README:63、:179 |
| `SubagentStop` | — | 子 agent 结束 | 只观察，不能阻断、不能加上下文 | CC README:64、:179 |

**不支持的清单也是权威事实**（写在两个包的 Known Limitations 里）：

- CC：**不支持 23 个**（官方当前 30 个）——`Setup`、`InstructionsLoaded`、`UserPromptExpansion`、`MessageDisplay`、`PermissionRequest`、`PostToolUseFailure`、`PostToolBatch`、`PermissionDenied`、`Notification`、`TaskCreated`、`TaskCompleted`、`StopFailure`、`TeammateIdle`、`ConfigChange`、`CwdChanged`、`FileChanged`、`WorktreeCreate`、`WorktreeRemove`、`PreCompact`、`PostCompact`、`SessionEnd`、`Elicitation`、`ElicitationResult`（CC README:174）。这些事件的配置**在组解析之前就被忽略**，所以一个不支持的事件不会让整份配置失效。
- Codex：**不支持 5 个**——`PermissionRequest`、`PreCompact`、`PostCompact`、`SubagentStart`、`SubagentStop`（Codex README:170）；这些配置在解析期被静默丢弃。

**两类 hook 都不跑的**：`http`、`mcp_tool`、`prompt`、`agent` 处理器只解析不执行，并给一条 warn（`hook-protocol/README.md:12`、`:129`）。

### 1.5 「native hook」是什么，什么时候不需要协议

官方定义只有一句，在 `docs/cookbook/extension-cookbook.md:13`：

> A "native hook" is an ordinary Cordis plugin on an interception point; it needs no external protocol.

同一个 cookbook 的 `:11-33` 给了最小例子，返回值是一个**类型化 Decision**（`PreToolDecision`）：

```ts
export function apply(ctx: Context) {
  ctx.on('tools/pre-execute', async (exec, next): Promise<PreToolDecision> => {
    if (!(await isAllowed(exec))) {
      return { kind: 'deny', reason: 'Denied by policy.' }
    }
    return next()
  })
}
```

`docs/cookbook/extension-cookbook.md:106` 的「产品特性 → 插件机制」表把 hook 系统的落地位置写全了：监听 `agent/session-start`、`agent/pre-step`、`agent/request`、`tools/pre-execute`、`tools/post-execute`、`agent/turn-stopping`；**waterfall 返回类型化 Decision**；`agent/turn-stopping` 可以 `steer` 出另一步；两个桥只是把这些扩展点与 hook 配置文件对接起来。

**什么时候不需要协议**：当你没有历史钩子配置要保住时。桥能做到的事，native hook 都能做到且更多——`docs/cookbook/extension-cookbook.md:33` 列出选择规则：可重排的策略层用 `tools/pre-execute` waterfall；需要单调最终拒绝用 `ctx.tools.guard()`；需要包裹派发生命周期（超时/重试/计量）用 `tools/execute`；需要变换结果用 `tools/post-execute`；只观察最终不可变结果用 `tools/result`。

**两者最硬的一条分界**（`hook-protocol/src/types.ts:44-46`）：native hook 不是桥，**不写 `hook/invoked` / `hook/result` 这对记录**。也就是说：走桥你有审计日志，走 native hook 没有——需要日志就自己在 `session/event` 上折。

## 3. 可引用片段

**片段 1**（`packages/hooks/hook-protocol/README.md:32`，组的存在理由与退出条件）：

> Choose `dsh-hooks-claude-code` or `dsh-hooks-codex` when you have existing Claude Code or Codex hooks and want them to keep working during agent runs. You never choose this package directly. Avoid the whole group for bespoke behavior with no reference-tool equivalent: a native Cordis plugin has the full harness API with no hook protocol in between.

**片段 2**（`docs/cookbook/extension-cookbook.md:13`，native hook 的唯一官方定义）：

> A "native hook" is an ordinary Cordis plugin on an interception point; it needs no external protocol.

**片段 3**（`packages/hooks/hook-protocol/src/types.ts:44-46`，两类 hook 的日志分界）：

> The bridge that ran a hook — the CC bridge stamps `'claude-code'`, the Codex bridge `'codex'`. A native plugin at the interception points is not a bridge and writes no `hook/*` invocation/result records (see the interception extension-points Agent Note).

**片段 4**（`packages/hooks/hook-protocol/src/codec.ts:65-69`，exit code 契约，迁移时最需要记住的一条）：

> ```ts
> // Both dialects treat exit 2 as a block with stderr as its reason.
> if (exitCode === BLOCKING_EXIT_CODE) {
>   output.decision = 'block'
>   if (trimmedErr.length > 0) output.reason = trimmedErr
> }
> ```

说明：迁移的判据全在这一段——`exit 2` + stderr 是**唯一**的阻断通道；其它任何退出码都是非阻断失败。

**片段 5**（`packages/hooks/hook-protocol/README.md:63`，整条流水线的一段话总结）：

> The library is a chain of single-purpose steps, one function each: validate the matcher pattern, run the command through the `dsh-shell` executor, decode the outcome, merge every matched hook's outcome into one most-restrictive result, and record the durable `hook/*` event pair. … Every step degrades to a contained outcome instead of throwing, so a hook can never crash the calling turn.

**片段 6**（`packages/hooks/hooks-claude-code/README.md:175`，最容易踩的能力缺口，也是 native hook 的卖点）：

> - **`SessionStart` is partial** — JSON `additionalContext` is consumed, but plain stdout context, `initialUserMessage`, `sessionTitle`, `watchPaths`, `reloadSkills`, and `CLAUDE_ENV_FILE` are unsupported. The hook runs detached, so context can miss the first request …

**片段 7**（`packages/hooks/hooks-claude-code/README.md:181`，`transcript_path` 永远不可用的原因）：

> … `transcript_path` is never populated: it is always the empty string, because the persistence seam exposes no artifact paths and the default Zstandard-compressed session log is not readable by hook scripts.

说明：这条直接否掉了「迁过来继续读 transcript」这一类 hook，也解释了为什么 `hook/result` 只留 stderr 摘要。

**片段 8**（`packages/hooks/hooks-claude-code/README.md:70`，进程级配置，最容易误以为「每会话各一份」的地方）：

> One config applies to the whole process: it is read once at startup, and a relative `configPath` resolves from the directory that launched the process.

## 4. 实际流程

### 4.1 一条真实 hook 的完整轨迹：`PreToolUse` 拦截 bash

仓库里有一条**现成的**完整案例，逐层可查：

1. **场景目录**：`snapshots/session/hook-cc-pretool-deny/`——`snapshot.yml` 声明 `profile: headless`、`composition: default`、`recording: live`；`workspace/hooks.json` 就是要复用的那份 CC 配置。
2. **夹具**（`snapshots/session/hook-cc-pretool-deny/workspace/hooks.json`，逐字）：

   ```json
   {
     "hooks": {
       "PreToolUse": [
         {
           "matcher": "bash",
           "hooks": [
   ```

   注意三件事：`matcher: "bash"` 是**字面量**精确匹配（`matcher.ts:19`）；命令往 **stderr** 写；**`exit 2`**。
3. **装配**（`apps/cli/tests/profiles/acp/cordis.yml:82-90`，真实 patch 片段）：


4. **运行期**：装载时读 `./hooks.json`（CC `index.ts:103`）→ 解析出 `{ PreToolUse: [{ matcher: 'bash', hooks: [...] }] }`（`config.ts:78-122`）→ 注册 `tools/pre-execute` waterfall（CC `:237`）→ 模型调 `bash` 时 matcher 命中 → `runHook` 通过 `ctx.shell` 跑命令（`runner.ts:79-97`）→ exit 2 → `codec.ts:66-69` 得 `{ decision: 'block', reason: 'bash is disabled by policy in this session' }` → `mergeHookOutputs` 折成 `deny` → 桥返回 `{ kind: 'deny', reason }`（CC `:240`）→ 工具不执行。

6. **模型看到什么**：CC README:157 给的是逐字文案——拒绝的工具在 hook 没提供 reason 时变成 `Error: blocked by PreToolUse hook`；PostToolUse 的反馈**恰好**是 `blocked by PostToolUse hook`；阻断 Stop 加的 steering **恰好**是 `continue: blocked by Stop hook`；被阻断的 prompt 被丢弃、**没有任何模型可见消息**，turn 以 `blocked` 结束。

### 4.3 迁移一条 hook 的判据（把上面的机制收敛成可操作步骤）

1. 看你的事件在不在这 7 / 5 个里（`config.ts:11-19` + Codex README:170）。不在 → 要么改成 native hook 的扩展点监听，要么放弃。
2. 看你的 handler `type` 是不是 `command`（CC `config.ts:98-101`）。`http`/`prompt`/`agent`/`mcp_tool` → 只能重写成 native hook。
3. 看你的阻断方式是不是 `exit 2` + stderr / 结构化 stdout（`codec.ts`）。是 → 直接迁；靠 `updatedInput` 改写参数 → **迁不过去**（`hook-protocol/README.md:127`）。
4. 看你依赖 `transcript_path` 吗（CC README:181）。依赖 → 迁不了。
5. 看 `matcher` 是否是正则（CC 是字面量 vs 正则双模式，Codex 永远正则，`matcher.ts:19`、`:58-61`）。同一条 `Bash.*` 在两个方言里行为不同。
6. 最后决定走哪条路：**保住配置** → 挂桥（`cordis.patch.yml` 插一行，指 `configPath`）；**要更细的行为** → native hook。

### 5.2 常见误用

1. **以为桥在出厂装配里。** `packages/bundle/*/cordis.patch.yml` 与 `apps/cli/config/` 里**都没有** `dsh-hooks-*` 的挂载（我全仓 grep 过）；挂载只出现在 `apps/cli/tests/profiles/acp/cordis.yml:82-90` 与 `snapshots/session/text-turn/cordis.yml:73-80`、`snapshots/acp/escalation-approved/cordis.yml:83-90` 这些测试补丁里。要用就得自己插一行。
2. **以为 `configPath` 每会话一份。** 它**进程级、装载时读一次**，相对路径按**启动目录**解析（CC README:70；`index.ts:45-51` 的 TODO 就是在记这笔账）。多个项目共用进程时这是坑。
3. **以为 `matcher` 是正则。** CC 侧纯词字符模式是**字面量**：`Bash` 匹配 `Bash` 但不匹配 `BashTool`；`Bash|Read` 是精确交替（`matcher.ts:58-61`，`matcher.spec.ts:15-27`）。Codex 侧永远是**非锚定正则**，同一个词模式会变成子串匹配（`matcher.ts:19`）。
4. **用 `updatedInput` 改写参数。** 解析、记日志、发 warn，**然后忽略**（`hook-protocol/README.md:127`）；`PreToolDecision` 根本不能改写参数，权威理由在 `2026-06-30-interception-extension-points.md:46`：history 与 audit 在派发前就记了，改写必须同时更新它们。
5. **指望 `continue: false` 停掉整个运行。** 会被折成 sticky `stop`，但**拦截点没有 hard-halt 原语**，桥只把它记进 `hook/result`（`hook-protocol/README.md:128`；CC `index.ts:188` 的 TODO）。
6. **写一个无条件阻断的 `Stop` hook。** 它会让每一步都被强制续跑——连续阻断上限**没有实现**（CC README:180、Codex README:175）。
7. **依赖 `transcript_path`。** 永远是 `''`（CC）/ `null`（Codex），因为持久化 seam 不暴露产物路径、默认日志是 zstd（CC README:181、Codex README:176）。
8. **指望多个 hook 并行或去重。** 命中后**串行**跑、**不去重**，而参考工具是并行+去重（CC README:182）——这是刻意的取舍，为了日志里 invoked/result 相邻（CC README:107）。
9. **以为 native hook 也会出现在 `hook/*` 日志里。** 不会（`types.ts:44-46`）。
10. **用 Codex 的 `PreToolUse` 提审批。** Codex 桥没有 `ask`（Codex README:83、`:58`）。

**核心代码骨架**（`src/index.ts`，约 100 行；4 空格缩进 / 单引号 / 无分号 / 中文 JSDoc）：

```ts
/**
 * native hook 演示：普通的 Cordis 插件，直接订阅扩展点，不经过任何外部协议。
 * 两个动作与桥接的 Claude Code hook 一一对照：
 *  1) tools/pre-execute 阻断危险 bash；
 *  2) agent/session-start 同步注入本会话的策略说明。
 *
 * @module dsh-native-hook
 */
import type { Context } from '@deepseek-ai/cordis'
import { createUserMessage } from '@deepseek-ai/dsh-llm'
import type { PreToolDecision, ToolExecution } from '@deepseek-ai/dsh-tools'

export const name = 'dsh-native-hook'

/** 可配置项。 */
export interface Config {
    /** 命中即拒绝的命令正则源（字符串数组，避免把 RegExp 写进配置）。 */
    blockedCommands: string[]
    /** 拒绝时给模型看的原因。 */
    denyReason: string
    /** 会话开始时注入的说明；空字符串表示不注入。 */
    sessionNote: string
}

/**
 * 从工具调用里取 bash 的命令行。
 *
 * @param exec - 本次工具调用。
 * @returns 命令行；不是 bash 或没有 command 参数时返回 undefined。
 */
function bashCommandOf(exec: ToolExecution): string | undefined {
    if (exec.name !== 'bash') return undefined
    const args = exec.arguments as { command?: unknown } | undefined
    return typeof args?.command === 'string' ? args.command : undefined
}

/**
 * @param ctx - 插件上下文。
 * @param config - 已校验的配置。
 */
export function apply(ctx: Context, config: Config): void {
    const patterns = config.blockedCommands.map(source => new RegExp(source))

    // 1) 危险命令：waterfall 返回类型化 Decision。native hook 不写 hook/* 记录。
    ctx.on('tools/pre-execute', (exec, next): PreToolDecision => {
        const command = bashCommandOf(exec)
        if (command === undefined) return next()
        if (!patterns.some(pattern => pattern.test(command))) return next()
        return { kind: 'deny', reason: config.denyReason }
    })

    // 2) 会话开始：同步注入，所以第一个请求就带着它。
    //    桥的 SessionStart 是 detached 的，可能错过第一个请求（见 README 限制）。
    ctx.on('agent/session-start', ({ agent }) => {
        if (config.sessionNote === '') return
        agent.inject(createUserMessage({
            content: [{ type: 'text', text: config.sessionNote }],
            source: { kind: 'plugin', plugin: name },
        }))
    })

    console.log(`[${name}] 已装：${patterns.length} 条阻断模式；sessionNote=${config.sessionNote === '' ? '无' : '有'}`)
}
```

**A/B 差异表（demo 的落点，正文照抄）**：

| 维度 | native hook（`dsh-native-hook`） | 桥接的 CC hook |
| --- | --- | --- |
| 载体 | TypeScript 插件，`ctx.on(...)` | JSON 配置 + `dsh-hooks-claude-code` |
| 阻断方式 | 返回 `{ kind: 'deny', reason }` | 进程 `exit 2` + stderr |

**为什么这个 demo 讲得清**：

- 它用一个**可切换的两行 patch** 把「协议」和「native」并排跑，读者不需要相信任何断言。
- 它把「我不需要协议」这句话变成可见的取舍：桥给你审计日志和 JSON 配置复用，native hook 给你类型化 Decision 和同步注入。
- 它踩在读者已经会的东西上（`ctx.on` waterfall、Config schema、`agent.inject`），新知识只有两条：扩展点在哪、`hook/*` 谁写。
- **未验证**：`agent.inject` 在 `agent/session-start` 里同步调用的确切效果（桥在 `hooks-claude-code/src/index.ts:205-213` 里是 detached 调的，native 侧同步调用是否在第一个请求前生效没有源码断言）——这一条必须由会跑 dsh 的人实测确认。

### 8.3 值得写进正文的反直觉点

1. **hook 协议是「兼容适配器」，不是插件机制的升级版。** 两个包的 README 都主动写着「bespoke behavior belongs in a native plugin」（`hook-protocol/README.md:32`、`hooks-claude-code/README.md:103`）——官方在劝你别用它。
2. **桥不在任何出厂装配里。** 我 grep 过 `packages/bundle/*` 与 `apps/cli/config/`：没有 `dsh-hooks-*` 的挂载；它们只出现在测试补丁与快照 `cordis.yml` 里。要用得自己插一行。
3. **CC 桥只承接 7 / 30 个事件，Codex 桥只承接 5 / 10 个。** 「不想重写」的代价被逐条写在 Known Limitations 里，而不是含糊的「部分支持」。
4. **`transcript_path` 永远是空的。** 持久化 seam 不暴露产物路径，默认日志又是 zstd —— 依赖 transcript 的 hook 从根上迁不过来（CC README:181）。
5. **native hook 不写 `hook/*` 日志。** 走桥白得一对审计记录，走 native hook 白得完全的自由——两个方向的取舍写在 `hook-protocol/src/types.ts:44-46`。
