# 第 18 篇素材包：发给同事安装

对象：DSH 的两种 manifest（bundle 的 `dsh.bundle`、profile 的 `dsh.profile`）、层加载顺序、表层组合包自带命令行、从 GitHub 安装时的构建脚本坑。
仓库：`local/deepseek-harness/`。下面所有 `路径:行号` 都相对该仓库根。

## 机制说明

本篇要讲清 DSH 的**分发层**：一条 `dsh plugin --profile x add <包>` 为什么能让别人装上你写的东西。

要在 01/02 篇的基础上往前推一步。前 16 篇里读者已经用过 `dsh.bundle.patch`（02 篇「bundle 声明」一节），但那时它是「让 `dsh plugin add` 认我这个包」的开关。本篇要讲的是：**同一个 `package.json` 里的 `dsh` 键可以回答两个不同的问题，而大多数人的困惑来自于把这两个问题混成一个。**

两个问题、两种 manifest，都在 `package.json` 的 `dsh` 键下，但键名不同（`packages/util/package-manifest/src/types.ts:29-36`）：

- **组合包（bundle）** 回答「我贡献什么配置」——`dsh.bundle.patch` 指向一个 patch 文件。它是**你写、你发布**的东西。
- **profile** 回答「这套组合由哪些组合包按什么顺序拼成」——`dsh.profile.bundles` 是一个有序名单，`dsh.profile.patchReload` 决定用户 patch 文件是热重载还是一次性加载。它是**用户机器上、按名字启动**的东西。

这两种角色由**位置**决定，不由包的性质决定：bundle 是任意一个 npm 包；profile 永远是 `$DSH_HOME/profiles/<name>` 下的一个目录（`packages/boot/app-boot/src/profile.ts:41-45`、`95-102`）。文档里那句话可以直接引用：「组合包是你编写并分发的东西；profile 是用户用 `dsh --profile <name>` 启动的东西。没有东西同时是两者。」（`docs/user/develop/basic/publish.zh.md`）

挂到读者已有的心智模型：

- **`dsh.bundle` ≈ npm 的 `bin`。** 两者都是「包在 `package.json` 里声明一个扩展点，由外部工具消费」。`bin` 让包贡献一条命令，`dsh.bundle` 让包贡献一层配置。区别在于 `bin` 由 npm 写进 `.bin/` 符号链接目录，而 `dsh.bundle` 由 `dsh` 的启动器在**每次启动时**解析并叠加——没有任何东西被写进 profile，只有包名进 `dsh.profile.bundles` 名单（`apps/cli/src/plugin.ts:47-91`）。
- **`dsh.profile` ≈ `docker-compose.yml` 的 `services` 列表，或者 tsconfig 的 `references`。** 它不是配置本身，而是「按顺序应用哪些层的清单」。真正的内容全在被引用的每个 bundle 的 patch 文件里。
- **「n 个 patch 叠在一棵空树上」≈ CSS 层叠，或者 options 的浅合并。** 后应用的层按行（row）胜出，且**一行的 `config` 是整体替换，不是深合并**。这条对作者有直接后果：你的 patch 覆盖前一层某行时，必须把要保留的键全部重述一遍（`packages/bundle/base/cordis.patch.yml:6-10` 的注释、`packages/bundle/web-app/cordis.patch.yml:3-5`）。

加载顺序是这一段的主线。生效配置在**一棵空树**之上按 6 步拼出来（`apps/cli/reference/README.md:7`、`apps/cli/src/profile-boot.ts:206-213`）：

1. profile 的 `dsh.profile.bundles` 里每个组合包的 patch，按名单顺序；
2. profile 自己的 `cordis.patch.yml`；
3. home 级的 `$DSH_HOME/cordis.patch.yml`（机器本地偏好，所以它**压过** per-profile 层）；
4. 每个 `--patch <path>` overlay，按 argv 顺序；
5. `DSH_TELEMETRY_DISABLED` 派生的关停 patch（`apps/cli/src/profile-boot.ts:167-170`、`241-242`）。

工具调用参数（`--port` 之类）**不是一层 patch**——表层组合包用自己的应用自有服务把它们解析出来（见「可引用代码片段」第 3 段）。

解析的双锚点规则也必须讲清：`dsh.profile.bundles` 里的名字**先从 dsh 安装目录解析，再从 profile 目录解析**（`packages/boot/app-boot/src/profile.ts:746-757`）。所以 `@deepseek-ai/dsh-base` 永远来自与运行中的 `dsh` 同一个安装，pnpm 从不管理它——这正是「你可以放心依赖 base 存在」的机制性理由（`packages/bundle/README.md` 末段）。而 patch 行里的**裸插件名**走 profile 目录的 Node 父目录逐级查找，落到启动器维护的扁平回退目录 `$DSH_HOME/profiles/node_modules`（`packages/boot/app-boot/src/profile.ts:16-22` 的模块注释、`547-560`）。

「表层组合包自带命令行」这一节的机制：启动器把**自己 flag 之后的同一份不可变参数快照**放进 `ctx.cmdlineArgs`，任何插件都能注入它、用 `@deepseek-ai/dsh-cmdline` 的 `parseCmdline` 解析自己的 flag 家族。所以加应用专属 flag 不需要改启动器，也不需要新的行类型（`packages/bundle/web-app/cordis.patch.yml:126-131`、`packages/bundle/web-app/src/startup.ts:12-14`、`packages/boot/cmdline/src/index.ts:84-88`）。

「从 GitHub 装」这一节的机制：git 安装拉的是**源码**，pnpm 只跑 `prepare`，不跑 `build`。这条路在代码里有明确的三处证据：`apps/cli/src/plugin.ts:150-161` 在 pnpm 非零退出且参数像 git spec 时专门打印一段修复指引；`packages/boot/app-boot/src/profile.ts:150-155` 给 profile 写死一份 `pnpm-workspace.yaml`（`nodeLinker: hoisted`、`autoInstallPeers: false`），并在注释里说明「pnpm ≥10 从 pnpm-workspace.yaml 读设置，不读 .npmrc」——这是 `allowBuilds` 该写在哪的答案。

export function initProfile(
  dir: string,
  bundles: readonly string[],
  patchReload: ProfilePatchReload = DEFAULT_PROFILE_PATCH_RELOAD,
): void {
  mkdirSync(dir, { recursive: true })
  const manifestPath = join(dir, 'package.json')
  if (!existsSync(manifestPath)) {
    const manifest: ProfileManifest & { private: boolean } = {
      name: `dsh-profile-${basename(dir)}`,
      private: true,
      dependencies: {},
      dsh: { profile: { bundles: [...bundles], patchReload } },
    }
    writeFileSync(manifestPath, JSON.stringify(manifest, undefined, 2) + '\n')
  }
  const patchPath = join(dir, PROFILE_PATCH_FILENAME)
  if (!existsSync(patchPath)) writeFileSync(patchPath, PROFILE_PATCH_TEMPLATE)

### 5. `dsh plugin add` 的调和逻辑（按已安装状态，不是依赖 diff）

`apps/cli/src/plugin.ts:59-91` 的核心 30 行：

```ts
function reconcilePlugins(before: ProfileManifest, profileDir: string): void {
  const after = readProfileManifest(NAME, profileDir)
  const beforeDeps = new Set(Object.keys(before.dependencies ?? {}))
  const dependencies = Object.keys(after.dependencies ?? {})
  const plugins = after.dsh?.profile?.bundles ?? []
  let changed = false
  for (const packageName of dependencies) {
    const isBundle = exportsPatch(packageName, profileDir)
    if (isBundle && !plugins.includes(packageName)) {
      plugins.push(packageName)
      changed = true
    } else if (!isBundle && !beforeDeps.has(packageName)) {
      process.stderr.write(
        `${NAME}: warning: ${packageName} declares no dsh.bundle — installed as a plain dependency, not a profile layer `
        + '(a later update that gains one activates it automatically)\n',
      )
    }
  }
  // ...省略：依赖被删掉或新版本不再声明 dsh.bundle 时，从 bundles 里摘掉
  if (!changed) return
  after.dsh = { ...after.dsh, profile: { ...after.dsh?.profile, bundles: plugins } }
  writeProfileManifest(profileDir, after)
}
```

## 内置消费者

- **六个内置组合包全在 `packages/bundle/`**：`base`、`web-app`、`headless`、`acp-app`、`sdk-app`、`sdk-minimal`。每个 `package.json` 都有 `dsh.bundle.patch`，每个都带一份 `cordis.patch.yml`。`base` 的 patch 有 487 行，`web-app` 有 484 行——它们本身就是「一个 patch 能写多大」的样本（`packages/bundle/base/cordis.patch.yml`、`packages/bundle/web-app/cordis.patch.yml`）。
- **`base` 明确只放「各模式共享」的行**，模式专属的行留给各模式组合包，理由写在文件头注释里：patch 整体替换 config，所以一行只应由「一个组合包层 + 用户层」持有（`packages/bundle/base/cordis.patch.yml:6-13`）。
- **`web-app` 覆盖 `base` 的行**是「同 id 重述 config」的现成例子：`packages/bundle/web-app/cordis.patch.yml:17-25` 重述 `system-prompt` 的 persona，`27-35` 重述 `session-query-sqlite`。文件头第 3-5 行说明为什么必须重述每个键。
- **表层组合包持有自己命令行**的消费者是 `web-app`（`web-startup` + `webserver`）、`headless`（`dsh-headless` 的 `headless-runner` 行）、`acp-app`、`sdk-app`——后三个都导出 `xxxAppStartup` 服务名并由协议行等待（`packages/bundle/acp-app/src/index.ts:14-20`、`packages/bundle/sdk-app/src/index.ts:14-20`、`packages/bundle/headless/src/index.ts:26-28`）。
- **`--from-default-profile` 也是 profile manifest 的消费者**：`apps/cli/src/profile-boot.ts:104-154`，从模板复制 `bundles` 与 `patchReload`，不读同名本地 profile、不记继承关系。
- **`scripts/verify-cordis-config.ts`** 在仓库内强制一件事：裸 plugin 名必须出现在其解析清单的 `dependencies` 里（`scripts/verify-cordis-config.ts:1-9` 的模块注释；根 `AGENTS.md` 的 Conventions 也有这条）。这是「外部插件作者不用管、但一旦你在仓库内写 patch 就绕不过」的约束。

| `dsh: installed package X must declare a non-empty version` / `main entry is missing at ...` | 只在**打包成单文件可执行体**（`process.pkg`）时才走的分支：ESM proxy 需要版本号与可解析的入口 | `packages/boot/app-boot/src/profile.ts:359-361`、`369-375`；测试 `tests/profile.spec.ts:856-870` |

其他要写成「注意事项」的坑：

1. **patch 不深合并。** 覆盖某行的 `config` 会丢掉你没写的键。作者侧后果：给用户留的默认值要写全（`packages/bundle/base/cordis.patch.yml:6-10`）。
2. **`--dump-config` 不跑应用命令行。** 它连 runtime module fallback 都不准备，且**接受应用参数会直接报错**：`error: config dumps take no app arguments, got ...`（`apps/cli/src/args.ts:100-104`、`apps/cli/reference/README.md:51`）。所以「先 dump 验层、再启动验 flag」是两步，不能一步。
3. **`--dump-config` 与 `--dump-default-config` 互斥**，且后者不接受 `--patch`（`apps/cli/src/args.ts:98-108`）。
4. **空或全是注释的 patch 文件会导致启动失败**，要禁用就用 `[]`（`packages/boot/app-boot/README.md:55`）——而 `initProfile` 生成的模板正好就是 `[]`。
5. **profile 目录里的 `cordis.yml` 是空根，不要编辑它。** 每次启动都被重写覆盖，因为 Loader 的自持写回会把组合结果烤进这个文件，下一次启动就会把每个 bundle 的 insert 重复一遍（`apps/cli/src/profile-boot.ts:84-88`、`172-180`）。
6. **patch 对象每代都要重新 clone。** include 是按引用把 `insert` 行推进挂载中的树的，后到的 id 定向 patch 会原地改这些对象；复用同一份解析结果会让「用户覆盖」烤进 bundle 的 insert 行，撤掉覆盖也回不到默认值（`apps/cli/src/profile-boot.ts:323-335` 的注释）。这一条适合作为「为什么每次热重载都要重新读盘」的答案。
7. **相对路径 spec 的锚定只覆盖裸相对路径与 `file:`/`link:` 前缀**。`dsh plugin --profile demo add .` 从插件 checkout 里跑会装那个 checkout，不会自链接 profile（`apps/cli/src/plugin.ts:93-112`）；但 `github:you/repo` 这种 spec 原样透传。
8. **`web` 是硬编码别名**，等价于 `--profile web`（`apps/cli/src/args.ts:12-13`）。`desktop` profile 被显式拒绝：`error: profile "desktop" is managed exclusively by the Electron application`（`apps/cli/src/args.ts:64-68`）。

## 外部插件可行性

**结论：完全可行，而且这是官方推荐路径。** `dsh.bundle` / `dsh.profile` 两个 manifest 字段本身就是给树外包用的；仓库外插件不需要任何仓库内构建管线。

分三件事给证据。

**（一）发布路径只需要 npm。** `docs/user/develop/basic/publish.zh.md` 给了两句话可以直接引用：
- 「组合包是你编写并分发的东西；profile 是用户用 `dsh --profile <name>` 启动的东西。没有东西同时是两者。」
- 「如果不想让用户做这项授权，就改为分发构建产物——发布到 npm，在 `pnpm publish` 时构建好 `lib/`；`dsh plugin add your-package` 安装的就是预构建代码。」

组合包的 manifest 字段就是普通的 `package.json`，`dsh` 键是自定义字段，npm 不校验也不剥离——六个内置组合包都是以 npm 包发布（`publishConfig.access: "public"`，`packages/bundle/base/package.json:7-9`）。

**（二）一个仓库外插件需要哪些依赖。** 从仓库现有 demo 的真实 `package.json` 可以读出最小集合：

- 只用 `apply` 注册运行时行为（不用框架类型）：`@deepseek-ai/cordis`（peer），够了。`../code/dsh_plugin/dsh-hello-world/package.json` 只有 `{ "@deepseek-ai/cordis": "^4.0.1" }`。
- 用 `Config` + schema：再加 `@deepseek-ai/schemastery`。`../code/dsh_plugin/dsh-note-search/package.json` 是 `{ cordis, dsh-tools, schemastery }`，并声明 `dsh.bundle.patch: "./patch.yaml"`。
- 用 `defineTool` / `ctx.tools`：加 `@deepseek-ai/dsh-tools`。
- 用到宿主服务（如 web 路由）：加对应包，例如 demo 里的 `@deepseek-ai/dsh-host-webserver`（`../code/dsh_plugin/dsh-chat-background/package.json`）。

这些包的公开版本可以从 npm 装上（已核对 npm registry 的 `dist-tags`）：

| 包 | `latest` | `next` | `alpha` |
| --- | --- | --- | --- |
| `@deepseek-ai/dsh-base` | `0.0.1-rc.1` | `0.2.0-rc.2` | `0.2.1-alpha.2` |
| `@deepseek-ai/dsh-app-boot` | `0.1.0-rc.6` | `0.2.0-rc.2` | `0.2.1-alpha.2` |
| `@deepseek-ai/dsh-tools` | `0.0.1-rc.1` | `0.2.0-rc.2` | `0.2.1-alpha.2` |

（本仓库版本是 `0.1.5-rc.2`，`package.json` 根 `version`。可见 `latest` 落后仓库很远——写文章时如果要给「装上某个固定版本」的命令，用 `next` 或显式版本号，别用 `latest`。）

**（三）关键限制：一层「只有仓库内走得通」的东西，集中在三处。**

1. **`engines.dsh` 不被执行。** `packages/util/package-manifest/README.md:91` 明说：「当前安装器与加载器都不强制 `dsh.manifestVersion` 或 `engines.dsh`；声明一个范围不会拒收不兼容的宿主，也不校验 SemVer 语法。」所以声明 `engines.dsh` 是写给人看的，不是安全网——版本兼容要靠自己对齐。
2. **裸 patch 名靠启动器维护的扁平回退目录解析**，这是仓库内插件的 peer 依赖能跑起来的原因（14 篇遇到的 `ctx.remote` 类限制同源）：`packages/boot/app-boot/src/profile.ts:16-22` 说明 `$DSH_HOME/profiles/node_modules` 镜像安装目录的**依赖闭包**，并且**peerDependencies 也参与遍历**——注释给的理由正是「服务定义包（dsh-subprocess、dsh-compaction……）是实现包的 peer，从来不是普通依赖，但树外插件要直接 import 它们」（`packages/boot/app-boot/src/profile.ts:476-479`）。所以外部插件**不需要**把 `@deepseek-ai/dsh-agent` 这类 peer 打进自己包里，装上也解析得到；但反过来说，这些包的状态由 dsh 安装决定，你无法在 profile 里换掉它。
3. **单文件可执行体（packaged executable）不能用符号链接**，必须走 ESM proxy 分支（`packages/boot/app-boot/src/profile.ts:314-317`、`396-401`、`491-498`）。这一支要求每个包 `exports` 是静态可解析的、`version` 非空、入口文件真实存在；`exports` 里的通配、无 `exports` 时的 `main` 回退各有一套规则（`packages/boot/app-boot/src/profile.ts:346-394`）。对纯 npm 发布形态的插件来说这条不构成限制，但它解释了「为什么桌面包里插件加载路径和 CLI 里不一样」。

**另一个必须说清的边界：`@deepseek-ai/dsh-base` 之类的内置组合包不从 npm 装。** 它们的名字在 profile 名单里，但解析**先从运行中的 dsh 安装**开始（`packages/boot/app-boot/src/profile.ts:734-745` 的 JSDoc：「安装优先顺序就是 @deepseek-ai/dsh-base 永远来自与运行中 dsh 相同的安装，绝不来自 profile 本地副本」）。所以别在 profile 的 `dependencies` 里写 `@deepseek-ai/dsh-base`——写了也不会生效，只会让 pnpm 多装一份没人用的。

**未确认**：仓库里没有关于「发布到 npm 的 `package.json` 是否会被某道 gate 剥离自定义 `dsh` 字段」的说明；从已发布的 `@deepseek-ai/dsh-base@0.2.0-rc.2` 的 registry manifest 里能读到 `"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}`，说明字段会原样发布。

## demo 设计建议

建议**在 02 篇的 `dsh-hello-world` 基础上加一个「自带命令行 + 可发布」的包**，而不是新写一个功能。这样 18 篇的增量正好是「分发」，不是「再学一个 API」。

包名：`dsh-greeter`。它演示三件本篇独有的事：一个 line 完整的组合包、一个应用自有服务（自带 flag）、以及 `publishConfig`。

目录结构（沿用专栏既有风格：`src/*.ts` + `patch.yaml` + `install.sh`）：

```
dsh-greeter/
├── package.json          # dsh.bundle.patch + dsh.bundle 之外的发布字段
├── patch.yaml            # 两条 insert：提供方行、消费方行
├── src/
│   ├── dsh-greeter.ts    # 提供方：inject cmdlineArgs，provide greeterStartup
│   └── dsh-greeter-echo.ts # 消费方：inject greeterStartup，读 !!js 配置
├── tsconfig.json
└── install.sh
```

`package.json`：

```json
{
  "name": "dsh-greeter",
  "version": "0.1.0",
  "type": "module",
  "private": true,
  "publishConfig": { "access": "public" },
  "dsh": { "bundle": { "patch": "./patch.yaml" } },
  "engines": { "dsh": ">=0.1.5" },
  "dependencies": {
    "@deepseek-ai/cordis": "^4.0.1",
    "@deepseek-ai/dsh-cmdline": "^0.1.0",
    "commander": "^15.0.0"
  }
}
```

`patch.yaml`（`!!js` 是本篇唯一的 YAML 新东西）：

```yaml
# dsh-greeter 的 bundle 补丁：提供方行 + 消费方行。
- insert:
    - id: greeter-startup
      name: 'dsh-greeter/startup'
    - id: greeter-echo
      name: 'dsh-greeter/echo'
      inject: [greeterStartup]
      config:
        greeting: !!js ctx.greeterStartup.greeting ?? 'hello'
```

`src/dsh-greeter.ts`（提供方 30 行，是 `web-startup` 的最小化版本）：

```ts
/**
 * dsh-greeter 的命令行提供方：解析自己的 flag，把结果发布成普通服务。
 * @module dsh-greeter
 */
import { Command } from 'commander'
import type { Context } from '@deepseek-ai/cordis'
import { parseCmdline } from '@deepseek-ai/dsh-cmdline'

export const name = 'greeter-startup'

/** 启动器在挂载任何条目之前就把参数快照放进来了。 */
export const inject = ['cmdlineArgs']

/** 本应用自有服务的名字；被 flag 配置的行注入它。 */
export const GREETER_STARTUP_SERVICE = 'greeterStartup'

/** 解析成功的取值。 */
export interface GreeterStartupValues {
    /** `--greeting`，给消费方行当默认值的后备。 */
    greeting?: string
}

/**
 * 建立本应用的命令，解析后把取值提供出去。
 * @param ctx - 带 cmdlineArgs 与 appExit 的插件上下文。
 */
export function apply(ctx: Context): void {
    const program = new Command()
        .name('dsh --profile greeter')
        .description('Say hello.')
        .option('--greeting <text>', 'greeting text')
    parseCmdline(ctx, program)
    // parseCmdline 在成功解析后才会跑到这里；--help 时它不返回。
    ctx.provide(GREETER_STARTUP_SERVICE, program.opts() as GreeterStartupValues)
}
```

`src/dsh-greeter-echo.ts`（消费方 15 行，证明 `!!js` 真的读到了服务）：

```ts
/**
 * dsh-greeter 的消费方：打印注入服务解析出来的问候语。
 * @module dsh-greeter/echo
 */
import type { Context } from '@deepseek-ai/cordis'

export const name = 'greeter-echo'

/** 等提供方发布后才激活。 */
export const inject = ['greeterStartup']

/** 由 patch 的 `!!js` 表达式求值后传进来。 */
export interface Config {
    greeting: string
}

/**
 * 打印问候语。
 * @param ctx - 已注入 greeterStartup 的上下文。
 * @param config - patch 里 `!!js ctx.greeterStartup.greeting ?? 'hello'` 的结果。
 */
export function apply(ctx: Context, config: Config): void {
    ctx.logger(name).info('%s', config.greeting)
}
```

**两处要先在文章里交代清楚的接线**（否则 demo 跑不起来，而这两点本篇正好要讲）：
- patch 行里的 `name` 是**包名 + 子路径**（`dsh-greeter/startup`），所以 `package.json` 的 `exports` 必须有 `"./startup"` 与 `"./echo"`，或者让入口名就是包名本身。**未确认**：`loadOverlayPatches` 是否支持把裸包名当插件名直接 import——`packages/boot/app-boot/README.md:57` 只说「插入的插件名可以是绝对路径、file URL 或包 specifier」，包 specifier 的解析由 Loader 负责。
- `Config` 在消费方是**必填字段**（`greeting: string` 没有 `?`），因为 patch 里已经给了 `!!js` 后备值；如果让 Config 自己带默认值，就变成两个默认值来源（06 篇的教训）。

`install.sh`（沿用 `dsh-note-search` 的做法，把 patch 里的绝对路径按本机位置重新生成）：

```bash
#!/usr/bin/env bash
set -euo pipefail

DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

cd "$DIR"
pnpm install

# patch.yaml 里的插件行要写绝对路径，按本机位置重新生成。
cat > patch.yaml <<EOF
- insert:
    - id: greeter-startup
      name: '$DIR/src/dsh-greeter.ts'
    - id: greeter-echo
      name: '$DIR/src/dsh-greeter-echo.ts'
      inject: [greeterStartup]
      config:
        greeting: !!js ctx.greeterStartup.greeting ?? 'hello'
EOF

dsh plugin --profile greeter-demo add "link:$DIR"

echo "验层：dsh --profile greeter-demo --dump-config | grep -A2 greeter"
echo "验 flag：dsh --profile greeter-demo --greeting 你好"
```

验证命令（三段，正好对应本篇三个知识点）：

```sh
# 1. 层进来了（此刻不跑应用命令行，所以不加 --greeting）
dsh --profile greeter-demo --dump-config | grep -A3 'id: greeter-startup'
# 2. 不带 flag 时走 !!js 后备值 'hello'
dsh --profile greeter-demo
# 3. 带 flag 时覆盖后备值
dsh --profile greeter-demo --greeting 你好
# 4. 只打印 bundle 层（证明 base 与 greeter 都在名单里）
dsh --profile greeter-demo --dump-default-config
```

**「发给同事」那一段的收尾建议**：把 demo 真的推到 GitHub，让读者跑一次 `dsh plugin --profile greeter-demo add github:<you>/dsh-greeter`，看它因为缺 `prepare` 而失败，再把 `prepare` 加上、把 pnpm 打印的键写进 profile 的 `pnpm-workspace.yaml` 的 `allowBuilds`。这比在文章里描述这道坎有说服力得多。
