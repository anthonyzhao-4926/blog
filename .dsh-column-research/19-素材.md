# 第 19 篇素材包：让 agent 自己加功能

对象：运行中的 Cordis——检查插件树、挂载与卸载内存插件、生命周期与清理、为什么会影响同进程其他会话；DSH 内置的「自修改」工具集。
仓库：`local/deepseek-harness/`。下面所有 `路径:行号` 都相对该仓库根。

## 机制说明

本篇要讲清 DSH 的**运行期组合**：不改 `package.json`、不改 patch 文件、不装包、不重启，往一个**正在跑的进程**里挂一截代码。

必须先把前 16 篇的隐含前提点破。到 16 篇为止，读者见过的所有插件都有一个共同点：**它们都是被「读配置文件」读进来的**。不管是 02 篇的 `dsh plugin add`、03 篇的 patch insert、还是 07 篇的热重载——那条链路的起点永远是磁盘上的一个 YAML 文件，终点是 Loader 按行 import 一个模块。

Cordis 本身没有这个限制。Loader 只是**一个普通插件**，它做的事是「读配置 → 对每行调用 `ctx.plugin(...)`」。而 `ctx.plugin()` 是框架 API，任何插件都能调。所以「动态挂插件」不是 DSH 新加的能力，而是**一直就在那儿、只是没人调**的东西。

### 两条路径的分工

| | 静态路径（前 16 篇） | 动态路径（本篇） |
| --- | --- | --- |
| 谁调用 | `cordis-plugin-loader` 按配置行 | 你自己的代码（或 DSH 内置 runner） |
| 输入 | 磁盘上的模块路径 / 包名 | 内存里的一段函数或 `{ apply }` 对象 |
| 存续 | 跟配置文件走，重启后还在 | 只在进程内存里，重启即消失 |
| 谁清理 | Loader 按行 dispose | 持有 fiber 的人 dispose |

挂到读者已有的心智模型：

- **`ctx.plugin(fn)` ≈ `element.appendChild(child)`**。它把一个「子节点」挂到当前上下文之下，返回一个句柄；这个句柄的 `dispose()` 就是 `removeChild`。而 `ctx.registry` ≈ `element.children`——它是**运行中检查插件树**的入口。
- **「内存插件」≈ 浏览器 DevTools 里现敲的一段 JS**，或者 REPL 里定义的一个函数。它真实生效、真实影响运行中的系统，但它不在任何文件里，关掉标签页就没了。
- **`ctx.effect` / disposer ≈ 05 篇已经讲过的资源归属**。动态挂载最容易犯的错和 05 篇完全一样：注册了东西没交给 fiber，dispose 之后它还留着。区别只是 05 篇的触发点是 Loader 卸载行，本篇的触发点是你自己调 `dispose()`。
- **「会影响同进程其他会话」≈ 在共享的 Node 进程里改一个全局变量**。这条不是设计缺陷，而是「同进程」这个词的直接后果——后面专门有一节讲它的边界。

### 四个必须讲清的概念

1. **fiber**：一次插件应用（plugin application）的运行时实例。`ctx.plugin()` 返回的就是它，它的 `uid` 在注册表里唯一，根 fiber 的 uid 是 0，dispose 之后变成 `null`（`vendor/cordis/src/fiber.ts:185-186`）。**fiber 是有状态机的**：`PENDING`（等依赖服务）→ `LOADING` → `ACTIVE` → `FAILED` / `UNLOADING` → `DISPOSED`（`vendor/cordis/src/fiber.ts:147-154`）。「挂上了但没生效」几乎总是 `PENDING`——它在等一个 `inject` 里写了但没人提供的服务。
2. **registry**：插件注册表。它按「插件的回调函数」为键，记录该插件的**所有 fiber**（同一个回调可以被挂多次，每次生成一个 fiber）（`vendor/cordis/src/registry.ts:135-145`、`316-336`）。`registry.delete(plugin)` 会把该插件的每个 fiber 都 dispose 掉再删记录（`vendor/cordis/src/registry.ts:258-267`）。`keys/values/entries/forEach` 就是运行中遍历插件树的那几个方法。
3. **fiber 的 dispose 是被父 fiber 的 effect 拥有的**。`new Fiber(...)` 的构造函数里，真正的 disposer 是这么来的（`vendor/cordis/src/fiber.ts:265-297`）：

   ```ts
   this.dispose = parent.fiber.effect(() => {
     const remove = runtime.fibers.push(this)
     return async () => { /* 摘掉自己、必要时删 runtime、卸载 */ }
   }, 'ctx.plugin()')
   ```

   这句话是整篇的枢纽：**子插件的生死被登记为父 fiber 的一个 effect**。所以父 fiber 卸载时，子插件自动跟着走，不需要谁记得手动清。这也是为什么「动态挂的插件在会话结束时会不会残留」这个问题的答案是「看它挂在谁的 fiber 上」。
4. **清理是反序的、可 await 的**。`ctx.effect(fn, label)` 收集 `fn` 产生的 disposer，在卸载时**反序**执行，可以返回 Promise，卸载会等它（`vendor/cordis/src/fiber.ts:402-418`、`425-442`）。

### 运行中检查插件树的三条路

1. **`ctx.registry`**（框架层）：`forEach` / `entries` 能列出「每个仍在注册表里的插件回调，以及它的所有 fiber」。适合回答「现在到底挂了多少东西」。
2. **`ctx.loader`（如果有）**：`Loader.locate(fiber)` 沿父链往上找「这个 fiber 属于配置树的哪一行」（`vendor/loader/src/index.ts:177-185`）。适合回答「这个插件是哪一行装进来的」。注意：**内存挂的插件不属于任何行**，`locate()` 对它返回 `undefined`——这正好是区分两条路径的判据。
3. **`ctx.get('loader')?.store`**（配置层）：`EntryTree.store` 是 id → Entry 的字典（`vendor/loader/src/config/tree.ts:13`），`getTasks()` / `await()` 用来判断树还在加载还是已经安定（`vendor/loader/src/config/tree.ts:36-62`）。

### DSH 已经把这套东西做成产品了

这是本篇和 20~25 篇的分界：**读者不用自己从零搭**。仓库里有四个包组成一个「自修改」工具集（旧组名就叫 `packages/self-modification/`，后来改名 `packages/extensions/`，理由记录在 `.agents/notes/archived/architecture/2026-08-11-repository-naming-contract-and-rename-ledger.md:261`）：

| 包 | 角色 | 给谁用 |
| --- | --- | --- |
| `@deepseek-ai/dsh-tool-cordis` | 七个模型可见工具 + 一段系统提示 | **模型** |
| `@deepseek-ai/dsh-cordis-host-runner` | 定义注册表 + `node:vm` 沙箱 + Host 半生命周期 | 工具委托给它 |
| `@deepseek-ai/dsh-cordis-client-runner` | 浏览器半的加载与应答 | 页面 |
| `@deepseek-ai/dsh-client-ui-cordis` | 面板与卡片（人在这上面批准） | **人** |

模型看到的七个工具（`packages/extensions/tool-cordis/README.md` 的「What the tools do」一节）：`cordis_inspect_list`、`cordis_inspect_query`、`cordis_inspect_self` 三个只读检查工具；`cordis_define`、`cordis_run`、`cordis_stop`、`cordis_undefine` 四个生命周期工具。

三个面向文章的结构性事实：

- **定义只活在进程内存里。** README 原话：「Definitions exist only in process memory and disappear when DSH restarts; the package does not write repository files, install dependencies, or change `cordis.yml`.」会话日志只留下 `cordis_define` 的调用参数（含源码）和回执，解析后的定义只在内存注册表里（`packages/extensions/cordis-host-runner/README.md` 的 "What happens to definitions"）。
- **版本不可变，修错靠加版本再切指针。** 一个 plugin 持有一串 package，`define` 之后 package 不再变；`currentPackageId` 是正在跑的，`nextPackageId` 是目标，`mode: "run"` 与 `mode: "update"` 的区别就是目标等不等于当前（`packages/extensions/cordis-host-runner/README.md` 的 "Design philosophy"）。这也解释了 `cordis-host-runner` 那条 `already registered` 的教学错误为什么要用户「先 stop 旧 id，再 run 新版本」。
- **Host 半挂在一个人造 group fiber 下。** runner 第一次需要时创建 `{ name: 'cordis-dynamic', apply: () => {} }` 这个空插件当容器（`packages/extensions/cordis-host-runner/src/index.ts:1237-1240`），每个 Host 半是它下面的子 fiber；停一个 package 就是 `await run.fiber.dispose()`（`packages/extensions/cordis-host-runner/src/index.ts:1219-1232`）。**注意这就是第 3 条概念的实战用法**：所有动态 Host 半共享同一个父 fiber，所以关掉 runner 就等于一次清空。

### 为什么会影响同进程其他会话

这条必须讲，而且要给准确的作用域词，不能用「可能会」。

- **工具定义本身是会话级的**：一个 package 只对定义它的会话可见，别的会话读它就像不存在；DSH 重启全部消失（`packages/extensions/cordis-host-runner/README.md` 的 "What happens to definitions"）。
- **但它跑起来之后的影响面是全进程的**：`cordis-host-runner/README.md` 的 "Trust stance" 说「the services it declares reach the live runtime」；`tool-cordis/README.md` 的 "Boundaries to plan around" 说得更直接：「stays active across later turns, and can affect other sessions in the same process while running」。原因是 Host 半的 fiber 挂在**根上下文**下的 group 上，而 `ctx.provide()` 写的是全局服务存储——不是「当前会话」的存储。
- **想缩小作用域，用的是 `dsh-scope`**，不是「少写点」。`createScope(ctx, key)` 用 `ctx.plugin(scope)` 造一个带标签的 fiber，然后 `fiber.ctx.extend({ [kScope]: key })` 得到一个作用域上下文：**通过它注册的东西同时获得「作用域可见」和「作用域生命期」两件事**，`dispose()` 一次收干净（`packages/core/scope/src/index.ts:130-145`）。core 组的注册表就是这么做的——工具、提示段、对话记录里都能看到那一套错误文案：「for a per-agent variant, register through that agent's `agent.ctx` instead」（`packages/core/tools/src/index.ts:719-721`）。
- **DSH 自己的动态工具集就是全进程作用域的**，所以它的信任口径是「把动态 package 当成 bash 访问」：sandbox 隔离的是全局变量，**不是安全边界**（`packages/extensions/tool-cordis/README.md` 的 "Known Limitations"）。

### 07 篇之后往下走什么（不要重复的部分）

07 篇讲的是 HMR 的**配置侧**：`patchReload`、`cordis-plugin-hmr` 的 `root` 配置、改文件后自动 reload。本篇讲的是**同一个 Cordis 运行时的另一条入口**。两者的区别值得用一张表收尾：

| | 07 篇的 HMR | 本篇的动态挂载 |
| --- | --- | --- |
| 触发源 | 磁盘文件变化 | 一次函数调用 |
| 作用对象 | **配置树里的某一行**被替换/重载 | **新造一个 fiber**，不属于任何行 |
| 需要磁盘上先有文件 | 是 | 否 |
| 需要重启 | 否（live 模式下） | 否 |
| 谁会用它 | 插件作者改自己的代码 | 模型/人，临时加一段功能 |

**一处必须纠正的术语**（调研发现）：任务说明里提到「07 篇讲过 HMR 的 `loader/volatile-update`」。全仓库搜索 `volatile-update` 得到**零结果**；`vendor/hmr/src/index.ts` 里也没有 `volatile` 字样（`grep -n volatile vendor/hmr/src/index.ts` 无输出）。这个符号在当前版本里不存在（可能来自更早的版本或上游 Cordis 的其他分支）。写 19 篇时**不要引用它**；07 篇正文里也没有出现过这个词。HMR 在本仓库的真实事件是 `hmr/change`、`hmr/reload`、`hmr/config-update-failed`（`vendor/hmr/src/index.ts:17-29`），另有内部事件 `loader/config-update`、`loader/entry-init`、`loader/partial-dispose`、`loader/patch-context`（`vendor/loader/src/index.ts:24-30`）。「volatile 字段」在 14 篇里指的是设置页那个把配置标为易失的字段，与 HMR 无关。

## 可引用代码片段

### 1. `ctx.plugin()` 的实现（22 行，含注释就是全篇的引子）

`vendor/cordis/src/registry.ts:316-336`：

```ts
  plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {
    // check if it's a valid plugin
    const callback = this.resolve(plugin)
    if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method, received ' + typeof plugin)
    this.ctx.fiber.assertActive()

    let runtime = this._internal.get(callback)
    if (!runtime) {
      let name = plugin.name
      if (name === 'apply') name = undefined
      runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
      this._internal.set(callback, runtime)
    }

    const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
    const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
    wrapped.then = (onFulfilled, onRejected) => {
      return fiber.await().then(onFulfilled, onRejected)
    }
    return wrapped
  }
```

要点的三句话：`resolve` 把三种插件形态归一成同一个回调；同一个回调只建一个 runtime，多次挂载只增加 fiber；返回值是个 **thenable 的 fiber**——`await ctx.plugin(x)` 等到它安定（或抛出启动错误），不 await 就是「挂上了，还没好」。

### 2. 运行中遍历插件树

`vendor/cordis/src/registry.ts:258-291`（截取 258-267 与 284-291）：

```ts
  delete(plugin: Plugin) {
    const key = this.resolve(plugin)
    const runtime = key && this._internal.get(key)
```

### 3. 子插件的生死是父 fiber 的 effect

`vendor/cordis/src/fiber.ts:265-297`：

```ts
      this.dispose = parent.fiber.effect(() => {
        const remove = runtime.fibers.push(this)
        return async () => {
          this.uid = null
          emitPluginDisposed(this.context, this)
          if (this.ctx.registry.has(runtime.callback)) {
            remove()
            if (!runtime.fibers.length) {
              this.ctx.registry.delete(runtime.callback)
            }
          }
          this._setEpoch(INACTIVE)
          // A PENDING fiber can already own effects registered by an
          // internal/plugin observer. Its epoch is still INACTIVE, so
          // _setEpoch() has no transition to drive; explicitly unload that
          // pre-activation work before reporting disposal complete.
          if (!this.inertia) {
            this._updateState(() => {
              this.inertia = this._unload()
              return FiberState.UNLOADING
            })
          }
          while (this.inertia) {
            await this.inertia
          }
        }
      }, 'ctx.plugin()')
```

### 4. DSH 的 Host 半生命周期（`lifecycle.ts` 全文 57 行，摘前 45 行）

`packages/extensions/cordis-host-runner/src/lifecycle.ts:22-45`：

```ts
export async function startHostHalf(
  group: Fiber,
  plugin: Plugin,
  reportGuardFailure: (error: Error) => void,
): Promise<Fiber> {
  await group.await()
  const fiber = group.ctx.plugin(guardedPlugin(plugin, reportGuardFailure))
  try {
    await fiber.await()
  } catch (error) {
    await fiber.dispose()
    const message = error instanceof Error ? error.message : String(error)
    // The commonest startup collision is running a NEW version of a package
    // while the old run still holds the name — teach the replace recipe.
    if (message.includes('already registered')) {
      throw new Error(
        `${message} — to REPLACE something an earlier dynamic package registered, first cordis_stop that package's id `
        + '(find it with cordis_runtime_inspect what:"temporary"), then run the new version.',
      )
    }
    throw error instanceof Error ? error : new Error(message)
  }
  return fiber
}
```

这段 24 行里包含了动态挂载的全部纪律：**先等父容器安定**（`await group.await()`）、**挂上后等它安定**（`await fiber.await()`）、**失败立刻收回**（`await fiber.dispose()`）、**把失败翻译成可操作的下一步**。文件头注释第 5-7 行还把「为什么停止不需要一个对称的 helper」说了：卸载走普通的 `await fiber.dispose()`，因为插件注册的一切都是它自己 fiber 上的 effect。

两个写文章时值得放大的坑：

1. **「挂上了」不等于「生效了」。** 三个不同的安定点：`ctx.plugin()` 返回（已登记）、`await fiber.await()` 返回（已安定）、`fiber.state === FiberState.ACTIVE`（真的在提供）。`PENDING` 是它们之间最常见的陷阱，而且**不报错**。
2. **不要用 `ctx.<service>` 属性代理检查可选服务。** `packages/AGENTS.md` 明说：「Optional services use `ctx.get(name)`. Reserve `ctx.<name>` for declared injections; the property proxy is topology-sensitive, while strict `ctx.get` reads the global service store.」沙箱给动态 package 的建议也是 `ctx.get(name)`（`sandbox.ts:20`）。这一条对「运行中检查」尤其重要——你要问的是「全局存储里有没有」，不是「我这个上下文位置能不能看见」。

## 外部插件可行性

**结论：机制本身完全对树外插件开放；DSH 的成品工具集也能从 npm 装，但它不是一个「组合包」，必须由某一层 patch 显式挂上去。**

分四点给证据。

**（一）`ctx.plugin()` 是公开框架 API，无仓库内依赖。** 它定义在 vendored Cordis 里（`vendor/cordis/src/registry.ts:316-336`），而 `@deepseek-ai/cordis` 是每个 DSH 包的 peerDependency，也是 npm 上的公开包。任何树外插件只要 `inject` 到自己的上下文，就能在 `apply` 里 `ctx.plugin(内存里的函数)`。这条路径**不需要** `dsh.bundle`、不需要 runner、不需要任何仓库内构建管线——它就是一段普通 JS。

不过有两个与 18 篇同源的现实约束：

- **同一个 Cordis 实例才共享服务存储。** 树的读法必须走 `ctx.get('...')`；`packages/boot/app-boot/src/profile.ts:16-22` 说明启动器为什么要维护 `$DSH_HOME/profiles/node_modules` 这份扁平回退：让树外插件的 peer 依赖（含 `@deepseek-ai/cordis`）**解析到安装目录那唯一一份 cordis**，否则你会拿到第二份实例、服务互相看不见。所以外部插件「能动态挂插件」的前提是自己那份 `@deepseek-ai/cordis` 与宿主是同一实例——由启动器的回退机制保证，不需要你做额外的事，**但也不要试图把 cordis 打进 bundle 产物**。
- **动态挂的插件不进入配置树。** `Loader.locate()` 对它返回 `undefined`（`vendor/loader/src/index.ts:177-185`），所以 dump-config 看不到它、patch 也定位不到它。这是它的性质，不是缺陷。

**（二）DSH 的成品工具集可从 npm 安装。** 已核对 npm registry：

| 包 | `latest` | `next` | `alpha` |
| --- | --- | --- | --- |
| `@deepseek-ai/dsh-tool-cordis` | `0.0.1-rc.1` | `0.2.0-rc.2` | `0.2.1-alpha.2` |
| `@deepseek-ai/dsh-cordis-host-runner` | `0.0.1-rc.3` | `0.2.0-rc.2` | `0.2.1-alpha.2` |
| `@deepseek-ai/dsh-cordis-client-runner` | `0.0.1-rc.3` | `0.2.0-rc.2` | `0.2.1-alpha.2` |
| `@deepseek-ai/dsh-client-ui-cordis` | `0.0.1-rc.3` | `0.2.0-rc.2` | `0.2.1-alpha.2` |

（本仓库版本 `0.1.5-rc.2`；`latest` 明显落后，给安装命令时用 `next` 或显式版本号。）

**（三）关键限制：`dsh-cordis-host-runner` 不是组合包——npm 上的它没有 `dsh` 字段。** 已核对 registry：`@deepseek-ai/dsh-cordis-host-runner` 的 `latest` 与 `next` 两个版本的 manifest 里 `"dsh": null`（既没有 `dsh.bundle`，也没有 `dsh.profile`）。同理 `tool-cordis` 的 `next` 版本 `"dsh": null`。

后果有两条，都要在文章里讲清：

- 你**不能**把它们写进 `dsh.profile.bundles`——那样会在启动时抛 `declares no dsh.bundle in its package.json`（`packages/boot/app-boot/src/profile.ts:788-790`）。
- 正确做法是**在自己的 patch 层（或 profile 的 `cordis.patch.yml`）里插入它们**，也就是官方示例 `apps/cli/config/examples/cordis/cordis.yml` 的写法。patch 行里的裸包名由 Loader 解析，落在 profile 的 `node_modules` / 启动器维护的回退目录里（`packages/boot/app-boot/src/profile.ts:16-22`）。

顺带一个对本篇 demo 很实用的推论：**`dsh plugin --profile <name> add` 会因为这些包没有 `dsh.bundle` 而打印「installed as a plain dependency, not a profile layer」的警告**（`apps/cli/src/plugin.ts:70-75`）——那是预期行为，正好可以当 18/19 两篇的接缝：18 篇教你什么时候包该是组合包，19 篇演示一个「是依赖、但不是组合包」的包。

**（四）只有仓库内走得通的部分：`cordisInspect` 的 API 目录与浏览器半。**

- 三个 inspect 工具的部分数据来自**生成物**：`packages/extensions/tool-cordis/src/api-catalog.ts` 是「工作区 Cordis 声明的投影」，由 `pnpm run gen-cordis-api` 重新生成、由 `verify-cordis-api` 把关（`tool-cordis/README.md` 的 "Source map" 表）。也就是说，从 npm 装到的版本里这张表是**发布时那一刻**的快照——它不会反映你本地新装的第三方服务。想让它认识自己的服务，得自己在发布侧重新生成。
- **`ctx.remote` 那道墙在这里同样存在**：`ctx.dynamicCordisRunner` 是 `TypertRemoteService`（`packages/extensions/cordis-host-runner/src/index.ts:124`），它暴露了 `@Remote('undefineFromPanel')` / `@Remote('runHostHalf')` 这类远端方法（`docs/subsystems/extensions.md`）。14 篇遇到的「只有仓库内构建管线才走得通」的限制在这里表现为：**Host 半的能力你随便用，Client 半与面板的远端方法需要 Typert 的生成物**。所以外部插件要做「自带一个批准面板」这件事，依赖面比「Host 半 + 工具」大得多。**未确认**：仓库里没有关于「第三方包能否独立生成 Typert 产物」的说明；`packages/api/typert/` 相关文档没有针对树外包的路径说明。

**跨版本兼容的提醒**：`engines.dsh` 不被执行（`packages/util/package-manifest/README.md:91`），而四个扩展包的 peerDependencies 是**精确版本对齐**的（例如 `next` 频道里 `tool-cordis` 的 `peerDependencies` 是 `"@deepseek-ai/dsh-agent": "0.2.0-rc.2"`、`"@deepseek-ai/dsh-cordis-host-runner": "0.2.0-rc.2"`）。所以从 npm 装这套东西时，**必须让所有 `@deepseek-ai/*` 落在同一发布批次**，否则 peer 不满足而无人告诉你。

## demo 设计建议

建议做成**两个 demo**，因为 19 篇其实有两件事：直接用框架 API 动态挂载（读者自己写），和用 DSH 的成品工具集让模型自己挂（读者配一行）。前者是理解，后者是体验。

### demo A：`dsh-live-greeter`——10 行 `apply` 换一个运行中的工具

这是全篇**核心机制的最短证明**：不改任何配置文件，让一个已经跑起来的 profile 多出一个工具，再收回去。

包名：`dsh-live-greeter`。目录沿用专栏风格：

```
dsh-live-greeter/
├── package.json
├── patch.yaml
├── src/
│   ├── dsh-live-greeter.ts   # 装配：挂一个动态 fiber，并在卸载时收回去
│   └── greeter-tool.ts       # 被动态挂上去的「内存插件」
├── tsconfig.json
└── install.sh
```

`src/greeter-tool.ts`（被挂的那个插件，20 行；注意它**不在任何 patch 行里**）：

```ts
/**
 * 被运行时挂上去的内存插件：注册一个打招呼的工具。
 * 它只通过 ctx 拿到能力，不 import 宿主内部模块。
 * @module dsh-live-greeter/greeter-tool
 */
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'live-greeter'

/** 需要工具注册表；没有它这个 fiber 会停在 PENDING。 */
export const inject = ['tools']

/**
 * 注册工具。
 * @param ctx - 已注入 tools 的插件上下文。
 */
export function apply(ctx: Context): void {
    ctx.tools.register(defineTool({
        name: 'live_greet',
        description: 'Return a greeting. Mounted at runtime by dsh-live-greeter.',
        parameters: { whom: { type: 'string', required: true, description: 'Who to greet.' } },
        output: { schema: { type: 'json' } },
        execute(args) {
            return Promise.resolve({ greeting: `hello, ${args.whom}` })
        },
    }))
}
```

`src/dsh-live-greeter.ts`（装配插件，35 行；这里就是文章要逐行讲的代码）：

```ts
/**
 * 把 greeter-tool 作为一个内存插件挂到当前进程，并保证它随本插件一起被收回。
 * @module dsh-live-greeter
 */
import type { Context, Fiber } from '@deepseek-ai/cordis'
import * as greeterTool from './greeter-tool.ts'

export const name = 'live-greeter-mount'

/**
 * 挂载内存插件；卸载由本 fiber 的 effect 负责。
 * @param ctx - 本插件的上下文。
 */
export function apply(ctx: Context): void {
    // ctx.plugin 返回一个 thenable 的 fiber：
    // await 它 = 等它安定；不 await = 已登记但可能还在 PENDING。
    const fiber: Fiber = ctx.plugin(greeterTool)

    // 检查：它到底有没有真的在提供能力？
    ctx.effect(() => {
        ctx.logger(name).info('mounted fiber uid=%s state=%s', String(fiber.uid), String(fiber.state))
        const disposeCheck = ctx.on('internal/status', (changed: Fiber, from: number) => {
            if (changed === fiber) ctx.logger(name).info('state %s -> %s', String(from), String(changed.state))
        })
        // 这一整段（含上面那个监听器）随本插件卸载一起撤销。
        return () => {
            disposeCheck()
            ctx.logger(name).info('unmounting uid=%s', String(fiber.uid))
        }
    }, 'live-greeter: mount + observe')
}
```

`patch.yaml`（**只有装配那一条行**，内存插件没有行）：

```yaml
# dsh-live-greeter 的 bundle 补丁：只有装配行。
# greeter-tool 是被运行期挂上去的，不在任何 patch 行里。
- insert:
    - id: live-greeter-mount
      name: 'dsh-live-greeter'
```

验证命令（三步，正好对应三个概念）：

```sh
# 1. 装上（这一步走 18 篇的路径）
dsh plugin --profile test add "link:$DIR"

# 2. dump 只能看到装配行——内存插件不在配置树里
dsh --profile test --dump-config | grep -c 'live-greeter-mount'   # 1
dsh --profile test --dump-config | grep -c 'greeter-tool'         # 0

# 3. 启动后让模型调 live_greet；然后改一行 patch 触发用户层热重载，
#    观察日志里 "unmounting uid=..." 与重新挂载的 uid 变化。
#    再 Ctrl-C，观察进程退出时不再有残留。
```

**要写在文章里的观察点**：`Fiber.uid` 每次重挂都不一样（`registry.counter` 是单调递增的，`vendor/cordis/src/registry.ts:206-209`）——这是「真的卸掉重挂了」而不是「复用了同一个 fiber」的肉眼证据。

### demo B：`dsh-self-cordis`——给模型装上「自己加功能」的能力

这个 demo 不写业务代码，只做两件事：装两个包、加一行 patch。

`package.json`（**注意这里没有 `dsh.bundle`** ——正是 18 篇讲的另一种包）：

```json
{
  "name": "dsh-self-cordis",
  "version": "0.1.0",
  "type": "module",
  "private": true,
  "dependencies": {
    "@deepseek-ai/dsh-cordis-host-runner": "0.1.5-rc.2",
    "@deepseek-ai/dsh-tool-cordis": "0.1.5-rc.2"
  }
}
```

`install.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail

DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

cd "$DIR"
pnpm install

# 这两个包都不是组合包（没有 dsh.bundle），所以 add 只会给警告：
# "declares no dsh.bundle — installed as a plain dependency, not a profile layer"
dsh plugin --profile web add "@deepseek-ai/dsh-cordis-host-runner@0.1.5-rc.2"
dsh plugin --profile web add "@deepseek-ai/dsh-tool-cordis@0.1.5-rc.2"

# web profile 自带 host-runner / client-runner / 面板，只缺工具面那一行。
PATCH_FILE="$HOME/.dsh/profiles/web/cordis.patch.yml"
mkdir -p "$(dirname "$PATCH_FILE")"
touch "$PATCH_FILE"
if ! grep -q 'id: tool-cordis' "$PATCH_FILE"; then
  cat >> "$PATCH_FILE" <<'EOF'

# 19 篇：把自修改工具集挂上（web profile 已有 host-runner 与面板）。
- insert:
    - id: tool-cordis
      name: '@deepseek-ai/dsh-tool-cordis'
      config:
        vmTimeoutMs: 5000
EOF
fi

echo "装上后重启 web profile，然后在会话里说：先 cordis_inspect_list，再 cordis_define 一个 hello 工具，最后 cordis_run。"
```

验证命令：

```sh
# 1. 工具真的进了模型可见的工具表
dsh --profile web --dump-config | grep -A3 'id: tool-cordis'

# 2. 启动后，在会话里让模型跑一遍：
#    cordis_inspect_list  → 看有哪些 Inspect Provider
#    cordis_define        → 写一个 host 半（3~6 字母 idPrefix）
#    cordis_run           → mode:"run"
#    cordis_inspect_self  → 看 version 指针与运行诊断
#    cordis_stop          → 停掉，定义还在
#    cordis_undefine      → 连定义一起删

# 3. 验证「进程本地」：重启 dsh，cordis_inspect_self 返回空。
```

**两个 demo 在文章里的分工**：A 用来讲机制（读者能逐行看到 `ctx.plugin` / `fiber.uid` / effect 收回）；B 用来讲 DSH 已经把它做成产品、以及边界（会话级定义 / 全进程影响 / 沙箱不是安全边界）。B 的信任提示要原样引用官方措辞，不要自己软化：`tool-cordis/README.md` 说「load this plugin as deliberately as you would grant [bash access]」，「the sandbox is containment for honest code, not a security boundary」。

**一处建议的诚实说明**：不要承诺「让模型随便加功能很安全」。把 `vmTimeoutMs` 只能围住同步部分、异步函数体逃逸、沙箱 `ctx` 白名单只有四个方法、以及 Host 半能提供全局服务这些事实都摊在文章里，再由读者决定装不装。
