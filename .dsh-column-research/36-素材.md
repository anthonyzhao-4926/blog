## 1. 机制说明

### 1.1 `docs/` 的组织方式

DSH 的文档不是「一堆 md」，而是一套**一处一个事实（one home per fact）的分层制度**。制度本身写在 `docs/AGENTS.md:15-33` 的那张表里，逐层规定「谁负责什么、什么不许写在那里」：

- 根 `AGENTS.md` / 子树 `AGENTS.md`：标准命令（standing orders），一到三行，细节链到 owner。
- `docs/architecture.md`：有序地图——组合、核心包、循环、seam、扩展点，「改 `packages/` 之前先读」。
- `docs/subsystems/`：每个子系统一页参考：类型定义、语义、生成的 Cordis API。「行为叙述」不属于这里。
- `.agents/notes/`：Agent Note，记录「为什么、放弃了什么、需要验证什么」。
- `docs/postmortem/`：唯一允许写事故叙事的一层。
- `docs/cookbook/`：带编号验证步骤的操作指南（设计理由链到 Agent Note）。
- 生成型参考（`cordis-surface` 区域、`cordis-api/`、`tool-catalog`、`config-catalog`、`persistence-catalog`、`module-graph`）：从源码重新生成、有新鲜度门禁。
- 包 README：单个包的契约。
- Skills（`.agents/skills/`）：可复用工作流。

放置规则一句话在 `docs/AGENTS.md:34`：bug → postmortem；理由 → Agent Note；流程 → cookbook；类型 → subsystems；包契约 → README；标准命令 → 根 `AGENTS.md` + 理由链接。

**三种维护模式**（`docs/graph-atlas.md:19-31` 的表格，末行 `:33` 是自我声明）：

| 图 | 模式 | 含义 |
| --- | --- | --- |
| module-graph、tool-catalog | `generated` | 全部由脚本生成，不许手改 |
| capability-seams、组合页、事件矩阵 | `hybrid generated` | 生成 + 人工策展混合 |
| agent-lifecycle、tool-execution-pipeline | `curated` | 人工撰写，无生成器 |

**双语三件套**：`docs/i18n/README.md:10` 规定一对文档是**同目录三个兄弟文件**——`foo.md`、`foo.zh.md`、`foo.i18n.yaml`；`:11-18` 说明 `.i18n.yaml` 里存的是**两侧的 Git blob 哈希**（不是 commit 哈希），`--write` 才把当前内容记录为「已确认一致」。`:22` 要求两侧的结构签名（标题层级与顺序、列表种类、表格行列数、代码块逐字节、语义链接目标）逐项对应。`:38` 给出实际做法：一个 PR 改了任一侧，同一 PR 里用一次术语导向的翻译更新另一侧，然后 `--write <pair>` 重新记录。`:40` 直说这条门禁的边界：**绿只证明「在这个内容上双方被确认过一致」，不证明确认得对**。

### 1.2 推荐的阅读顺序

对「想改内核」的读者，从「先读地图，再读契约，最后读理由」这个顺序走，每一跳都能从上一跳找到落点：

1. `docs/graph-atlas.md`（全文 33 行）——它是索引，告诉你有哪些图、各自什么模式。
2. `docs/architecture.md` → `Where new behavior goes`（`:133`）——**唯一的稳定面清单**，一组「想做的事 → 挂在哪」的对应。
3. `docs/capability-seams.md`（`:6` 说明图上有什么）——谁声明服务、有哪些实现、谁在消费。
4. `docs/module-graph.md`（`:6` 说明读法：边 `a --> b` 表示 a 把 b 当 peer）——「共享实例」关系，普通 runtime 依赖不画。
5. `docs/subsystems/<主题>.md`——精确类型与语义，含生成的 `cordis-surface` 区域。
6. 生成目录（`tool-catalog` / `config-catalog` / `persistence-catalog`）——当字典查。
7. `.agents/notes/`——为什么这么设计、放弃了什么。
8. `docs/postmortem/`——哪一类 bug 曾经真的漏出去。

### 1.3 一个改动要过哪些门禁

门禁的**权威清单不在文档里，在代码里**：`scripts/run-gates.ts` 是唯一的编排器，`package.json` 是脚本的唯一登记处。`gatesForMode()`（`:232-296`）按模式返回门禁数组；常用入口：

- `pnpm run check:all`（`package.json:77` → `run-gates.ts:263-283`）：本地全套近似，串了 runtime-closure、cordis-config、client-domain-graph、test、审批/议题策略、duplication、snapshot、expected、build、build:web、hygiene 族、doc-sync 族、module-graph。
- `pnpm run check:ci`（`package.json:78` → `run-gates.ts:318-345`）：CI 主泳道，静态门禁 + typert 契约 + typecheck + lint + coverage + node 兼容冒烟 + snapshot + doc-sync + module-graph + build + publint + node-next-types + 内建包不变式 + built-bin 冒烟。
- `pnpm run doc-sync`（`package.json:170` → `run-gates.ts:715-768`）：**29 条**文档门禁，从 `doc-typecheck`、`docs:build`、`verify-doc-graphs` 一直排到 `verify-package-readme-limitations`。
- `pnpm run test:docs`（`package.json:116` → `run-gates.ts:776-778`）：`doc-quick`，即上面那 29 条里 `quick: true` 的子集，不构建、不重新生成。

`gen-*` 与 `verify-*` 的分工不是两类脚本，而是**同一个脚本的两种模式**：

```
package.json:158  "verify-doc-graphs": "tsx scripts/gen-doc-graphs.ts --check"
package.json:160  "verify-persistence-catalog": "tsx scripts/gen-persistence-catalog.ts --check"
package.json:162  "verify-session-format-catalog": "tsx scripts/gen-session-format-catalog.ts --check"
package.json:168  "verify-module-graph": "tsx scripts/gen-module-graph.ts --check"
```

**Git 钩子刻意很窄**（`docs/development.md:117-127`）：`pre-commit` 只做暂存区的配对记录校验、`*.staged.json` 配置的 lint（带一次有界重试）、必要时重生成 `THIRD_PARTY_NOTICES.md`、暂存 diff 的空白检查、vendor 清单守卫；`pre-push` 只跑一次增量 typecheck。`:125` 原话：钩子**故意不跑**测试、快照、文档检查、构建、hygiene——那是 CI 的事。`:127` 补一句：`pnpm run check:all` 与 Git 钩子无关，也不是「给 agent 的指令」。

### 1.4 三种测试（以及实际是几种）

`docs/testing.md:7-15` 的 `Tiers` 一节列了**七**项，而 README 规划写的是「三种测试」。实际分层是：

| 层 | 命令 | 覆盖什么 | 需要 key |
| --- | --- | --- | --- |
| 单测 | `pnpm run test` | `tests/**` 下的 spec + `scripts/**/*.spec.ts`；每个 registry 必须有 HMR 安全测试（卸载贡献 fiber、断言清理） | 否 |
| 覆盖率 | `pnpm run test:coverage` | **门禁跑法**：`packages/*/*/src` 逐文件 100% | 否 |
| 真 API e2e | `pnpm run test:e2e` | 真供应商 API；各套件无 key 自跳过 | 是 |
| owner-local expected | `pnpm run test:expected` | 无 key 的 CLI/进程期望输出，不走记录会话 | 否 |
| 性能基准 | `pnpm run test:bench` | `benchmarks/` 里的用户路径时间/堆/伸缩预算 | 否 |
| 会话快照 | `pnpm run test:snapshot` | 顶层场景的最高 generation 提供输入与模型回放，同时作为期望的持久化结果 | 否（回放） |
| Web 浏览器快照 | `pnpm run test:web` | Chromium 对比会话驱动输出与纯 UI 输出 | 否 |

三条最容易被误读的规则：

- **覆盖率是必要的、不是充分的**（`docs/testing.md:10`）：逐文件 100% 只证明「这些行跑过」。
- **产品可见插件需要一次真组合测试**（`:39`）：手工 `ctx.plugin(...)` 的套件不够，得把 test-only 的 `cordis.yml` 走 Loader 与进程启一遍。
- **要验证世界，不要验证自述**（`:35`）：e2e 断言要重新跑命令或重新读文件；对 agent 自己输出的关键词探测放得过一个作弊的 agent。
- **「真入口路径」指已发布产物**（`:41`）：包的 `bin` 是 plain `node` 跑构建出的 `lib/bin.js`，专门暴露 tsx 会掩盖的失败（settle 竞态、模块解析、被吞掉的加载失败）。

`:53-55` 是硬约束：任何非平凡、模型/协议/人可见的改动，同一个 PR 里都要加或更新一个**无 key 的记录会话场景**；`Agent-loop`、`session-lifecycle`、`SessionEventMap` 的改动还要同时更新 TypeScript 与 Python 两个 SDK 的期望输出。

### 1.5 invariants 与 defensive-patterns 各解决什么

**invariants 解决「没人看出来」的问题**：`ctx.invariants` 是一个可配置的注册表服务（`docs/subsystems/invariants.md:5`），它不属于 agent-loop 主干，也不是三件套 seam，而是 support 组的一个包。每个 workspace 包**发布一个 `./invariant` 伴生插件**，用自己精确的 npm 包名注册检查（`:5`、`:55`）。检查能断言什么、不能断言什么是硬规则（根 `AGENTS.md:107`）：**只断言包自己拥有的、可独立观察到的关系**；服务存在性、插件元数据、effect、写死的例子都算无效检查。没有可查关系的包必须导出一个**空安装器**，且开头注释以 `No runtime invariant:` 开头、逐包解释为什么没有可查的东西（`docs/subsystems/invariants.md:59`）。这条由 `pnpm run verify-package-invariants` 机械拒绝：生成的占位标记、没解释的空安装器、忽略了 reporter 的非空安装器、注册名不对、导出/发布/依赖/bundle 接线不完整（同 `:59`）。

**defensive-patterns 解决「同一类 bug 再犯」的问题**：全文 33 行，七个模式，每个都是**真的上线过或差一点上线**的缺陷类（`docs/defensive-patterns.md:5`）。它是**读前置**：写生命周期、并发、子进程、拆卸代码之前先读。七个标题分别是「独立报告正交结果」（`:7`）、「两侧都要守公开契约」（`:11`）、「异步状态不是同步状态」（`:15`）、「dispose 要到达静止而不是只发请求」（`:19`）、「派发器里兜住回调异常」（`:23`）、「绝不把环境或可预测路径交给不可信输出」（`:27`）、「link 形状的路径用 unlink」（`:31`）。

两者是**互补**的：invariants 是**运行期**断言「包与包之间的关系还成立吗」，defensive-patterns 是**写代码时**避开已经付过代价的陷阱。测试层的三个对应物（真入口路径、验证世界、资源归属）在 `docs/testing.md`（`defensive-patterns.md:5` 末尾点明这层分工）。

### 1.6 一份 postmortem 该怎么读

`docs/postmortem/README.md:5-11` 定义得很清楚：postmortem **不是** Agent Note（那是设计决策与放弃的备选），而是**向后看**的失败记录——什么坏了、机制是什么、**为什么每一道安全网都漏了**、加了什么具体护栏让同一类 bug 下次大声失败。`:9` 给出三条准入：机制**微妙**、原因**系统化**（漏出去是测试/工具/约定的缺口，不是一次性手误）、**重新发现代价高**。`:11` 规定每篇开头必须是 30 秒能读完的「Executive summary」。现存四篇列在 `:15-18`。

以 0001 为例，读的顺序是「先看 `Executive summary`（`0001-...md:7-9`），再直接跳到 `Why every test missed it`（`:89-98`）和 `Guardrails added`（`:100-106`），最后看 `Lessons`（`:108-113`）」——因为**入口 bug 本身的价值远小于「178 个绿测试 + 100% 行覆盖为什么全漏」**。`:98` 的原话是全篇最有教学价值的一句：行覆盖只证明行跑过。`:104` 展示了「护栏」长什么样：一条无 key 的真 Loader e2e，且**验证过「把 bug 放回去它会红」**。`:113` 是最反直觉的一条：**信 trace，不信理论**——那个漂亮的 shadow 解释是真的，但它是第二个 bug；第一个是一行 export 手误。

0002（`docs/postmortem/0002-js-expression-disabled-filesystem-tools.md`）是另一个类型的反面教材：一个字面量 `!!js` 对象**永久禁用了**文件系统快照工具。它正好接上第 03 篇讲过的 `!!js` 表达式——同一个机制在事故里出过一次。

### 1.7 i18n 流程

见 1.1 的双语契约。补三条对改文档的人最关键的：

- **一次通过，不调用翻译 skill**（`docs/i18n/README.md:61`）：日常工作由**干活的那个 agent** 读完 `terminology.md` 后直接更新对应侧，不生成 brief、不跑单独的翻译评审、不委派子 agent；`dsh-translate-docs` 只在用户显式调用时用。
- **生成型英文源不参与「回链」**（`docs/i18n/README.md:21`、`:46`）：普通英文文档要在 H1 后写 `English | [中文](foo.zh.md)`，而生成型英文源**省略这一行**，否则生成器就过期了；其中文侧仍然链回英文。
- **排除清单是显式的**（`docs/i18n/README.md:48-55` + `scripts/translation-pairing.manifest.json`）：`docs/AGENTS.md`、`.agents/notes/**/AGENTS.md`、`docs/cordis-api/inherited.md`、`docs/i18n/terminology.md`、`style-samples.md`、`translation-prompt.md`、`.github/review-ownership/README.md`、`.agents/notes/archived/`。被排除的文件**不能**有 `.zh.md`，有就报错（`:48`）。

## 3. 可引用片段

**片段 1**（`docs/AGENTS.md:23`，`architecture.md` 这一层的职责，同时说明「什么不属于它」）：

> `architecture.md` | Ordered map: composition, core packages, loop, seams, extension points; read before changing `packages/` | Type definitions (→ subsystems), per-package detail (→ package READMEs), decision rationale (→ Agent Notes), implementation-status annotations

说明：`architecture.md` 是**入口地图**，不是类型手册。它明确排除实现状态标注——所以别在里面写「已实现」。

**片段 2**（`docs/AGENTS.md:38`，写作原则，直接决定你怎么写 PR 说明与文档）：

> **Document current state, not change history.** Name live mechanisms, not PRs, commits, stack positions, or "previously/now/no longer". Keep history in commits, PRs, Agent Notes, or postmortems. General Session-format prose links [version/status authority](session-format-status.md); retain numbers for version-specific contracts, examples, or evidence.

说明：这条规则把「变更史」赶进 commit / Agent Note / postmortem，文档只说当前事实——也解释了为什么 DSH 没有 CHANGELOG（第 20 篇已提这条后果）。

**片段 3**（`docs/testing.md:39`，真组合测试的要求，门禁里最容易被忽略的一条）：

> - Product-visible plugins require a non-unit REAL-composition test. Hand-built `ctx.plugin(...)` suites are insufficient: boot test-only `cordis.yml` through Loader and app/process, mock only external services or nondeterministic inputs, and assert model-visible request/log, durable state, or user-visible output. Keep opt-ins out of shipped defaults.

说明：手工挂载的套件**永远抓不到** Loader 层的问题——这正是 postmortem 0001 的机制。

**片段 4**（`docs/postmortem/0001-acp-default-export-drops-inject.md:98`，覆盖率神话的原文）：

> 100% line coverage was satisfied the whole time. Coverage proves lines *ran*; it says nothing about whether the feature works *the way it ships*.

说明：一句可以直接引用到正文里的判据，比「覆盖率不是万能的」有力得多。

**片段 5**（`docs/postmortem/0001-...md:110-111`，两条能直接照做的教训）：

> - A namespace plugin and a default export are mutually exclusive under the cordis Loader. Pick the namespace form (`name`/`inject`/`Config`/`apply`) and do not add `export default` — `unwrapExports` will discard the namespace.
> - For a service a plugin reads opportunistically but does NOT declare in `static inject`, use `ctx.get(name)`, never `ctx.<name>`.

说明：`export default` 与命名空间插件互斥——外部插件作者也会踩，且报错是 `cannot get property "x" without inject`，看不出与 export 有关。

**片段 6**（根 `AGENTS.md:107`，不变式的准入判据）：

> - **Runtime invariants assert owned relationships.** Publish `./invariant` only when independent observations can diverge. Otherwise omit its source and wiring and record why in its README; empty installers and checks of service presence, plugin metadata, effects, or fixed examples are invalid ([package invariant rules](packages/AGENTS.md)).

说明：「检查服务存不存在」是**无效**的不变式——这条把「我以为在自检」和「真的有自检」分开了。

**片段 7**（`docs/defensive-patterns.md:9`，正交结果要分开报）：

> A result can be several things at once — a process can time out AND exit 0 because it trapped the signal. Surface each independent fact (`timedOut`, `signal`, `exitCode`) on its own; never nest one flag's report inside another's branch, or a caller reads a cut-short run as a clean success.

说明：一个具体到字段名的模式，可以直接拿来 review 自己的工具返回值。

**片段 8**（`CONTRIBUTING.md:9`，必须面对的现实）：

> DeepSeek Harness is still at an early stage and under active development. We are sorry that we cannot accept external pull requests at the moment.

说明：这篇的标题与现状的冲突点。正文应当把它变成「先按仓库的规矩在 fork 里改，能不能合并由上游决定」，并把「贡献生态」的三条替代路径（GitHub Discussions 报问题、给项目打 `dsh-plugin` topic、写博客）当出口。

## 4. 实际流程

### 4.1 一次真实改动的轨迹（以「加一个 workspace 包」为模板）

依据：`docs/cookbook/adding-a-package.md` 的五步 + `.agents/skills/dsh-pre-push-checks/SKILL.md` 的选证据流程 + `docs/development.md` 的钩子说明。

1. **先读地图**：`docs/architecture.md` → `Where new behavior goes`（`:133`）确认这件事该挂在哪；`docs/capability-seams.md:6` 确认是否已有 seam 承接。规则「新行为挂文档化扩展点」（根 `AGENTS.md:112`）在这一步兑现。
2. **写 Agent Note**：非平凡改动必须在**同一个 PR** 里加/更新至少一条 Agent Note（`docs/AGENTS.md:39`；`.agents/notes/README.md:46`）。路径按 `{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`（`.agents/notes/README.md:9`），class 从闭集里选（`scripts/agent-note-tree.ts:20`）。
3. **建包**：按 `docs/cookbook/adding-a-package.md:7-27` 落 4 个文件；package.json 的字段契约照 `:25`；`files` 只列白名单。
4. **注册**：按 `:31-36` 的表加进 `tsconfig.host.json` 或 `tsconfig.client.json` 的 `references`，**不许两个都进**（`api/remotes` 是仓库特例，新包不许照抄）。
5. **写契约**：`README.md` 的 Model Experience 区块与 `Known Limitations and Deferred Work` 章节是被门禁校验的（`:106`；`run-gates.ts:752-753`、`:767` 三条 verify）。
6. **选证据**：`pnpm --silent run change-scope --base <verified-base-ref>`（`dsh-pre-push-checks:19-25`）列出改动范围，再按 `SKILL.md:33-40` 的对应表选最小证据集；文档改动 → `doc-sync`；manifest/导出/构建路径 → `build` + hygiene + built 冒烟；真供应商行为 → `test:e2e`。
7. **跑验证**（`docs/cookbook/adding-a-package.md:110-115`）：
    ```sh
    pnpm install
    pnpm run doc-sync
    pnpm run constraints && pnpm run typecheck && pnpm run lint
    pnpm run build && pnpm run hygiene
    ```
8. **提交与推送**：pre-commit 只修暂存区 lint、查空白、必要时重生成 `THIRD_PARTY_NOTICES.md`；pre-push 只跑增量 typecheck（`docs/development.md:119-121`）。`SKILL.md:42` 明确要求**不要**为了「反正要推了」再手动重跑一次 typecheck。
9. **改写历史只允许 lease 形式**（`SKILL.md:73`）：`--force-with-lease=<branch>:<observed-oid>`；原生 `--force` 从不允许。
10. **CI 与栈**：栈式 PR 用 `gh stack rebase` / `gh stack push`；`gh stack sync` 会先发布后校验，必须紧接着按 `SKILL.md:79-86` 的 post-sync 序列补验证，未通过前不许合并。评审回应走 `docs/cookbook/responding-to-pr-review-on-a-stack.md`（`:7` 地面规则、`:15` 通过栈解析评论、`:27` 验证）。

### 4.2 文档改动的轨迹（双语 + 生成物）

1. 改英文源（或中文侧）——`docs/AGENTS.md:38` 要求写当前状态。
2. **同一 PR** 里按 `terminology.md` 一次翻译到位（`docs/i18n/README.md:38`、`:61`）。
3. `pnpm run verify-translation-pairing --write <pair>` 重新记录 blob 哈希；这条 yaml diff 就是「确认一致」的可评审动作（`docs/i18n/README.md:18`）。
4. 若改的是**生成型**文档（`module-graph`、`tool-catalog`、`config-catalog`、`persistence-catalog`、`cordis-api/*`、`capability-seams`、`event-producer-consumer`）：**改源码或生成器**，然后跑对应 `gen-*`，再跑 `verify-*`（即 `--check`）。手改生成的英文源会被下一次 verify 判过期。
5. 若改了被 `type-equiv` 跟踪的粘贴块：同改 `scripts/type-equiv.manifest.json`（`docs/AGENTS.md:41`）。
6. 若字数超了：按 `docs/AGENTS.md:53-55` 顺序处理——先「搬家到该去的层级」，再「压缩」，最后才是抬上限，且抬之前要在 PR 里论证。

## 5. 失败模式与坑

### 5.1 逐字门禁文案

**字数超限**（`scripts/verify-doc-budgets.ts:42`，逐字）：

```text
${path}: ${words} words exceeds the ${ceiling}-word ceiling — relocate or condense per docs/AGENTS.md (raising the ceiling requires justification in the PR)
```

同文件 `:30`、`:36` 是另两种：`${path}: ceiling must be a positive integer, got ${ceiling}`、`${path}: budgeted file does not exist (renamed or deleted? update scripts/doc-budgets.manifest.json in the same change)`；失败时的头尾在 `:52-54`：

```text
verify-doc-budgets failed:

See docs/AGENTS.md for the documentation standard and the relocation-first rule.
```

**段落被硬换行**（`scripts/verify-md-wrap.ts:82`，逐字）：

```text
verify-md-wrap: hard-wrapped prose paragraphs found (write one physical line per paragraph):
```

**生成物过期**，每个生成器一套文案，逐字举例：

```text
gen-module-graph: stale — ${stale.join(', ')}. Run `pnpm run gen-module-graph` and commit the result.
gen-config-catalog: ${OUT} is stale. Run `pnpm run gen-config-catalog` and commit ${OUT}.
gen-tool-catalog: ${OUT} is stale. Run `pnpm run gen-tool-catalog` and commit ${OUT}.
gen-session-format-catalog: ${OUT} is stale; run pnpm run gen-session-format-catalog
gen-client-catalog: stale — ${OUT}. Run `pnpm run gen-client-catalog` and commit the result.
```

依据分别是 `scripts/gen-module-graph.ts:169`、`scripts/gen-config-catalog.ts:870`、`scripts/gen-tool-catalog.ts:791`、`scripts/gen-session-format-catalog.ts:242`、`scripts/gen-client-catalog.ts:547`。注意格式**不统一**——不要记「固定后缀」，记「跑它提示的那条 `gen-*`」。

**Loader 元数据里的 `!!js`**（`scripts/verify-cordis-config.ts:509`、`:521`，逐字）：

```text
${expressionPath}: !!js is not interpolated here
```

**包版本不一致**（第 20 篇已引，这里只作为「门禁族里的另一条」）：`package.json version must match root version`（见 [[20-DSH 升级后的版本与兼容性排查]]）。

### 5.2 常见误用

1. **以为门禁清单在文档里。** `docs/development.md:131`、`:137` 都明说权威是 `scripts/run-gates.ts` 与 `package.json`——文档只给摘要，且会漂。
2. **手改生成型文档。** `docs/graph-atlas.md:1-2`、`docs/module-graph.md:1-2`、`docs/capability-seams.md:1-2`、`docs/event-producer-consumer.md:1-2` 全都带「do not edit by hand」。改法只有一个：改源码/生成器再跑 `gen-*`。
3. **只改英文侧。** 配对门禁会红；生成型英文源例外（它本身不许加语言切换行，`docs/i18n/README.md:21`、`:46`）。
4. **给被排除的文件加 `.zh.md`。** `docs/i18n/README.md:48` 明说门禁**拒绝**被排除文件的 `.zh.md` 或 `.i18n.yaml`。
5. **以为 `verify-*` 都是手写脚本。** 多数是 `gen-* --check`（`package.json:158/160/162/168`）；找「谁负责这个文件」应当去找生成器。
6. **把「服务存在性检查」当不变式。** 根 `AGENTS.md:107` 判定为无效；`verify-package-invariants` 会拒。
7. **手工 `ctx.plugin(...)` 就以为测过加载路径了。** `docs/testing.md:39`、postmortem `0001:93`：`unwrapExports` 只有 Loader 调。
8. **在 pre-push 之后又手动跑一遍 typecheck。** `SKILL.md:42` 明确叫停。
9. **看到 `gh pr checks` 报「no checks reported」就怀疑推送丢了。** `SKILL.md:120-126`：PR 处于 `CONFLICTING`/`DIRTY` 时 GitHub 根本不创建 `pull_request` workflow；解决冲突是唯一修法，空提交/`--allow-empty`/draft 来回切都无效。
10. **文档自述与清单不一致时以为文档是对的。** 实测：`docs/AGENTS.md:57` 写 `testing.md` 上限 **1,300**，而门禁读的 `scripts/doc-budgets.manifest.json` 里是 **1350**（`:1-10`）。**权威是清单**（门禁读它），文档这段已经漂了。这条本身就是一个很好的「为什么要一处一个事实」的例子。

## 6. 适用的读者范围

**这篇面向**：

- 想在 fork 里改 DSH 内核或内置包、并希望改动「一次就能过门禁」的人。
- 想知道「我改的这个文件会牵动哪些生成物 / 文档 / 快照」的人。

**对「只写仓库外插件」的读者，以下内容其实用不上，正文要如实说**：

- **栈式 PR 与评审流程**（`docs/cookbook/responding-to-pr-review-on-a-stack.md`、`dsh-pre-push-checks` 里的 `gh stack *`、force-with-lease 部分）：只在给这个仓库提 PR 时才有意义；而 `CONTRIBUTING.md:9` 说目前不收外部 PR。
- **`docs/cookbook/maintaining-dsh-code-review.md` 整篇**：它描述的是**一个指定维护者**在本机跑私有工具维护 `dsh-code-review` skill 的流程（`:5`、`:17`、`:64`「工具源码、评审适配器、凭据、调度器按设计都在仓库之外」）。外部读者既拿不到工具也不需要这套流程。
- **i18n 全流程**：外部插件不需要 `.zh.md`/`.i18n.yaml` 三件套；只有当你给这个仓库改文档时才必须走。
- **字数预算、`type-equiv` manifest、`verify-package-invariants`、`verify-cordis-config`**：都是**仓库内**门禁，对树外包没有任何约束力。
- **`docs/AGENTS.md` 的层级分类表**：读它是为了「知道该去哪一页找答案」，不是让你照它组织自己的文档。

## 7. demo 设计建议

### 7.1 结论先行：不要复用 `tool-cordis`

`code/dsh_plugin/dsh-self-cordis/` 已经存在，做的正是「把 `dsh-tool-cordis` + `dsh-cordis-host-runner` 插进 profile」，而且它是 [[19-运行期动态挂载插件]] 的配套 demo。36 篇再用同一条路会撞车。

**另一个必须绕开的坑**：`@deepseek-ai/dsh-tool-cordis` 的 `exports` 只有 `.`、`./src/*`、`./package.json`（`local/deepseek-harness/packages/extensions/tool-cordis/package.json`），而 `files` 只发 `lib/index.js` 与 `lib/types/**/*.d.ts`——**源码不进包**。它导出的 API 目录数据（`SERVICE_API` / `EVENT_API`，见 `packages/extensions/tool-cordis/src/api-catalog.ts:83`、`:3020`）**不能**被树外插件按子路径 import。**未验证**：从 npm 装的这个包里 `./src/*` 是否可解析，但按 `files` 判断应当不能。

### 7.2 demo：`dsh-kernel-map`

**核心代码骨架**（`src/index.ts`，约 95 行；4 空格缩进 / 单引号 / 无分号 / 中文 JSDoc）：

```ts
/**
 * 把 DSH 生成的事件地图读成可查询的服务面：
 * 解析 docs/event-producer-consumer.md，注册一个只读工具，再挂一条 HTTP 报告。
 *
 * @module dsh-kernel-map
 */
import { readFileSync } from 'node:fs'
import { join } from 'node:path'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'dsh-kernel-map'
export const inject = ['tools']

/** 可配置项。 */
export interface Config {
    /** DSH 检出目录，默认取进程工作目录。 */
    repoRoot: string
}

/** 事件矩阵里的一行。 */
interface EventRow {
    /** 事件名，例如 agent/pre-step。 */
    name: string
    /** 分发模式：emit / bail / serial / waterfall / parallel。 */
    mode: string
    /** 声明处的源码指针，例如 packages/core/agent/src/runtime-types.ts:330。 */
    declaredIn: string
}

/**
 * 解析 gen-doc-graphs.ts 生成的事件矩阵。
 *
 * @param markdown - docs/event-producer-consumer.md 的正文。
 * @returns 逐行解析出的事件；表头与不合形状的行跳过。
 */
function parseEventMatrix(markdown: string): EventRow[] {
    const rows: EventRow[] = []
    for (const line of markdown.split('\n')) {
        const cells = line.split('|').map(cell => cell.trim())
        const name = cells[1]?.match(/^`([^`]+)`$/)?.[1]
        const mode = cells[2]?.match(/^`([^`]+)`$/)?.[1]
        const declaredIn = cells[3]?.match(/`([^`]+)`/)?.[1]
        if (name !== undefined && mode !== undefined && declaredIn !== undefined) {
            rows.push({ name, mode, declaredIn })
        }
    }
    return rows
}

/**
 * @param ctx - 插件上下文。
 * @param config - 已校验的配置。
 */
export function apply(ctx: Context, config: Config): void {
    const matrixPath = join(config.repoRoot, 'docs/event-producer-consumer.md')
    const rows = parseEventMatrix(readFileSync(matrixPath, 'utf8'))
    const byMode: Record<string, number> = {}
    for (const row of rows) byMode[row.mode] = (byMode[row.mode] ?? 0) + 1

    ctx.tools.register(defineTool({
        name: 'kernel_event_map',
        description: '查询 DSH 事件地图：按分发模式或名字片段列出事件。数据来自仓库的生成文档，不靠记忆。',
        parameters: {
            mode: { type: 'string', description: '只看这一种分发模式，例如 waterfall。' },
            filter: { type: 'string', description: '事件名包含这个子串。' },
            limit: { type: 'integer', description: '最多返回多少条，默认 10。' },
        },
        output: {
            schema: {
                type: 'object',
                additionalProperties: false,
                properties: {
                    hits: {
                        type: 'array',
                        required: true,
                        items: {
                            type: 'object',
                            additionalProperties: false,
                            properties: {
                                name: { type: 'string', required: true },
                                mode: { type: 'string', required: true },
                                declaredIn: { type: 'string', required: true },
                            },
                        },
                    },
                    total: { type: 'integer', required: true },
                },
            },
            render: (_args, value) => [{
                type: 'text',
                text: `${value.total} 条命中\n`
                    + value.hits.map(hit => `${hit.name}  [${hit.mode}]  ${hit.declaredIn}`).join('\n'),
            }],
        },
        isConcurrencySafe: () => true,
        execute(args) {
            const hit = rows.filter(row => (args.mode === undefined || row.mode === args.mode)
                && (args.filter === undefined || row.name.includes(args.filter)))
            return { hits: hit.slice(0, args.limit ?? 10), total: hit.length }
        },
    }))

    // connection 是可选的：headless 装配下没有它，插件照常加载，只是没有报告面。
    ctx.inject(['connection'], (connCtx) => {
        connCtx.connection.fetch.register({
            path: '/api/dsh-kernel-map/report',
            methods: ['GET'],
            requestBody: 'buffered',
            fetch: async () => new Response(JSON.stringify({
                total: rows.length,
                byMode,
                source: matrixPath,
            }), { headers: { 'content-type': 'application/json; charset=utf-8' } }),
        })
    })

    console.log(`[${name}] 读入 ${rows.length} 条事件，来源 ${matrixPath}`)
}
```

`report` 会给出总事件数、按分发模式的分组计数、以及数据来源路径——这就是「内核的事件地图长什么样、它是怎么来的」的答案。**未验证**：`rows.length` 的具体数值、按 mode 分组的具体结果、`/api` 路由前缀是否与 `dsh-upgrade-guard` 完全一致（`dsh-upgrade-guard/src/index.ts` 用的是 `connCtx.connection.fetch.register({ path: '/api/dsh-upgrade-guard/report', ... })`，本 demo 照抄该形状）。

**为什么这个 demo 讲得清**：

- 它把「读懂内核」从口号变成一条可验证命令：地图是**机械生成**的，插件只是消费者。
- 它天然演示 `docs/AGENTS.md:66-67` 那条 slop 规则：**手抄目录会烂，读生成物不会**。
- 它踩在读者已经会的东西上（Config schema、`ctx.inject`、`defineTool`、`connection.fetch.register`），新知识只有一条：**生成文档是机器可依赖的接口**。
- 它和「提 PR」这件事直接相关：改内核时你最先动的是这张地图涉及的源码，改完 `pnpm run gen-doc-graphs` 会让它重排——插件立刻能看出差异。
