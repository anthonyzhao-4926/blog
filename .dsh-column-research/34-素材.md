## 1. 机制说明

### 1.1 为什么不能拿一次性 subprocess 代替长驻终端

`dsh-subprocess` 一次 spawn 一个进程、拿到退出码就结束（第 33 篇讲的那条路）。它丢掉的正是交互式终端最要紧的东西：**cwd、导出的环境变量、shell 函数、以及还活着的前台子进程**。包组 README 把适用情形写得很直白：`stepping a debugger, exploring in a Python or Node REPL, or returning to a shell after interrupting a foreground command`（`packages/terminal/terminal-bash/README.md:32`），并明确「一次性 bash 工具用于该在一次调用里开始并结束的有界命令」（同文件）。

还有一条硬差别：**终端是「一次发送、多次读」的**。一次性 subprocess 的结果就是它的全部输出；PTY 会话保留 scrollback，可以被反复翻页（`TerminalReadRequest` / `TerminalReadResult`，`packages/terminal/terminal/src/types.ts:104-123`）。

反过来也有代价，必须诚实写出来：`Sessions remain local to one harness process and do not survive a restart.`（`packages/terminal/README.md:12`）、`Sessions do not survive process exit`（`packages/terminal/terminal-bash/README.md:169`）、`PTY 状态与原始字节仍局限在进程内`（`docs/subsystems/terminal.zh.md:91`）。

### 1.2 角色分工：谁定义、谁提供、谁消费

| --- | --- | --- | --- |

| Service Provider（后端） | `packages/terminal/terminal-bash/` | 注册到 `ctx.terminals` | `packages/terminal/terminal-bash/src/index.ts:225`（`ctx.terminals.registerBackend(...)`），类 `:174` |
| Consumer（模型面） | `packages/terminal/tool-terminal/` | 注册到 `ctx.tools` | `packages/terminal/tool-terminal/src/index.ts:27`（`inject = ['terminals','tools','systemPrompt']`） |

**这是本篇最重要的搭桥点**：读者已经会第 08 篇的「服务定义 / 提供方 / 消费者三件套」。terminal 就是那个三件套的另一份实例，而且替换后端**不会**改变模型请求——`TerminalBackend` 的 JSDoc 原话是 `Replaceable provider for one PTY session type.`（`packages/terminal/terminal/src/types.ts:165`）。

### 1.3 会话的生命周期与所有权

一次会话要经过五个阶段，每一个都有确切的代码位置：

1. **报名（注册后端）**：`registerBackend(backend)` 检查 type 非空、不重复，然后**走 `ctx.effect` 注册**，返回的 disposer 精确摘掉这一份贡献（`packages/terminal/terminal/src/index.ts:125-137`）。
2. **铸造身份**：id 由**服务**铸造，形如 `pty-${++this.nextId}`（`:166`），类型是 branded 的 `TerminalSessionId`（`src/types.ts:11`，铸造函数 `src/index.ts:78-80`）。名称只是**拥有者本地的显示元数据**（`packages/terminal/terminal/src/types.ts:46-48`；`docs/subsystems/terminal.zh.md:9`）。
3. **未发布的创建**：`spawn()` 先向后端要一个 session，**成功并且拥有者仍然活着时才开始发布**（`sessions.set(...)` 在 `:194`）。发布前失败就回滚（`:201-208`），后端自己清理失败则抛 `TerminalBackendCleanupError`（`src/types.ts:18-26`，提示语 `PTY backend startup and cleanup both failed` 在 `:23`）。
4. **授权**：每个操作都先 `expectOwned(owner, id)`，比对的是**确切的那个 Agent 对象**，不是 id、不是名字（`:387-392`）。归属校验失败的两种码是 `NO_SESSION` / `FOREIGN_SESSION`（`:55-63`）。
5. **清理**：`kill()` 只在后端真正安静下来之后才把会话从表里删掉（`:285-301`）；同时有一条挂在**拥有者 ctx 上的清理**（`ensureOwnerCleanup`，`:322-333`），所以 agent 消失时会话不会漏；服务整体销毁时 `disposeAll()` 是 best-effort 且**先清表、再跑 owner cleanup**，保证一个卡住的会话不能连累其它（`:435-454`）。

另外有一个反直觉的设计：**服务会不会话的所有权，而不是终端状态的所有权**。`docs/subsystems/terminal.zh.md:27` 与 `:91`：后端拥有终端状态并负责让资源停稳；服务只负责 id、发布、授权与等待完成的清理。

### 1.4 就绪判定：一次发送什么时候算「完了」

这是这篇最值钱的一节。一次 `terminal_send` 等待的结束原因只有四种，类型定义在 `packages/terminal/terminal/src/types.ts:29`：

```
'stdin_read' | 'inferred_idle' | 'timeout' | 'session_exit'
```

语义边界（`docs/subsystems/terminal.zh.md:11` 的原话）：**wait reason 与 session status 是两件事**。一次发送可以因「静默」或「超时」返回，而顶层 shell 还活着；`session_exit` 表示**顶层 shell 退出了**，不代表某个前台子进程退出了。

后端真正怎么判定（`packages/terminal/terminal-bash/src/session.ts:472-523`，`pollReadiness`），按顺序：

1. **顶层进程已退出** → `session_exit`（`:476-479`）。
2. **受控提示符 + 提示符文本 + 静默达到一个 poll + 前台进程组就是 shell 自己** → `stdin_read`（`:492-496`）。
3. **Linux 上的精确探针**：`elapsed >= exactProbeAfterMs` 且前台进程组「可证明地在等 stdin」→ `stdin_read`（`:501-504`；`acceptsStdinWait` 的判定在 `:143-150`，它专门把「写入之前就存在的那个等待」排除掉）。
4. **静默兜底**：`idleFor >= idleSilenceMs + handoffGrace` → `inferred_idle`（`:509-512`）。`handoffGrace` 只在见过提示符时才有，注释解释了原因：前台子进程会继承 `PROMPT_COMMAND`，所以不能在等 shell 拿回前台时只靠标记（`:505-508`）。
5. **绝对上限**：`setTimeout(..., this.config.timeoutMs)` 在 `startSend` 里就挂上了（`:277-283`）。

提示符不是猜的，是**受控提示符**：后端给 bash 注入 `PS1 = 'dsh> '`（`packages/terminal/terminal-bash/src/sanitize.ts:9` 的 `CONTROLLED_PROMPT`），并让 `PROMPT_COMMAND` 在每次提示前发一个 OSC 标记 `133;D;`（`sanitize.ts:6` 的 `PROMPT_MARKER_PREFIX`；环境拼装在 `src/index.ts:80-88`）。流的解析器是 `TerminalSanitizer`（`sanitize.ts:24`），它同时承担去掉 CSI/OSC 转义序列的活。

可调项与默认值（`packages/terminal/terminal-bash/src/config.ts:84-100`）：

| 字段 | 默认 | 作用 |
| --- | --- | --- |
| `pollIntervalMs` | 50 | 就绪轮询间隔 |
| `exactProbeAfterMs` | 150 | 开始做精确探针的延迟（`src/config.ts:31` 注释：Linux 专属） |
| `idleSilenceMs` | 3000 | 静默多久判 `inferred_idle` |
| `handoffGraceMs` | 500 | 见过提示符后额外等 shell 拿回前台的宽限 |
| `timeoutMs` | 30000 | 一次发送的绝对上限 |
| `disposeGraceMs` | 3000 | 拆除升级到 `SIGKILL` 前的宽限 |

还有一条**加载期校验**（不是运行时才发现）：`handoffGraceMs` 必须 ≥ `pollIntervalMs`，理由是「宽限窗口里至少得跑一次就绪轮询」（`src/config.ts:119-121`）。

### 1.5 为什么读取要有界，以及「两个界」

终端输出的量级不可控（一条 `yes`、一个构建日志）。DSH 用三层布防，缺一层都会被真实使用打穿：

1. **单次发送的结果**是有界的：`LocalSendOperation` 内的 `BoundedTextBuffer(maxBytes)`（`session.ts:82-98`），结算时把它快照成 `viewport`（`:116-126`），并置 `truncated`（`:124`）。
2. **保留的 scrollback** 是有界的：`BoundedTextBuffer(config.scrollbackMaxBytes, config.scrollbackLines)`（`session.ts:220`），超行先丢最老的、超字节再按 UTF-8 尾部截（`BoundedTextBuffer.append` 在 `:54-67`，`utf8Tail` 在 `:31-43`）。
3. **每次读** 也是有界的：`read()` 默认 `count = 500`，真正生效的是 `utf8Tail(requested, this.config.maxReadBytes)`（`session.ts:352-375`，截断点 `:366`）。

默认值：`maxReadBytes` 262144、`scrollbackLines` 10000、`scrollbackMaxBytes` 4 MiB（`src/config.ts:91-93`），并且有一条组合约束：**`maxReadBytes` 不得超过 `scrollbackMaxBytes`**（`src/config.ts:116-118`）。工具的产出口径另有上限：`tool-terminal` 的 `maxResultBytes` 默认 256 KiB，最小 64（`packages/terminal/tool-terminal/src/index.ts:30-32`、`:43-46`）。

分页语义是「相对最新一行」：`offset` 是从最新往回的偏移量，`lineBegin` / `lineEnd` 是同一坐标系下的半开区间（`src/types.ts:103-123`），实现见 `session.ts:352-375`。

### 1.6 并发：一次发送独占，但读和信号不排队

- 服务层不允许同一会话有两个进行中的发送：`PTY session ${id} already has an active send`（`src/index.ts:246`，码 `SEND_ACTIVE`）；后端再兜一层（`session.ts:254-261`，带 `or draining provider write` / `or draining foreground interrupt` 后缀）。
- `read()` 与 `signal()` 不排队，直接打到后端会话上（`src/index.ts:263-276`）。
- 取消不是「写 `\x03`」，而是**对当前前台进程组发真 `SIGINT`**：`interruptOnce` 在 `session.ts:670-687`，README 也点明了 `it never emulates interruption by writing \x03`（`packages/terminal/terminal-bash/README.md:103`）。
- 后台发送不是终端自己的能力，而是 `tool-terminal` 把 send operation 注册进 `ctx.jobs`（`packages/terminal/tool-terminal/src/index.ts:250-275`，job kind `pty-send` 在 `:18-22`）。

### 1.7 tmux-context：它到底做什么

一句话：**在每一轮的第一步，如果模型进程真的跑在某个 tmux pane 里，就往会话里追加一条带来源标记的位置消息**。

- 形态：一个 `agent/pre-step` 的 **waterfall 监听器，且 `prepend: true`**（`packages/context/tmux-context/src/index.ts:236-264`，`{ prepend: true }` 在 `:264`）。
- 门槛：只在 `step === 1`、`decision.kind !== 'reject'`、未被取消时执行（`:241`）。
- 抓什么：8 个 tab 分隔的 tmux 格式字段（`TMUX_FIELDS`，`:51-60`）：session 名、window 序号与名字、pane 序号与 id、两个 active 标志、`window_layout`。
- **怎么确认「真的在 tmux 里」**：拿 pane 的 `#{pane_tty}` 和**本进程的控制终端**（`ps -o tty=`）比对，不匹配就什么都不注入（命令拼装在 `:116-123`；理由在 `:88-96`——VS Code 集成终端会继承 `$TMUX`/`$TMUX_PANE`，变量在但 pane 不在）。
- **变更抑制**：把「上一次注入的稳定状态块」存在 session projection 里（`ctx.sessionProjections.register` 在 `:219-234`，state key `tmuxContext`），渲染后的状态没变就不重复注入（`:251-252`）；可选 `refreshIntervalMs` 再加一个时间下限（`:245-248`）。
- 注入内容长这样（`renderReading`，`:173-175`；README 的样例在 `packages/context/tmux-context/README.md:106-110`）：

```markdown
tmux location (turn <turn>):
session <session>, window <index> "<name>", pane <index> <pane-id>
window active=<0|1>, pane active=<0|1>, layout <window-layout>
```

- **失败一律是 no-op**：没有 `ctx.shell`、不在 pane 里、字段数不对、pane id 为空、非零退出，全部直接返回原 decision（`:242-250`、`:132-146`）；只有**执行器本身 reject** 才记一条 warning 后继续（`:127-131`）。

配置只有一个字段：`refreshIntervalMs`（`Config` 在 `:36-44`），并有一条加载期校验 `tmux-context: refreshIntervalMs must be a non-negative safe integer, got ${...}`（`:189-191`）。README 明确它是 opt-in：`This package is opt-in and is not included in the shipped Web or headless profiles.`（`packages/context/tmux-context/README.md:12`）。

**与 terminal 的关系：没有关系。** 它不读 `ctx.terminals`，只通过 `ctx.shell` 跑两条只读命令。正文要把这点说破，否则读者会以为它是终端功能的附属品。

### 1.8 LSP：四种操作分别解决什么问题

`packages/lsp/lsp/src/types.ts:17` 的闭合联合就是全部：

| 操作 | 映射到的 LSP 请求 | 解决什么问题 |
| --- | --- | --- |
| `goToDefinition` | `textDocument/definition`（`packages/lsp/lsp-stdio/src/translate.ts:34`） | 「这个名字定义在哪」——文本搜索在重名时给不出唯一答案 |
| `findReferences` | `textDocument/references`（同处 `:35`） | 「改它会影响谁」——**永远包含声明本身**，因为 host 固定发 `context: { includeDeclaration: true }`（`packages/lsp/lsp-stdio/src/instance.ts:196-198`），调用方**没有**对应 flag（`types.ts:92-93`） |
| `goToImplementation` | `textDocument/implementation`（`:36`） | 「接口的实现是谁」——文本搜索找不到这层关系 |
| `hover` | `textDocument/hover`（`:37`） | 「这个符号的类型/文档是什么」，不改变光标位置 |

结果只有两个分支（`types.ts:85-87`）：三个导航操作归一化成 `{ kind: 'locations', locations, resolvedWorkspaceUri }`，`hover` 归一化成 `{ kind: 'hover', hover: LspHover | null }`。闭合联合的用意写在 `types.ts:75-84`：消费方 `switch` 到穷尽，新增分支会编译失败。

**坐标系**：seam 与协议一致，是**从 0 开始的 UTF-16**（`types.ts:19-31`）；面向模型的工具用**从 1 开始**的光标，并在输入输出两侧转换（`packages/lsp/tool-lsp/src/render.ts:56-57`、`:97-98`）。`findReferences always includes the declaration` 也直接写进了给模型的提示词（`packages/lsp/tool-lsp/src/index.ts:54`）。

### 1.9 LSP provider 要满足什么契约

```ts
// packages/lsp/lsp/src/types.ts:95-107（节选，逐字）
interface LspProvider {
  readonly id: LspProviderId
  readonly extensionToLanguage: Readonly<Record<string, string>>
  query(request: LspProviderQuery, signal?: AbortSignal): Promise<LspQueryResult>
}
```

- **`id`** 是 branded 的（`packages/lsp/lsp/src/brand.ts` 通过 `LspProviderId(...)` 铸造），注册时**原子预留**：id 与每一个扩展名一起校验、一起预留，任何冲突都不发布任何东西，返回的 disposer 一起释放（`packages/lsp/lsp/src/index.ts:90-141`，注释原话见 `:91-92` 与 `:128-129`）。
- **扩展名映射**必须是「小写、前导点」的键；归一化在 `:153-156`，合法性由 `EXTENSION_PATTERN = /^\.[^./\\]+$/` 把关（`:70`）。一个 provider 内部重复（`.TS` 与 `.ts`）也算错（`:117-119`）。
- **选择是按扩展名、每次查询独立、与注册顺序无关**：`routes.get(finalExtension(request.filePath))`（`:144`），`finalExtension` 会把 `foo.d.ts` 归一成 `.ts`、并把 `.bashrc` 这类点文件判成无扩展名（`:60-67`）。
- **`languageId` 不由请求携带**，而是由 seam 从 provider 的映射里派生后再交给 provider（`types.ts:49-57`、`index.ts:148`），且它「只用于同步瞬态文档，从不参与选择」（`docs/subsystems/lsp.zh.md:42`）。
- **seam 刻意不提供逃生口**：没有协议类型、没有进程或文档控制、没有通用 JSON-RPC 通道（`types.ts:5-6`、`packages/lsp/lsp/src/index.ts:10`）。

### 1.10 LSP 的进程生命周期（stdio provider）

- **懒启动、按 (provider, 规范化工作区) 单飞**：`LocalLspProvider.instances` 一个 `Map<WorkspaceKey, LspInstance>`（`packages/lsp/lsp-stdio/src/index.ts:221`），`instanceFor` 在需要时同步发布实例（`:332-339`）。
- **每个工作区一条完整串行队列**（读源 → didOpen → 请求 → didClose 都不交错）：`queues` 在 `:223`，`enqueue` 在 `:318-329`，注释点明「tail 跟随真实的前序工作，即使调用方放弃等待也不会解除串行」（`:321-322`）。
- **查询是「瞬态打开」**：每次都重新通过 `ctx.fs` 读当前字节（`:279`），在队列内、spawn 之前读，理由是「排队查询轮到自己时看到的是当前字节，而非法源不能在池里留下一个空转进程」（`:277-279`）。
- **传输失败只重试一次**，而且是透明的：`:305-312`，判定用 `instance.isTransportFailure(...)`（`packages/lsp/lsp-stdio/src/instance.ts:82-84`，接线到连接保留的致命原因）。
- **拆除**：先 graceful `shutdown`/`exit`，预算 `shutdownTimeoutMs`（默认 5000），然后 `forceTerminate`（`instance.ts:290-320`）。一个已知的坑：`initialize.processId: null` 让服务端不再监控客户端 PID，所以**被 SIGKILL 的 harness 会留下孤儿语言服务器**（`packages/lsp/lsp-stdio/README.md:150`）。
- 工具侧的兜底预算：`tool-lsp` 给工具挂了 `timeoutMs`（默认 60000），由 `dsh-tool-call-timeout-policy` 执行（`packages/lsp/tool-lsp/src/index.ts:50,69,182`）。

### 5.2 fail-closed / fail-soft 分界

| 场景 | 待遇 | 依据 |
| --- | --- | --- |
| 后端重复注册 / 名字冲突 | **fail-closed**，加载即抛，什么都不发布 | `src/index.ts:126-129`、`:337-341` |
| LSP provider 冲突或非法扩展名 | **fail-closed 且原子**：先全量校验，再一次性预留 | `packages/lsp/lsp/src/index.ts:90-141` |
| LSP 配置里有一个坏条目 | **fail-closed 到整张表**：先解析所有可执行文件，再注册任何 provider | `packages/lsp/lsp-stdio/src/index.ts:139-169` |
| 会话创建失败 | **fail-closed + 回滚**：未发布就关掉半成品；清理也失败则用 `TerminalBackendCleanupError` 保留两个原因 | `src/index.ts:196-223`、`src/types.ts:18-26` |
| tmux 查询失败 | **fail-soft**：no-op，只有执行器 reject 才 warn，绝不失败整轮 | `packages/context/tmux-context/src/index.ts:127-132,146,242-250` |
| 沙箱模式切换 | **fail-closed**：有会话或在创建中就直接拒绝，并且拦在事件提交之前 | `packages/terminal/terminal-bash/src/index.ts:51-61` |
| LSP 查询遇到传输故障 | **fail-soft 重试一次**，然后如实抛 | `packages/lsp/lsp-stdio/src/index.ts:305-312` |
| 服务拆除 | **best-effort + 聚合错误**：先清表、跑 owner cleanup，再把聚合错误抛出去 | `src/index.ts:435-454` |

### 5.3 陷阱清单

1. **把 `inferred_idle` 当成「命令跑完了」**。系统提示词专门写了一句防这个（`packages/terminal/tool-terminal/src/index.ts:159`），README 也写了两遍（`packages/terminal/terminal-bash/README.md:64`、`docs/subsystems/terminal.zh.md:11`）。
2. **以为 macOS 也有精确的 stdin 等待证据**。没有：`exactProbeAfterMs` 的 JSDoc 写着 `Delay before Linux exact syscall probes`（`src/config.ts:31`），README 也承认 `Readiness is heuristic without an exact tier`（`packages/terminal/terminal-bash/README.md:166`）。所以在 macOS 上「就绪」更依赖提示符与静默。
3. **以为 `maxReadBytes` 只管读**。它也管发送结算的 viewport（`src/config.ts:27-28` 的 JSDoc）。
4. **把 `pane_id` 当成唯一位置**。tmux 的 reading 会因为「window 改名、pane 被移动、布局变了」重新注入（`packages/context/tmux-context/README.md:77`），但**只有第一步**会读（同文件 `:127`）。
5. **在 tmux 里跑但读到「不在 tmux」**。这是设计如此：`tty` 不匹配就当作不在（`packages/context/tmux-context/README.md:52,131`）。
6. **LSP 只看得到文本匹配时的问题**：提示词明说 `Use search/read for ordinary navigation. Use lsp when textual matches are ambiguous...`（`packages/lsp/tool-lsp/src/index.ts:54`）。
7. **位置传错一位**。模型面是 1-based、seam 是 0-based（`render.ts:56-57`），而**结果回给模型时又 +1**（`render.ts:97-98`）。传 0 会被 `oneBased()` 直接拒（`render.ts:67-71`）。
8. **`file:` URI 不要用宿主的路径规则去相对化**。`locations` 变体专门带 `resolvedWorkspaceUri` 就是为这个（`packages/lsp/lsp/src/types.ts:80-84`），工具里的实现见 `render.ts:138-164`。
9. **同一扩展名不能给两个 provider**（`LSP_CONFLICT`，`index.ts:124`），而**同一个 provider 内部**把 `.TS` 和 `.ts` 都写上也报错（`:117-119`）。
10. **语言服务器本身没有沙箱**：`this package trusts the configured server and does not sandbox its process`（`packages/lsp/lsp-stdio/README.md:147`）。要隔离得靠同一执行世界的 fs/subprocess/sandbox 提供方（`lsp-stdio/README.md:75`）。
11. **硬杀 harness 会留孤儿语言服务器**（`lsp-stdio/README.md:150`），同样的暴力终止也会留下 PTY 子进程——后者的清理保证属于 subprocess provider，不属于这个后端（`packages/terminal/terminal-bash/README.md:168`）。

## 6. 外部插件可行性

结论：**两边的 provider 面都对仓库外插件开放，但路径不一样；终端侧最省事的复用点被包边界挡住了。**

**能做的**

| 能力 | 依据 |
| --- | --- |
| 注册自己的 PTY 后端 | `registerBackend` 是服务上的普通公开方法（`packages/terminal/terminal/src/index.ts:125`），契约 `TerminalBackend` 从包入口导出（`src/types.ts:165-171`）；seam 文档就把它叫「可替换的提供方」 |
| 消费终端能力 | `ctx.terminals` 是公开服务键；`tool-bash-persistent` 就是仓库内的活例（`packages/shell/tool-bash-persistent/src/index.ts:432`） |
| 注册自己的 LSP provider | `registerProvider` 是公开方法（`packages/lsp/lsp/src/index.ts:90`），契约导出（`types.ts:95-107`），`LspProviderId` 由包主入口再导出（`packages/lsp/lsp/src/index.ts:24`）；包 exports 只有 `.`、`./src/*`、`./package.json`，**没有** `./brand` 子路径 |
| 复用 stdio provider 的零件 | `lsp-stdio` 导出 `LspInstance`、`LspConnection`、`canonicalizeWorkspace`、`readHostSource`（`packages/lsp/lsp-stdio/src/index.ts:30-41`）——但要自己写池化、队列、重试 |
| 自己写一个 tmux 式的上下文插件 | 只需要 `inject: ['agents', 'sessionProjections']` 与 `ctx.get('shell')`（`packages/context/tmux-context/src/index.ts:33,242`） |

**卡在哪（要写进正文的实话）**

1. **最强的复用点没导出，而且不是「忘了加 export」那么表面**：`LocalPtySession` 在源码里有 `export`（`packages/terminal/terminal-bash/src/session.ts:161`），但包入口只再导出了 `Config` 与配置类型（`packages/terminal/terminal-bash/src/index.ts:21-22`），**没有**导出这个类。关键在发布边界：这些包的 `files` 只有 `lib/index.js` 与 `lib/types/**/*.d.ts`（`packages/terminal/terminal-bash/package.json` 的 `files`），也就是说 `src/` 根本不随包发布——虽然每个包都声明了 `"./src/*": "./src/*"` 这个 exports 子路径，它在安装后的包里指向**不存在的文件**。结论：仓库外插件拿到的运行时面就等于 `lib/index.js` 里那几个导出，**拿不到**那套已经写好的就绪轮询、有界缓冲、sanitizer——只能自己从 `ctx.subprocess.spawnTerminal`（`SubprocessTerminalHandle`）往上写一遍。同理 `LocalLspProvider` 没有 `export`（`packages/lsp/lsp-stdio/src/index.ts:217`），而 `LspInstance` / `LspConnection` / `canonicalizeWorkspace` / `readHostSource` 是入口显式导出的（`:30-41`），所以 stdio 那条路**部分**可用。
   → **demo 建议据此避开「从零写后端」**（见第 7 节）。
2. **`dsh-tool-terminal` 与整个 `lsp` 家族在已装 dsh 里根本不存在**（见第 0 节表）。要用它们，profile 必须能装到这些包；这属于「部署前提」，不是「代码能不能写」。
3. **需要同世界的 fs / subprocess / sandbox 提供方**：`lsp-stdio` 要求 `fs`、`subprocess` 同世界（`packages/lsp/lsp-stdio/README.md:75`），`terminal-bash` 在受限模式下要求 `ctx.sandbox`，否则创建时直接抛（`packages/terminal/terminal-bash/src/index.ts:103-106`）。
4. **未验证**：外部插件包只声明 `peerDependencies: { '@deepseek-ai/dsh-terminal': ... }` 时，在 `autoInstallPeers: false` 的 profile 里（参考卡片 [[dsh 插件开发学习/参考/profile与插件包结构|profile 与插件包结构]] 的 `pnpm-workspace.yaml` 一节）能不能解析到宿主那份服务实例。**要由会跑 dsh 的人实测**；保险做法是把需要 `ctx.terminals` 的包写进 `dependencies`。

## 7. demo 设计建议

**形态**：仓库外插件包，一个包两个插件（与第 09 篇「一个 demo 三个插件」的先例一致），因为这一篇本来就是两件事。

- 包名（目录）：`dsh-nav-kit/`
- 插件名（Loader 行名）：`dsh-term-journal`（消费终端）与 `dsh-md-links`（提供代码导航）
- 演示什么：
  1. `ctx.terminals` 的**消费者契约**——`list` + 有界 `read` + 分页字段，并强制暴露「wait reason ≠ 命令退出」这条事实；顺带演示 `hasOwnerActivity` 的用途（判断自己要不要先等创建落地）。
  2. `ctx.lsp` 的**provider 契约**——一个不依赖任何语言服务器的 provider，把 `[[笔记名]]` 当作符号：`goToDefinition` 找同名笔记文件、`findReferences` 找所有引用它的笔记、`hover` 返回那一行的上下文。它一次就把「四种操作」「扩展名→languageId 映射」「`resolvedWorkspaceUri` 为什么必须由 provider 给」全讲清，而且是这个仓库自己会用得上的能力。

**为什么这个 demo 讲得清**

- 它避开了一个不可能的任务：从零写一个 PTY 会话（就绪轮询 + 有界缓冲 + 转义序列清理，约 400 行，而且 `LocalPtySession` 拿不到），改成**只写消费者**，把 1.4/1.5 的机制用「读」这一侧展示出来——读者写插件时最可能做的也正是这一侧。
- LSP 那一半是**真的只有几十行**：一个 provider 就是 `{ id, extensionToLanguage, query }`，没有进程管理、没有协议帧。
- 两个插件共享同一个「界」的认知：一个读别人的会话（seam 的消费方），一个被别人读（seam 的提供方）。

import { join } from 'node:path'
import type { Context } from '@deepseek-ai/cordis'
import { LspProviderId } from '@deepseek-ai/dsh-lsp'
import type { LspProvider, LspProviderQuery, LspQueryResult } from '@deepseek-ai/dsh-lsp'

/** Cordis 插件名 */
export const name = 'nav-kit-md-links'
/** 只依赖文件系统与 LSP seam */
export const inject = ['lsp', 'fs']

/** 与 package.json 同级声明的 provider id */
const PROVIDER_ID = LspProviderId('dsh-nav-kit/md-links')

/**
 * 定位光标所在行里的 [[...]] 引用。
 * @param text - 整篇笔记文本
 * @param line - 从 0 开始的行号
 * @returns 该行第一个 wiki 链接目标，没有则 undefined
 */
function targetAt(text: string, line: number): string | undefined {
    const row = text.split('\n')[line] ?? ''
    return /\[\[([^\]|#]+)/u.exec(row)?.[1]
}

/** 递归收集工作区里的 markdown 文件。 */
async function collectNotes(dir: string, depth = 4): Promise<string[]> {
    const found: string[] = []
    for (const entry of await readdir(dir, { withFileTypes: true })) {
        if (entry.name.startsWith('.')) continue
        const full = join(dir, entry.name)
        if (entry.isDirectory() && depth > 0) found.push(...await collectNotes(full, depth - 1))
        else if (entry.name.endsWith('.md')) found.push(full)
    }
    return found
}

/**
 * 注册这个提供方。
 * @param ctx - 插件上下文
 */
export function apply(ctx: Context): void {
    const provider: LspProvider = {
        id: PROVIDER_ID,
        extensionToLanguage: { '.md': 'markdown' },
        async query(request: LspProviderQuery): Promise<LspQueryResult> {
            // provider 必须自己把工作区规范化，并把权威 URI 回传给调用方。
            const root = await ctx.fs.resolve(request.workspaceRoot)
            const resolvedWorkspaceUri = ctx.fs.fileUrl(root)
            const source = await ctx.fs.readText(await ctx.fs.resolve(request.filePath, { cwd: request.workspaceRoot }))
            const target = targetAt(source, request.position.line)
            if (request.operation === 'hover') {
                return { kind: 'hover', hover: target === undefined ? null : { contents: `wiki 链接 → ${target}` } }
            }
            if (target === undefined) {
                return { kind: 'locations', locations: [], resolvedWorkspaceUri }
            }
            const notes = await collectNotes(request.workspaceRoot)
            const hits = notes.filter(path => path.split('/').at(-1) === `${target}.md`)
            return {
                kind: 'locations',
                locations: hits.map(path => ({
                    uri: ctx.fs.fileUrl(await ctx.fs.resolve(path)),
                    range: { start: { line: 0, character: 0 }, end: { line: 0, character: 0 } },
                })),
                resolvedWorkspaceUri,
            }
        },
    }
    ctx.lsp.registerProvider(provider)
}

/**
 * 从长驻终端的有界 scrollback 里取一页，并把分页坐标原样交给模型。
 */
import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'
import { defineTool } from '@deepseek-ai/dsh-tools'

/** Cordis 插件名 */
export const name = 'nav-kit-term-journal'
/** 需要终端注册表与工具注册表 */
export const inject = ['terminals', 'tools', 'systemPrompt']

/** 插件配置 */
export interface Config {
    /** 一页最多要多少行；后端仍会按字节再截一次 */
    pageLines?: number
}

/** Schemastery 校验 */
export const Config: z<Config> = z.object({
    pageLines: z.number().default(200),
})

/**
 * 注册 terminal_journal 工具。
 * @param ctx - 插件上下文
 * @param config - 已解析配置
 */
export function apply(ctx: Context, config: Config): void {
    const pageLines = config.pageLines ?? 200
    ctx.systemPrompt.section({
        name: 'tool:terminal-journal',
        order: ctx.systemPrompt.getSectionOrder('TOOL_PTY'),
        text: 'terminal_journal 只读取保留的输出；读到 inferred_idle 或 timeout 不代表前台命令已结束。',
    })
    ctx.tools.register(defineTool({
        name: 'terminal_journal',
        description: '读取某个长驻终端会话保留输出的一页，返回分页坐标。',
        parameters: {
            sessionId: { type: 'string', required: true, description: 'terminal_open 返回的会话 id。' },
            offset: { type: 'number', description: '相对最新一行的偏移，默认 0。' },
        },
        async execute(args, exec) {
            const owner = exec.agent
            if (owner === undefined) throw new Error('terminal_journal 需要一个发起它的 agent')
            const exists = ctx.terminals.list(owner).some(snapshot => String(snapshot.sessionId) === args.sessionId)
            if (!exists) throw new Error(`不认识这个终端会话：${args.sessionId}`)
            const page = ctx.terminals.read(owner, args.sessionId as never, {
                offset: args.offset ?? 0,
                count: pageLines,
            })
            return {
                text: page.text,
                totalLines: page.totalLines,
                lineBegin: page.lineBegin,
                lineEnd: page.lineEnd,
                truncated: page.truncated,
            }
        },
    }))
}

## 8. 与其他篇的交界

**前面已经讲过、本篇不重复**

- **08（替换内置能力的提供方与消费者）**：服务定义 / 提供方 / 消费者三件套、`inject` 与 `ctx.get` 的必需/可选之分、选择失败的四种 code。本篇只用它的词汇，不重讲理论；terminal 与 lsp 的三件套归属直接用一张表带过（1.2 节）。
- **11（为模型注册自定义工具）**：`defineTool`、参数描述、`output.schema`、后台任务。`tool-terminal` / `tool-lsp` 只作为「消费者长什么样」引用，不重讲工具注册。
- **21（文件访问的三层管控）**：沙箱、观察策略、权限预设。本篇只提一处**新的交叉**：终端后端自己有一道「模式切换栅栏」（`packages/terminal/terminal-bash/src/index.ts:37-62`），它拦的是**切换到更宽的模式**，理由是「用更宽访问权开的终端不能活过一次降级」——这是 21 篇没有的一条边界。
- **23（会话上下文的压缩、裁剪与排水）**：投影、上下文提供方、压缩。tmux-context 是「又一个上下文插件」，它的变更抑制正是靠一个 session projection（`packages/context/tmux-context/src/index.ts:219-234`）；只引用，不重讲投影机制。
- **24（会话用量与成本的计量）**：`time-context` 已经讲过一次「请求期注入上下文」的形态。tmux-context 与它同族，本篇只讲**它特殊的那一点**：tty 判定与变更抑制。
- **33（让模型跑代码）**：一次性 `subprocess` 与 code-runtime。本篇开篇第一段就与它划界（1.1 节），不再展开。

**留给别的篇**

- LSP 诊断（diagnostics）怎么进上下文、要不要自己写一个 provider 把编译错误喂给模型——本篇只说明「seam 是闭合的四操作，没有 diagnostics」，具体怎么做留给需要的人。
- `e2b` 远程执行下的终端与 LSP：`packages/e2b/e2b/tests/fixtures/composition/cordis.yml` 就是这两件事在远程世界的组合样例，但那是第 33 篇/后续的话题。
- `isolate`（`ctx.isolate` / realm）的完整语义：只在「出厂预设为什么把 `terminals` 隔离到 entry 局部」这一句里出现（`packages/preset/agent-presets/presets/minimal/agent.cordis.yml:24-25`），机制本身留给真正需要多份能力实例的场景。
- 客户端渲染：终端卡片（`card: 'terminal'`，`packages/terminal/tool-terminal/src/index.ts:289`）的样子属于第 16 篇。

**值得写进正文的 2~4 个反直觉点**

1. **「长驻终端」在读者的机器上大概率不存在。** 出厂只有 `minimal` 预设挂 PTY，跑代码的常用预设（`standard`/`ptc`/`cordis`）一行终端都没有；六个 `terminal_*` 工具与整个 LSP 家族更是连包都没装。这篇真正的第一步是补装配，而不是写代码。
2. **「就绪」不是一个布尔值。** 一次发送有四种返回原因，其中 `inferred_idle` 与 `timeout` 只是「我等到这儿先回去」，前台命令可能还在跑。系统提示词、两份 README 和子系统文档各自独立地强调过同一句话。
3. **有界读取的界有两层，而且第一层不在 `read()` 里。** 发送结算的 `viewport` 与固定 scrollback 都受 `maxReadBytes`/`scrollbackMaxBytes` 约束；`read()` 的 `count` 只是请求，真正生效的是末尾的 UTF-8 字节截断。
4. **LSP 的四种操作里，「找引用」没有开关。** provider 必须内部保证包含声明（host 固定发 `includeDeclaration: true`），调用方拿不到 flag——这是把「一件容易忘的事」从接口上删掉的设计。
5. **坐标系有两次翻转。** 模型给的是 1-based，seam 是 0-based，结果回到模型时再 +1；错一位的表现是「明明有定义却查不到」。
