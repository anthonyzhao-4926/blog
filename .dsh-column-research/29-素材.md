## 1. 机制说明

### 1.1 这篇要解决的事，和前面已经学的怎么接上

读者在 [[11-为模型注册自定义工具]] 里已经做过一件事：调 `ctx.tools.register(defineTool({...}))`，把**自己进程里**的一个函数变成模型可见的工具。

MCP 客户端做的是同一件事的另一个版本：它把**另一台机器 / 另一个进程**上的工具，翻译成同一种 `ToolDefinition`，注册进**同一个注册表**。差别只有三处：

| | 自己写工具（11 篇） | MCP 客户端（本篇） |
| --- | --- | --- |
| 工具从哪来 | 你代码里的函数 | 远端 `tools/list` 的返回值 |
| 名字从哪来 | 你自己起 | 由 `(serverName, rawName)` 确定性推导 |
| 生命周期 | 跟插件一起生老病死 | 会**世代交换**：远端改一次工具列表，注册表整批换一次 |

所以「工具 catalog」不需要新概念——它就是 [[08-替换内置能力的提供方与消费者]] 里那个 `ctx.tools` 服务。**MCP 客户端是这个服务的又一个提供方**，只不过它批量供、且供的是远端能力。

### 1.2 三件套：谁定义、谁提供、谁消费

| 角色 | 是谁 | 服务键 / 位置 |
| --- | --- | --- |
| 服务定义 | `@deepseek-ai/dsh-tools` | `ctx.tools`（`ToolRuntime`） |
| 提供方（本篇主角） | `@deepseek-ai/dsh-mcp-client` | 一个插件实例 = **一台** MCP 服务器；多台 = cordis.yml 里多行。`inject = ['tools']`（`packages/mcp/mcp-client/src/index.ts:32`） |
| 提供方（0.2.0 新增） | `@deepseek-ai/dsh-mcp-resources` | 三个共享资源工具；base 已经挂好，**没有配置字段** |
| 消费者 | 模型（通过工具 catalog）、`@deepseek-ai/dsh-acp`（按会话挂客户端，见 §4.2） | — |

**关键：MCP 客户端不新增任何服务键。** 它只是往 `ctx.tools` 里写。这意味着：
- 想统计「模型问了几次内部系统」，直接听 `session/event` 的 `tool/call`（事件字段见 `packages/core/session/src/types.ts:341`），和 09 篇学的完全一样；
- 想拦「不许查生产库」，用 12 篇学的 `ctx.tools.guard()`，**不需要 MCP 特有的钩子**——因为进注册表之后它就是一个普通工具。

### 1.3 「一台服务器一条配置项」是什么意思

源码模块头一段就说明了（`packages/mcp/mcp-client/src/index.ts:1-14`）：

> Each plugin instance connects to one MCP server; load multiple instances in `cordis.yml` for multiple servers.

所以不存在「一个插件管一堆服务器」。要挂三台，就写三条配置行，`serverName` 各不同。`serverName` 是**本地起的名字**，不是远端报上来的名字——README 把理由写得很直白（`packages/mcp/mcp-client/README.zh.md:106`）：远端 `serverInfo.name` 不可信、跨部署不唯一、升级还会变，所以不允许它悄悄改掉面向模型的工具名。

### 1.4 工具名怎么算出来的

这是一个**纯函数**（`packages/mcp/mcp-client/src/tools.ts:112-118`）：

1. 先拼 `mcp__<serverName>__<rawName>`；
2. 把 `[^A-Za-z0-9_-]` 全换成 `_`；
3. 如果没换过、且长度 ≤ 64，直接用；
4. 否则截断到 `64 - 12 - 1` 再拼 `_` + 12 位十六进制 SHA-256（hash 的输入是 `serverName\0rawName`，也就是身份本身）。

第 4 步是防折叠的：两个不同的 MCP 身份**绝不会**压成同一个模型可见名。README 的说法是「命名是固定约定」（`:107`）。

为什么值得单讲：**这个名字是会话历史和权限规则的锚点**。工具名稳定 ⇒ 昨天的审批规则今天还认得它。

### 1.5 世代交换（最容易写错的地方）

远端可以随时通知「我的工具变了」（`notifications/tools/list_changed`）。客户端处理这件事的方式是**两阶段世代交换**（`packages/mcp/mcp-client/src/tools.ts:120-142` 的文档注释）：

- **阶段一 取**：把所有页 `tools/list` 拉完，先在内存里造好整批 `ToolDefinition`。这一阶段任何失败（网络、重名、重复游标）→ **抛错，上一代原样保留**。
- **阶段二 换**：先 dispose 上一代，再注册新一代。这一阶段失败（注册表冲突）→ **整批回滚**，结果是「要么全有，要么全没有」，绝不给半套。

两阶段的中间是「dispose 旧的」这一步——所以**两次同步绝不能交错**。源码用一条串行队列保证（`packages/mcp/mcp-client/src/connection.ts:161-170`，注释里明说交错会导致「double-dispose one generation and leak another」）。

  const joined = `mcp__${serverName}__${rawName}`
  const normalized = joined.replace(INVALID_NAME_CHARS, '_')

### 5.2 鉴权与安全陷阱

1. **MCP 客户端不接 `credentials` seam。** 头部/环境值就是普通字符串。想让密钥不落明文，只有两条路：`!!js process.env.X`（HTTP header / stdio env）。`docs/user/guide/mcp-memory.zh.md:13` 直接给了纪律：**不要把密钥写进 YAML**。
2. **`--dump-config` 不会泄露 `!!js` 的值。** CLI 参考明说「`!!js` 表达式保持未求值」（`apps/cli/reference/README.zh.md:53`）——所以 dump 出来的是表达式文本，这是好的一面。
3. **但密钥会进子进程环境，且会被模型跑的命令读到。** 显式 `env` 的合并发生在清洗之后（`src/transport.ts:22`），这是设计，不是漏洞；但意味着 `mcp__...` 那台服务器的子进程能看到这把密钥。网络代理那篇把同一个性质讲得更狠：`HTTPS_PROXY` 里的密码「DSH 运行的每一条命令——包括模型编写的那些——都能读到」（`docs/user/guide/network-proxy.zh.md:62`）。
4. **环境清洗删的是「名字像凭据的」。** `TOKEN`/`KEY`/`SECRET`/`PASSWORD` 命中即删，`DSH_*` 全删（`packages/subprocess/subprocess/src/index.ts:45,67`）。所以：把 MCP 令牌放在名为 `LOG_MCP_TOKEN` 的环境变量里、又指望它「自动继承」给 stdio 子进程——**不会**，必须显式写进 `env`。
5. **`cwd` 默认 `''`。** stdio 子进程的工作目录就是 harness 自己的 cwd；把内部系统的本地工具指到一个宽松目录是不必要的暴露面。
6. **HTTP 分支的 `url` 只做 `new URL()`，不做 scheme 白名单。** 对照 ACP 的写法（`assertHttpUrl` 只放 `http:`/`https:`，`packages/acp/acp/src/mcp.ts:125-132`），直接写配置行时没有人帮你挡。
7. **`args` 不过 shell**（README `:61`）。所以 `args: ['-y', '@scope/pkg']` 是安全的；反过来说，想靠 shell 展开 `$HOME` 也是不行的。

### 5.3 并发与生命周期陷阱

1. **两阶段交换必须串行。** `enqueueSync` 把所有同步（初始、通知、重连）串到一条 promise 链（`packages/mcp/mcp-client/src/connection.ts:161-170`）；注释明写交错会「double-dispose one generation and leak another」。
2. **`syncChain` 的尾巴必须吞错。** `syncChain = run.catch(() => {})`（`:168`），否则一次失败会毒掉后面所有同步。
3. **`dispose` 是「请求 + 停稳」，不是「发个信号」。** 它先标记 `disposed`、清重连定时器、关当前 client，再 `await settling` 和 `await syncChain`，最后才注销（`:327-349`）。注释点明理由：在飞的那次尝试会在 settle **之前**把它的同步排进队列（`:343-344`）。
4. **代数关闭有 5 秒硬闸。** `GENERATION_CLOSE_TIMEOUT_MS = 5_000`（`:50`），理由写在 `:47-49`：SDK 的 stdio 传输自己有两个 2 秒宽限期，多留 1 秒证明旧代真的没了；超时**fail-closed**（停止重连）而不是让两个子进程重叠。
5. **重连定时器 `unref()`**（`:224`）——一个挂着的重连定时器不许把进程撑住。
6. **稳定窗口 = `maxDelayMs`。** 连接活过 `maxDelayMs` 才算「这次中断结束、预算归零」（`:201-203`）。所以把 `maxDelayMs` 调很大，等于「crash-loop 的服务器更难被累计到放弃」。
7. **放弃之后唯一的出路是卸载/重启。** `:213` 的文案自己说了。
8. **重连在「传输关闭」时触发**（README `:193`）：stdio 子进程崩了会触发重连；Streamable HTTP 的失败按**请求**由 SDK 自己重试，监督器不会重新 spawn。**这是一个真坑**：HTTP 服务器挂了，你不会看到 `connection lost; reconnecting`，只会在每次调用时失败。
9. **`failOnStartupError: false` 不是「没问题」，是「延后」**：harness 照样起，但那台服务器的工具**不存在**，只有一条 error 日志（README `:70`）。
10. **图片是唯一「持久富结果」。** 音频、嵌入资源、resource link 只以有界文本呈现（README `:194`）。

### 5.4 fail-closed / fail-soft 对照

| 决定 | 取向 | 依据 |
| --- | --- | --- |

**卡在哪：** 不卡在 MCP 客户端，卡在「让你自己写的那层插件进 profile」。如果插件是个纯 bundle，`dsh plugin --profile X add link:.` 就够；如果它要在运行期按 agent 作用域挂客户端，就必须有 `scopeOf(ctx)` 意义上的 agent 作用域可用——在 `test` profile（只有 base）里没有 HTTP/web 层，你只能靠日志验证，不能靠界面。

## 7. demo 设计建议

### 7.1 插件名与演示目标

**`dsh-logs-mcp-kit`** —— 把公司日志系统的 MCP 挂到 DSH，并证明两件读者最容易搞错的事：

1. **一条配置行就能挂**（声明式），以及**程序式**按 agent 作用域挂（ACP 同款）；
2. **失败长什么样**——stdin 里没有那个命令时，日志到底给什么。

│   └── index.ts              # 观察插件：把 mcp__ 前缀的调用记成一行日志

### 7.5 核心代码骨架（`src/index.ts`，约 90 行）

```ts
/**
 * 把 MCP 工具的调用记成一行日志，用于观察「远端工具是否真的进了 catalog」。
 *
 * 只读：不注册工具、不拦调用，只监听会话事件里的工具调用。
 *
 * @module dsh-logs-mcp-kit
 */

import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'
// 副作用类型导入：把 session/event 的载荷类型挂到 Context 上。
import type {} from '@deepseek-ai/dsh-session'

/** Loader 诊断里显示的插件名。 */
export const name = 'mcp-call-observer'

/** 只要会话事件，不注入任何服务，避免在缺服务的组合里停在 PENDING。 */
export const inject = []

/** 观察插件的配置。 */
export interface Config {
    /**
     * 只统计这些 serverName 前缀；空数组表示所有 mcp__ 工具。
     */
    serverNames: string[]
    /** 每个会话最多记多少行，防止刷屏。 */
    maxLines: number
}

export const Config: z<Config> = z.object({
    serverNames: z.array(String).default([]),
    maxLines: z.number().step(1).min(1).default(50),
})

/** 判断一个工具名是否属于我们要观察的 MCP 服务器。 */
function watched(toolName: string, serverNames: string[]): boolean {
    if (!toolName.startsWith('mcp__')) return false
    if (serverNames.length === 0) return true
    return serverNames.some(server => toolName.startsWith(`mcp__${server}__`))
}

/**
 * 订阅会话日志里的 tool/call，把命中的 MCP 调用记一行。
 *
 * @param ctx - 插件上下文，只用到 logger 与事件。
 * @param config - 观察范围与行数上限。
 */
export function apply(ctx: Context, config: Config): void {
    const seen = new Map<string, number>()
    let total = 0

    // 监听本身就是 effect：ctx.on 返回的 disposer 由 Cordis 在卸载时调用。
    ctx.on('session/event', (session, event) => {
        if (event.type !== 'tool/call') return
        const toolName = event.data.name
        if (!watched(toolName, config.serverNames)) return

        const sessionId = String(session.header.id)
        const count = (seen.get(sessionId) ?? 0) + 1
        seen.set(sessionId, count)
        total += 1
        if (count > config.maxLines) return

        // 远端工具名与它进 catalog 时的名字是同一个，可以直接对日志和工具表。
        ctx.logger.info(`mcp-call-observer: ${sessionId} 调用 ${toolName}（本会话第 ${count} 次，全局第 ${total} 次）`)
    })

    ctx.logger.info(`mcp-call-observer: 已挂载，观察 ${config.serverNames.length === 0 ? '全部' : config.serverNames.join(',')} 的 mcp__ 工具`)
}
```

**未验证**：上面 `ctx.on('session/event', (session, event) => ...)` 的**参数顺序**取自 `packages/acp/acp/src/index.ts:135`；`session.header.id` 取自 `packages/mcp/mcp-client/README.zh.md` 之外的用法（同一处 `acp/src/index.ts:136` 用的是 `session.header.id`）。`event.data.name` 取自 `packages/core/session/src/types.ts:341`。这三个都读到了源码，但没有实际跑过。

### 7.7 为什么这个 demo 讲得清

1. **两条 mcp-client 行把 stdio 与 HTTP 的差别摆在同一个文件里**，读者一眼看到「只有 `command`/`url` 这一组字段不同」。
2. **`!!js` 出现在两处不同位置**（`env` 与 `headers`），正好讲清「凭据是转发，不是托管」。
3. **观察插件只有 90 行、零依赖服务**，却能让读者亲眼看到「远端工具进了同一个 catalog」——这是全篇的核心命题。
4. **失败是可复现的**：故意用不存在的命令，日志里的重试阶梯就是 §5 那张表的现场。
5. **接得上 `golang_mcp`**：读者刚在那栏写完一个日志 MCP（`list_services` / `query_logs`），这一栏就能把同一个服务挂到模型面前。demo 里的 `serverName: logs` 就直接呼应它。

### 8.4 值得写进正文的 2~4 个反直觉点

1. **「挂 MCP」不是装包，是加一行配置。** `dsh` 已经把 `@deepseek-ai/dsh-mcp-client` 装好了（`apps/cli/package.json:58`），你只是从来没给它一台服务器。**默认全关**这一点很容易被误读成「DSH 不支持 MCP」。
2. **`env` 里的令牌**不是「自动继承」，而是「清洗之后再显式放回去」。名字叫 `*_TOKEN` 的变量会被清洗删掉，你不写进 `env` 它就永远到不了 MCP 子进程（`packages/subprocess/subprocess/src/index.ts:67` + `packages/mcp/mcp-client/src/transport.ts:22`）。
3. **重连只在「传输关闭」时发生。** stdio 子进程崩了会自动重连；**HTTP 服务器挂了不会**——它的失败按请求由 SDK 自己暴露（检出 README `:193`）。这个差别会直接决定你排障时该看日志还是看调用结果。
4. **MCP 工具进 catalog 后就是普通工具。** 想统计、想拦截、想渲染卡片，用的都是前面几篇学的东西，没有「MCP 专用钩子」——这是设计上最有说服力的地方，也是本篇最大的「不用学新东西」。
