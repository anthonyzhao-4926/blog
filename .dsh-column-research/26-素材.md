## 1. 机制说明

### 1.1 这一篇要解决的两个不同问题

「把跑腿活挪出主上下文」和「一个任务太大要拆给多个 agent」是两件事，DSH 用两套机制回答：

- **subagent（子代理）**：一个父 agent 派一个**子 agent**去干活，子 agent 有自己的会话、自己的上下文。父子之间是**树**，父是唯一的授权来源。一句话：**上下文的隔离单元**。
- **agent team（代理团队）**：一个 Lead 会话 + 若干 teammate，共享**任务板**和**邮箱**，teammate 之间可以互相发消息。这是一个**有名字的群体**，身份归 Lead 会话（root Session）所有。一句话：**协作的组织单元**。

两者的地基是同一个：subagent 的「continue 型子代理」（continuable child）就是 team 的成员载体。team 在 subagent 之上加了三样东西：**名册（roster）**、**共享任务 DAG**、**持久邮箱**。

### 1.2 subagent 的能力 seam 三件套

沿用读者在 [[08-替换内置能力的提供方与消费者|08 篇]] 已经学会的「服务定义 / 提供方 / 消费者」骨架：

| 角色 | 是谁 | 服务键 / 位置 |
| --- | --- | --- |
| 服务定义 | `@deepseek-ai/dsh-subagent` | `ctx.subagents`（`SubagentRuntime`） |
| 提供方（可并存多个） | `spawn` / `fork` / `acp` / `codex` / `claude-code` / `dsh-sdk` | 各自 `packages/subagent/subagent-*/` |
| 消费者 | `dsh-tool-subagent`、`dsh-tool-subagent-control`、`dsh-tool-ralph`、`dsh-workflow-worker-thread` | 注册成模型可见的工具 |

**这与 08 篇的 web 能力有一个关键差别，必须讲**：web 是「一个服务、一个实现」（后注册的顶掉先注册的），而 subagent 是**按名字注册的注册表，多个实现共存**。源码里明说了它的先例是 LLM adapter 注册表，而不是单实现的 bash executor（`docs/subsystems/subagent.md:5`）：

> "It differs from the other capability seams because **multiple provider implementations coexist** in one context, registered by name (`ctx.subagents`), while bash allows only one executor. Its registry follows the [LLM adapter registry](llm-streaming.md), not the single-service bash executor."

所以「换掉内置 subagent」这件事在这一篇里不存在；正确的心智模型是「**往注册表里再加一个名字**」。

### 1.3 两种能力，两种发现方式（本篇最核心的设计）

源码把「提供方能干什么」拆成两半，用两种完全不同的机制发现（`docs/subsystems/subagent.md:13-15`）：

1. **启动期能力（start-time capabilities）**：`SubagentProvider.capabilities` 是一组静态布尔标志，服务在 `start()` **之前**检查。缺什么就报 `UNSUPPORTED_CAPABILITY`。它描述的是**一次性（one-shot）** 路径——因为那条路上是提供方自己组装子代理。
2. **运行期能力（continuable）**：continue 型子代理是**续接管理器自己组装的**，所以提供方不再声明标志，而是「**可选方法存在即能力**」——`SubagentProvider.prepareContinuable?`（`packages/subagent/subagent/src/types.ts:374-389`）。TypeScript 的方法存在性就是发现机制。

这就是规划里说的「启动期与运行期的能力分割」。给读者的搭桥说法：**这跟你写 LLM adapter 时「声明支持的模型列表」是一类事，但 DSH 在 continue 路径上换成了「有没有这个方法」**——因为那一路提供方根本没参与组装，声明标志会骗人。

规则是 **fail loud，绝不静默降级**（`packages/subagent/subagent/src/types.ts:120-123`）：

> "a request that needs a capability the chosen provider lacks is rejected with a typed error rather than accepted-then-ignored (the "fail loud, no silent degradation" rule)."

### 1.4 spawn 与 fork 的差别（一句话 + 一处代码）

| | spawn | fork |
| --- | --- | --- |
| `inheritsParentContext` | `false` | `true` |
| 子代能看到什么 | 什么都没有，全新会话 | 父的**已完成轮次前缀**（balanced completed-turn prefix） |
| 工具描述怎么对模型说 | 「给一个完整、独立的提示词：它看不到这次对话」 | 「它已经看到这次对话已完成的轮次，直接接着说」 |
| 基础装配里的模式 | `backgroundMode: continuable` | `backgroundMode: one-shot` |
| 证据 | `packages/subagent/subagent-spawn-in-process/src/index.ts:50`；`packages/bundle/base/cordis.patch.yml:349-367` | `packages/subagent/subagent-fork-in-process/src/index.ts:72`；`completedTurnPrefix` 在 `:48-55` |

**注意 `inheritsParentContext` 是「描述性」的，不是被服务校验的能力**（`packages/subagent/subagent/src/types.ts:349-354`）。它唯一的作用是让消费者（工具层）生成**说真话的措辞**。子代继承的是**对话历史**，不是工具、服务、作用域或授权——正文必须点明，否则读者会以为 fork 子代权限更大。

### 1.5 授权模型：唯一的凭据是「活的 Agent 对象」

这是最容易踩坑、也最反直觉的一点。continue 型子代理的 `sendMessage` / `interrupt` 不接受「会话 id + 自称是父」这种凭据，而是要求传入**确切的活着的 `Agent` 实例**：

- 父→子投递：目标 Session 的 `SessionHeader.parentSession` 必须指向发送方（`docs/subsystems/subagent.md:150`）
- 子→父投递：发送方**驻留中的 Activation** 必须指向目标（同处）
- 「兄弟、隔代祖先、自我投递、过期的 Agent 对象、一次性子代理」全部拒绝（`docs/subsystems/subagent.md:150`）

人（浏览器）走的是另一条路：用 `durable` 的父会话 id 作为地址（`SubagentInterruptAuthority` 的 `kind: 'user'` 分支，`packages/subagent/subagent/src/types.ts:65-67`）。

### 1.6 agent team 的构成

`docs/subsystems/agent-team.md` 把 team 的持久形态完整列了出来：

- **身份**：`TeamId` 就是 root Session 的 id，套了一个不同的 brand；`TeamTaskId` 是 Team 内单调分配的 `task-<n>`；`TeamMessageId` 全局随机。teammate 的**持久身份是它的 Session id**，`name` 只是不可变的标签（`docs/subsystems/agent-team.md:9`）。
- **名册**：每个成员从 `provisioning` 开始，最终且只能落到一个终态：`active` 或 `failed`。运行时状态 `running`/`idle`/`inactive` 是**另外派生**的，永不回写这条记录（`docs/subsystems/agent-team.md:24`）。
- **邮箱**：Lead 会话先存下完整消息，只有目标侧的 pending inbox 项或 user message **落盘之后**才回执。所以「已入队减已投递」就是恢复用的邮箱（`docs/subsystems/agent-team.md:28`）。
- **任务 DAG**：每个任务事件存**完整快照**，`revision` 是 CAS 值，每次改动 +1；`blockedBy` 必须指向未删除的任务且保持无环；`writeScopes` 是**规范化后的建议性路径前缀，不是锁**（`docs/subsystems/agent-team.md:58`）。
- **重放**：`foldTeam()` 把一个 root Session 重放成名册、任务板和「已入队减已投递」邮箱；它**按 TeamId 过滤**，所以普通 fork 继承来的事件带着祖先 id，不会混进新 root 的状态（`docs/subsystems/agent-team.md:78`）。

### 5.2 生命周期与并发陷阱

1. **`signal` 的管辖范围分两段**。inbox 接受之前，调用方取消负责查找/物化/准入；**接受之后管理器独立拥有该 Activation，之后的调用方取消既不会取消已被接受的轮次，也不会释放子代理**（`docs/subsystems/subagent.md:152`）。误用：以为「取消 tool call 就能撤掉已经进队列的后台子代理」。
2. **`interrupt` 是 fire-and-return，不保证静止**。它调 `Agent.cancel(cause, { keepInbox: true })` 后立刻返回；Activation、未认领的 pending inbox、已发布的下级都**原封不动**；已被认领进当轮的活**不会重排队**（`docs/subsystems/subagent.md:156`）。误用：`interrupt_agent` 之后马上读结果。
3. **只有一条队列**。Agent inbox 是唯一的队列，所有消息都走 `Agent.steer()`；continuation 层**不定义第二条队列**（`docs/subsystems/subagent.md:148`）。误用：自己缓存未投递消息，导致与恢复邮箱不一致。
4. **「等待」可能永远等不到**。`waiting` 的定义包含「它拥有的子 Activation 尚未完成处置」，因此被 `Agent.inject()` 停靠的上下文能让一个空闲 Activation 及其活祖先一直驻留（`docs/subsystems/subagent.md:146`）。这是保守规则，不是 bug。
5. **处置是 child-first 且 await 每一支**。`drainContinuableDescendants` 即使个别分支失败也要等全部收束，最后抛聚合错误（`docs/subsystems/subagent.md:547`）。误用：把它当成「能很快返回」的调用。
6. **teammate 的 roster 相位与运行时状态是两回事**。`provisioning → active | failed` 是持久的；`running`/`idle`/`inactive` 是派生的，永不回写（`docs/subsystems/agent-team.md:24`）。误用：用 `list_agents` 的运行时状态判断「成员是否创建成功」。
7. **`writeScopes` 不是锁**。它是**规范化后的建议性路径前缀**（`docs/subsystems/agent-team.md:58`），视图层只产出重叠告警。误用：以为两个 teammate 不会同时写同一个文件。
8. **失败时不留半成品**。`start()` 的拒绝意味着「未发布的部分资源已被清理，且不发任何生命周期事件对」，而发布后的结果拒绝才「闭合已发出的那一对」（`docs/subsystems/subagent.md:455`）。误用：监听 `subagent/start` 来统计「尝试过的委派次数」——失败的尝试没有事件。

### 5.3 fail-closed / fail-soft 的分界

| 场景 | 行为 | 依据 |
| --- | --- | --- |
| 请求了提供方没有的启动期能力 | **fail loud**（`UNSUPPORTED_CAPABILITY`），绝不接受后忽略 | `packages/subagent/subagent/src/types.ts:120-123` |
| 提供方注册名重复 | **fail loud** | `index.ts:514` |
| `maxDepth` / `subagentDepth` 非法 | **fail loud**（`TypeError`） | `depth.ts:31`、`:49` |
| 目标不存在（`interrupt` / `drain*`） | **fail soft**：接受的 no-op；无管理器时也是 no-op | `docs/subsystems/subagent.md:530`、`:554` |

## 6. 外部插件可行性

**结论：完全可行。subagent 与 agent team 两套都能被仓库外插件使用。**

依据：

1. **服务定义与全部依赖都在 npm 上公开发布**，`private` 均未设置、`publishConfig.access` 都是 `public`：
   - `@deepseek-ai/dsh-subagent`（`packages/subagent/subagent/package.json`）
   - `@deepseek-ai/dsh-subagent-in-process-driver`（`packages/subagent/subagent-in-process-driver/package.json`）
   - `@deepseek-ai/dsh-agent`、`@deepseek-ai/dsh-session`、`@deepseek-ai/dsh-llm`、`@deepseek-ai/dsh-tools`、`@deepseek-ai/dsh-system-prompt`、`@deepseek-ai/dsh-brand`、`@deepseek-ai/dsh-invariants`（各自的 `package.json`）
2. **注册口是公开 API**：`registerProvider(provider)` 是 `SubagentRuntime` 的公开方法（`packages/subagent/subagent/src/index.ts:509`），注释明说「Registration is effect-scoped and HMR safe」。
3. **不需要仓库内构建管线**。一个提供方的最小实现只需要 import 已发布的 `@deepseek-ai/dsh-subagent`（类型 + `startInProcessRun`），像 `subagent-fork-in-process` 那样（整个包 96 行）。它不引用任何 monorepo 路径别名。
4. **`./src/*` 这条 exports 子路径不是障碍，但也不要依赖它**。多个包在 `package.json` 里写了 `"./src/*": "./src/*"`（例如 `packages/subagent/subagent-fork-in-process/package.json`），而 `files` 只发布 `lib/index.js` 与 `lib/types/**/*.d.ts`——**所以外部装到的包里根本没有 `src/`，这条 exports 对仓库外是悬空的**。「未验证」：我没有实际解包 npm tarball 核对；结论来自 `files` 字段。
5. **agent team 也能用**：`packages/experimental/AGENTS.md:6` 明说五个 Agent Teams 包「是显式公开例外，保留 experimental 名字，设置 `publishConfig.access: public`，加入 dsh 发布族」。registry 上也能查到 `@deepseek-ai/dsh-experimental-agent-team` 有多个已发布版本（含 `0.2.0-rc.2`、`0.2.1-alpha.2`）。

**必须同时讲清的两条限制**：

- **团队包不承诺稳定**。`packages/experimental/AGENTS.md:8`：「Publishing an explicit exception does not promote it or add a stability promise.」包名带 `experimental-`，一旦被提升就会**改名并原子更新所有配置行**。所以外部插件依赖它 = 接受随时改名的风险。
- **发布包不得反向依赖实验包**：`packages/experimental/AGENTS.md:7`「Release packages and apps outside this group must not name experimental packages in `dependencies`, `optionalDependencies`, or `peerDependencies`」。所以**你不能写一个仓库外的普通插件让别的发布包依赖它**，只能在自己的 profile 层显式加载。

**卡住的地方在哪里（如果要说「不能」）**：
- 想让**别人的** profile 默认带上 agent team —— 不行，必须显式加层（`packages/experimental/agent-team-profile/cordis.patch.yml` 是一层可选 patch）。
- 想复用 `dsh-tool-subagent-control` 的 `send_message` 同时又要 team —— 名字冲突，team 的做法是先 `disabled: true` 关掉全局那两个行（`packages/experimental/agent-team-profile/cordis.patch.yml:5-9`）。外部插件必须自己处理这个顺序。

## 7. demo 设计建议

**插件名**：`dsh-subagent-audit`
**为什么不叫 `dsh-team-kit`**：`code/dsh_plugin/dsh-team-kit/` 已经存在，但它是**装配包（bundle）**，讲的是关掉 `session-title-llm` + 往系统提示塞团队约定（见 `code/dsh_plugin/dsh-team-kit/README.md`、`package.json` 的 `dsh.bundle.patch`）——**与 agent team 完全无关**。正文要提醒读者别被名字骗了，demo 也必须换名。

### 要演示什么

在**仓库外**注册一个**第三个 subagent 提供方**，复用已发布的同进程驱动，并且故意把它声明成「能力不全」，让读者亲眼看到 fail-loud：

1. `apply` 里 `ctx.subagents.registerProvider(new AuditProvider('audit'))`，注册即生效、卸载即消失（对照 [[05-插件生命周期与 ctx.effect|05 篇]]）。
2. `AuditProvider` 复用 `startInProcessRun`，因此是一个**真的能跑**的子代理，不是假 run。
3. 能力表故意留一项 `false`，再用第二个 `tool-subagent` 实例请求那一项，展示 `UNSUPPORTED_CAPABILITY` 的**逐字报错**。
4. 用 `ctx.on('subagent/start')` 打印审计行，展示事件带 `provider` 字段。

### 核心代码骨架（`src/index.ts`）

```ts
/**
 * 注册第三个 subagent 提供方：audit。
 *
 * 它复用已发布的同进程驱动（与内置 spawn/fork 同一个 startInProcessRun），
 * 所以是一个真能跑的一次性子代理；区别只在于我们故意把 persona 能力声明为
 * false，用来演示「请求了不支持的能力就 fail loud」这条规矩。
 *
 * @module dsh-subagent-audit
 */

import type { Context } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'
import type {
    ResolvedSubagentStartRequest,
    SubagentCapabilities,
    SubagentProvider,
    SubagentRun,
    ContinuableCreateRequest,
    ContinuableCreateSpec,
} from '@deepseek-ai/dsh-subagent'
import { startInProcessRun } from '@deepseek-ai/dsh-subagent-in-process-driver'

export const name = 'dsh-subagent-audit'

/** 只依赖 subagents 服务；不碰 tools，工具实例由 patch 层自己加。 */
export const inject = ['subagents']

/** 插件配置：注册名与是否声明 persona 能力。 */
export interface Config {
    /** 在 ctx.subagents 上注册的名字（默认 audit）。 */
    providerName: string
    /** 是否声明 persona 能力；默认 false，用来演示能力拒绝。 */
    personaCapable: boolean
}

export const Config: z<Config> = z.object({
    providerName: z.string().default('audit'),
    personaCapable: z.boolean().default(false),
})

/**
 * 审计提供方：与内置 spawn 同源，只少声明一项能力。
 */
class AuditProvider implements SubagentProvider {
    readonly capabilities: SubagentCapabilities
    /** 审计子代理是全新会话，不继承父的已完成轮次。 */
    readonly inheritsParentContext = false

    constructor(readonly name: string, personaCapable: boolean) {
        this.capabilities = {
            agentOptions: true,
            outputSchema: true,
            depthLimit: true,
            toolFilter: true,
            persona: personaCapable,
        }
    }

    start(request: ResolvedSubagentStartRequest): Promise<SubagentRun> {
        // 不传 seed：这就是 spawn 语义，子代理看不到父的对话。
        return startInProcessRun(request, {})
    }

    /**
     * continue 型子代理的创建贡献：方法存在即能力。
     * 审计提供方只提供「不播种」这一种，因此返回空 spec。
     */
    prepareContinuable(_request: ContinuableCreateRequest): Promise<ContinuableCreateSpec> {
        return Promise.resolve({})
    }
}

/**
 * 装配：注册提供方，并给每次委派打一行审计日志。
 * @param ctx - 插件上下文。
 * @param config - 已解析的插件配置。
 */
export function apply(ctx: Context, config: Config): void {
    ctx.subagents.registerProvider(new AuditProvider(config.providerName, config.personaCapable))

    // 事件是按委派父作用域过滤的，所以这一行只会看到自己发出的委派。
    ctx.on('subagent/start', info => {
        ctx.logger.info(`audit: provider=${info.provider} child=${info.id}`)
    })
    ctx.on('subagent/end', info => {
        ctx.logger.info(`audit: child=${info.id} finished`)
    })
}
```

### 为什么这个 demo 讲得清

- **注册、能力、拒绝三件事一次说全**：`registerProvider` 是接口点，`capabilities` 是启动期能力，persona 那一项是活生生的拒绝路径。
- **没有造假的 run**：复用 `startInProcessRun` 意味着 demo 真的会产生子会话，读者能在 session 日志里看到 `subagent/descriptor` 与父子关系；对照 [[23-会话上下文的压缩、裁剪与排水|23 篇]] 的会话日志一起看。
- **和内置实现形成最小对照**：把 `packages/subagent/subagent-fork-in-process/src/index.ts` 的 96 行摆在旁边，读者立刻明白「写一个提供方」的边际成本有多低。
- **可观察**：日志、事件、工具名三层表象都能在命令行看到，不需要开界面。
- **能自然引出 team**：结尾一句「team 就是在这个注册表上加名册/任务板/邮箱」，为读者后面自己读实验包铺路。

### 值得写进正文的 4 个反直觉点

1. **「能力」不是一个概念，是两套机制**。启动期用静态布尔 + 服务侧校验（fail loud）；continue 路径用「可选方法是否存在」当能力。同一个提供方可以同时走两条路、用两套发现方式（`packages/subagent/subagent/src/types.ts:120-136` vs `:374-389`）。

2. **`inheritsParentContext` 不被校验，只是用来生成措辞**。它明确「不代表继承工具、服务或授权」（`packages/subagent/subagent/src/types.ts:349-354`）。读者很容易以为 fork 子代理权限更大——恰恰相反，代码注释专门警告：对 fork 说「你看不到这次对话」是**假话**（`packages/subagent/tool-subagent/src/index.ts:242-245`）。

3. **深度只升不降**。`delegationDepthOf` 取持久头与运行时字段的**较大者**，因为恢复出来的子代理带着全新 options，从零重算会让它以为自己是最顶层（`packages/subagent/subagent/src/depth.ts:18-36`）。这是「持久状态优先于运行时状态」的一个漂亮例子。

4. **agent team 住在 `experimental/`，却发在 npm 上**。`packages/experimental/AGENTS.md:6` 说明这五个包是「显式公开例外」，而 `:8` 同时说明「发布不等于提升、不附带稳定性承诺」。所以它可以被外部插件依赖，但等于把自己的稳定性绑在一个随时会改名的实验包上——这是一个值得让读者自己权衡的取舍。
