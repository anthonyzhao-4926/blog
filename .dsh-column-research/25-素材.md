## 机制说明

### 这一篇要讲的三块，各自是什么

DSH 把「插件要把东西存下来」拆成了三条互不重叠的缝（capability seam）。三条缝都是「抽象服务 + 供应商（provider）+ 消费者（consumer）」三件套，装载后从 `ctx` 上取用：

| 缝 | 服务键 | 抽象定义在 | 供应商（DSH 自带） | 存的是 |
| --- | --- | --- | --- | --- |
| storage | `ctx.storage` / `ctx.storageDomain` | `packages/storage/storage`、`packages/storage/storage-domain` | `storage-json`（`json`）、`storage-sqlite`（`sqlite`） | 插件的**普通状态**（KV 记录） |
| credentials | `ctx.credentials` | `packages/credentials/credentials` | `credentials-local` | 插件的**密钥值** |
| settings | `ctx.settings` | `packages/settings/settings` | `settings-file` | 用户的**可改配置** |

三者的分工是刻意的，也能一句话说清：

- **settings 存配置，不存状态**。它只保存用户愿意手改或愿意在界面上改的那部分；它有一条严格的「只收 JSON」写入校验（`cloneJsonShaped`，`packages/settings/settings/src/index.ts:243`），并且每次写入都会跑一遍 schema。
- **storage 存状态，不收配置**。它没有任何 schema 冲突检查以外的语义，值对后端是 opaque JSON（`packages/storage/storage/src/backend.ts:76-84`）。谁读谁负责解释。
- **credentials 只存密钥**，而且**存的是「引用」而不是「引用指向的东西被写进配置文件」**：配置里出现的是环境变量名（`DEEPSEEK_API_KEY`），值由供应商持有。

### 谁在谁的上面

不是三层塔，而是三套平行的东西，只有一条真实的依赖：

```
ctx.settings     （用户文档：$DSH_HOME/settings.yaml）
ctx.credentials  （凭据文档：$DSH_HOME/.credentials.yaml）
ctx.storage      （中枢，只做名字→后端的登记，自己不做 IO）
   └─ ctx.storageDomain（数据面：schema 校验 + 变更事件 + 写链）
         └─ 后端 json / sqlite（真正落盘）
```

**settings 和 credentials 之间唯一的结构性耦合是「引用」这个概念**：settings 的 schema 里可以用 `.role('credential-ref')` 标一个字段是凭据引用（`packages/web/web-search-deepseek/src/index.ts:65`、`packages/llm/llm-deepseek/src/index.ts:188`、`packages/webhook/webhook-github/src/index.ts:31`）。DSH 自己不做「把引用解析成值」这件事——消费者自己在每次操作时调 `ctx.credentials.resolve(ref)`。

**storage 与另外两条完全无关**。它有自己的 backend/provider 结构，也不读 settings。

### 为什么这么分

三个理由，都能在源码里找到痕迹：

1. **密钥不能进配置文件**。settings 的文档是用户随时手改、随手贴给别人看的（`packages/settings/settings-file/README.md:12` 明确说「users can edit the document directly — changes take effect live」）。所以 settings 里只放引用，值放 `$DSH_HOME/.credentials.yaml`，并且那个文件被强制成 0600。
2. **状态是可丢的派生数据，配置不是**。storage domain 的 spec 里有一个 `invalidRecords: 'backup-and-skip'` 选项，专门给「投影缓存」这类可重建数据用——存坏了就把那份文档挪走、记日志、当没有（`packages/storage/storage-domain/src/spec.ts:57-67`）。settings 没有这个选项，存坏了直接拒绝启动。
3. **运行期改配置不改插件形态**。settings 的解析是三层（schema 默认值 → 组合 base → 用户文档），每次写入先算候选值、跑 schema、跑 owner 自己的 `validate`，通过了才落盘再提交（`packages/settings/settings/src/index.ts:676-687`）。

### 怎么挂到读者已有心智模型上

- `ctx.settings` ≈ **`localStorage` + 一份带 schema 的 JSON 文件**：键是「命名空间」，值是「这一节的用户覆盖」，读的时候自动把默认值垫在下面。区别是它有版本号（`revision`）和并发拒绝。
- `ctx.credentials` ≈ **系统钥匙串，但目前实现不是钥匙串**。「引用」这一半等于「keychain 的条目名」，`resolve()` 等于 `keychain.get()`。但要如实说：DSH 自带的供应商把值以**明文 YAML** 存在 `$DSH_HOME/.credentials.yaml`，靠 `0600` 文件权限保护；`packages/credentials/credentials-local/README.md` 的 Known Limitations 里明确写了「A same-UID process can read the document — the file-effect sandbox modes do not deny reads, and an OS-keychain provider is deferred」。
- `ctx.storageDomain` ≈ **一个自带 schema 的小型 KV 库**（像 lowdb / 一个 JSON 版 SQLite 表）。一个「domain」就是一张（或几张）表 + 一个可选的全局单例，独占一份落盘单元。它**不是隔离或权限机制**，只是一个命名分区：任何能拿到 `ctx` 的代码都可以按名字打开别人的 domain（见「失败模式与坑」）。

### domain 到底是什么

一句话：**domain 是「一份被命名、被版本、被 schema 约束的 KV 分区」，由拥有它的包在模块加载时声明一次**。

它不是隔离、不是权限、不是多租户。名字就是后端单元名——`DomainSpec.name` 的 JSDoc 直接写着「doubles as the backend unit name」（`packages/storage/storage-domain/src/spec.ts:36`）。所以：

- 名字决定落盘位置：`json` 后端下 `single` 布局是 `<root>/<name>.json`，`per-record` 布局是 `<root>/<name>/<table>/<key>.json`（`packages/storage/storage-json/src/single-unit.ts:31`、`packages/storage/storage-json/src/format.ts:5-8`）。
- `version` 决定读的时候接不接受：`single` 布局版本不对就整体拒（`version-mismatch`），`per-record` 布局版本不对只丢那一条记录（`packages/storage/storage-json/src/format.ts:101-125`）。
- `tables` 和 zod schema 决定开的时候校验什么：任何一条存着的记录不符合当前 schema，整个 `open` 就拒 `invalid-record`（除非声明了 `backup-and-skip`）。
- 同一个 domain 名在一个进程里只能开一次：`DomainFacility.open` 用 `reserved` 集合做占用（`packages/storage/storage-domain/src/index.ts:104-106`），第二次抛 `already-open`。

规格（`DomainSpec`）包含：`name`、`version`、可选 `layout`、可选 `compatibleVersions`、可选 `invalidRecords`、可选 `global`（全局单例槽）、`tables`（表名 → 记录 schema）。

### credentials 的「引用」到底存了什么

必须讲清，这是本篇最容易写错的一点：

- **配置文件（settings 文档 / `cordis.yml`）里存的是名字**，形如 `DEEPSEEK_API_KEY`，类型叫 `CredentialRef`，语法是 POSIX 环境变量名（`/^[A-Za-z_][A-Za-z0-9_]*$/`，`packages/credentials/credentials/src/index.ts:19`）。schema 里用 `.role('credential-ref')` 标出来，配置界面就会把它渲染成「引用选择器」。
- **值存在供应商管的可写源里**。自带供应商 `dsh-credentials-local` 的可写源就是 `$DSH_HOME/.credentials.yaml` 的 `refs:` 段，**明文**（`packages/credentials/credentials-local/src/index.ts:443-448`）。
- 另有一个完全不同的键空间 `CredentialKey`，形如 `<scope>/<id>`（如 `llm-pi-ai/openai-codex`），存的是**记录**，不是引用：`api-key` 或 `grant`（`packages/credentials/credentials/src/types.ts:37-60`）。这一半不能分层（一个 OAuth 授权没有环境变量可以读），所以「记录存在」就是全部事实；写只能走 `modifyRecord`。

### 分层解析的层序（credentials，自带供应商）

`packages/credentials/credentials-local/src/index.ts:5-10` 的模块注释就是权威表，`resolve` 的实现是 `:617-625`：

```
1. 继承的进程环境                    只读，最高优先级，赢
2. $DSH_HOME/.credentials.yaml       供应商管的可写源
3. <启动时 cwd>/.env                 只读兜底（project-env）
4. $DSH_HOME/.env                    只读兜底（user-env）
```

代码里第 3、4 层由 `launchEnvironmentOf(ctx).getFrom(ref, ['project-env', 'user-env'])` 一并取，来源标签分别是 `project-env` / `user-env`（`packages/util/launch-environment/src/index.ts:16`、`packages/boot/app-boot/src/index.ts:211-215`）。

关键规则：

- 第 1 层**赢**。因为它代表「本次运行你明确想要的那个值」（`DEEPSEEK_API_KEY=… dsh`、CI secret、容器 `-e`），进程内改不了它，所以写的时候会被**直接拒绝**而不是静默失败（`assertUnshadowed`，`:794-801`）。`describe()` 对它报 `writable: false`（`:631-633`）。
- 第 2 层赢过 3、4 层：界面上存的 key 不会被 checkout 里带的 `.env` 顶掉。
- 空字符串在整条缝上等于「没有」：`resolve` 跳过、`describe` 报未配置（`packages/credentials/credentials/src/index.ts:159-161`）。
- **每次操作重新 resolve，不缓存**。这正是热更新的全部机制：LLM 适配器每个模型请求解析一次（`packages/llm/llm-deepseek/src/index.ts:449-455`）。

### settings 的分层解析

`packages/settings/settings/src/index.ts:740-751`，`resolve = schema(mergeLayers(base, section))`：

```
1. schema 默认值（Schemastery 的 .default(...)）
2. 组合 base（注册时传进来的 options.base，通常是这一行在 cordis.yml 里的 config）
3. 用户文档里的这一节（$DSH_HOME/settings.yaml 的 <namespace>: 段）
```

`mergeLayers` 的规则：纯对象递归合并，其它值（含数组）整块替换下层（`packages/settings/settings/src/index.ts:287-295`）。`update` 只往用户层 merge（`:562`），`replace` 整节换、缺的键回落到 base 和默认值（`:581`），`mutate` 走路径级 `set`/`unset`（`:602-618`）。

### `authorization` 包是干什么的

`@deepseek-ai/dsh-authorization`（`ctx.authorization`）**不存任何东西**，它是「一个凭据没法从配置里得到、只能跟人对话拿到」这件事的缝：OAuth 登录、粘一个 code、选一个账号（`packages/credentials/authorization/src/index.ts:1-8`）。

- 插件注册一个流程：`registerFlow({ key, label, methods, run(session) })`，`key` 就是它要写的那个 `CredentialKey`。
- 流程只拿到一个中立的会话对象：`notify(notice)` 报进度、`prompt(prompt)` 问人（`text` / `secret` / `select`）——它不知道对面是网页还是终端。
- 写记录是流程自己的事：`run()` 里的提交走 `ctx.credentials.modifyRecord`。缝在流程结束后确认「这次尝试期间确实提交了这个 key 的记录」，否则报 `NOT_COMMITTED`。
- 一个 key 同时只允许一次尝试：第二次调用抛 `ALREADY_IN_FLIGHT`（不是加入第一次）。
- 错误码：`DUPLICATE_FLOW`（`:206`）、`NO_FLOW`（`:279`）、`UNKNOWN_METHOD`（`:284`）、`ALREADY_IN_FLIGHT`（`:288`）、`NOT_COMMITTED`（`:425`、`:431`），加上「人拒答」用的 `DECLINED`（`:81`）——都在 `packages/credentials/authorization/src/index.ts`。
- 仓库里唯一的消费者是 `packages/llm/llm-pi-ai`。

**本篇定位建议**：`authorization` 只要有 2~3 段（它是什么、什么时候需要它、本篇不深入），因为给外部插件做 OAuth 流程是另一篇的量。

```ts
export function defineDomain<S extends DomainSpec>(spec: S): S {
    if (!UNIT_NAME_RE.test(spec.name)) {
        throw new Error(`domain name '${spec.name}' must match ${UNIT_NAME_RE}`)
    }
    if (!Number.isInteger(spec.version) || spec.version < 0) {
        throw new Error(`domain '${spec.name}' version must be a non-negative integer, got ${spec.version}`)
    }
    for (const compat of spec.compatibleVersions ?? []) {
        if (!Number.isInteger(compat) || compat < 0 || compat >= spec.version) {
            throw new Error(
                `domain '${spec.name}' compatibleVersions entries must be non-negative integers below version ${spec.version}, got ${compat}`,
            )
        }
    }
```

```ts
/** Resolve one namespace value: schema defaults, then `base`, then the user layer. */
private resolve<T>(
    schema: z<T>,
    base: unknown,
    section: Record<string, unknown> | undefined,
    validate?: (value: T) => void,
): T {
    // The merged candidate is untyped by construction; the schema call is the
    // runtime validation that admits it into T.
```

**误用：domain 名字撞车读到别人的数据。** `ctx.storageDomain.open(spec)` 不检查「这个 domain 是不是你的」——它只看名字有没有被占用、版本/schema 对不对得上。如果一个插件声明了 `name: 'workspace'` 并且表/schema 与 `dsh-workspace` 一致，它就能读到工作区数据；schema 不一致则整个 open 炸 `invalid-record`。**domain 名字就是所有权约定，DSH 不强制**。因此命名务必带自己的包名前缀（本仓内置的 `workspace` / `session_projcache` 都是短名，因为它们事实上属于内核；外部插件应写 `note_keyed_cache` 这类带前缀的名字）。同理，`~/.dsh/storages/workspace.json` 这种文件可以被任何插件读。

**误用：把可丢数据当权威数据。** 权威数据不该开 `invalidRecords: 'backup-and-skip'`——那会静默把不合 schema 的记录挪走当没有。反过来，派生缓存如果不开，一条坏记录就能让整个 domain 打不开、连带启动失败。

**误用：`per-record` 布局里用不安全的 key。** key 会变成路径段，必须匹配 `[a-zA-Z0-9_-]+`，不安全直接拒（`packages/storage/storage-json/src/per-record-unit.ts:39` 定义、`:309-310` 拒绝）。`single` 布局的 key 是 opaque 的，任意字符串。

**限制：跨进程看不到变更。** `domain/changed` 只在进程内发；第二个 host 进程或重连的界面要等跨进程版本模式落地才看得到（`packages/storage/storage-domain/README.md` Known Limitations）。

**限制：`json` 的 `single` 布局每次写都重写整份文件**，且**没有跨进程写锁**（两个进程写同一个单元是「后完成者赢」）。记录多、写频繁就该换 `per-record` 或路由到 sqlite。

**坑：把 secrets 放进 settings 的普通字段。** schema 里不标 `role('secret')` 的字段会**原样出现在 `describe()` 的结果里**、也会被渲染成普通输入框、还会被复制进 dump。要么用引用（`role('credential-ref')`），要么标 `role('secret')`。注意即便标了 `secret`，`redactSecrets` 也只走 `object` / `dict` / `array` 容器——藏在 union / intersection / transform 后面的 secret 会被**原样返回**，且 `secrets` 列表为空（`packages/settings/settings/README.md` Known Limitations 明说这不是已证明的 wire 边界）。所以 wire 上的命名空间不要用那些 schema 形态。

**坑：把 `replace` 当成通用写法。** 页面拿到的是**脱敏后**的节，`replace` 整节回传会把没返回过的 secret 字段静默删掉。所以路径级写入（`mutate` + `SettingsPathOp`）才是对付脱敏视图的写路径（`packages/settings/settings/src/index.ts:183-192`）。14 篇里前端用的 `form.mutate(ops, revision)` 就是这条。

**坑：把「设置页按 entry id 自动配对」和「`ctx.settings.register`」当成一回事。** 前者是 Loader 的 volatile 投影（14 篇讲的那套，命名空间 = entry id）；后者是插件主动注册的命名空间（本篇这套，命名空间是插件自己起的字符串）。两者都落在同一个 settings 服务和同一份 `settings.yaml` 里，但登记路径不同。

**限制：只有一层用户层。** 解析知道 schema 默认值、一个组合 `base`、一份用户文档；它**不记录哪一层供给了每个解析后的值**（`packages/settings/settings/README.md`）。想知道「这个字段是不是用户覆盖过」，只能看 `descriptor.user` 里有没有这个键。

## 外部插件可行性

**结论：三块都能用，不需要仓库内构建管线。**

### 依赖清单

一个仓库外、只用 npm 上公开包的最小插件，按要用到哪块加依赖（版本对齐本机装着的 `0.2.0-rc.2` 线，与 [[dsh 插件开发学习/14-让别人自己配插件|14 篇]] demo 的 `^0.2.0-rc.2` 写法一致）：

| 要用到的能力 | 需要声明的包 | 为什么要它 |
| --- | --- | --- |
| 服务类型 + `ctx.storageDomain` 的类型 | `@deepseek-ai/dsh-storage-domain` | `defineDomain` / `domainTable` / `DomainSpec` / `KvTable` |
| 只需要 `ctx.storage` / `KvUnit` 类型（少见） | `@deepseek-ai/dsh-storage` | hub 与后端契约 |
| 自己写后端（很少见） | `@deepseek-ai/dsh-storage` + `@deepseek-ai/schemastery` | 实现 `StorageBackend` |
| 凭据引用 | `@deepseek-ai/dsh-credentials` | `credentialRef` / `CredentialRef` / `CredentialKey` / `modifyRecord` |
| 凭据的线上视图类型 | 同上（走子路径 `@deepseek-ai/dsh-credentials/types`） | 那个子路径只含类型、不加载 Context 增强，浏览器编译面可以直接读 |
| 设置命名空间 | `@deepseek-ai/dsh-settings` + `@deepseek-ai/schemastery` | `ctx.settings.register` / `installSection` |
| 想自己算 `$DSH_HOME` 路径 | `@deepseek-ai/dsh-home-paths` | `resolveDshHome` / `dshHomePath` / `dshCachePath` |
| `zod` | `zod`（`^4.4.3`） | domain 记录 schema。**这是 domain 唯一的外部直接依赖**（`packages/storage/storage-domain/package.json` 的 `dependencies`） |
| cordis 本体 | `@deepseek-ai/cordis` | 插件骨架 |

**不需要**声明、也不该挂载：`storage-json` / `credentials-local` / `settings-file` —— 这些供应商由 `@deepseek-ai/dsh-base` 装配，每个 shipped profile 都带（`packages/bundle/base/cordis.patch.yml:90-156`）。插件只用 `inject` 等它们出现。（`storage-sqlite` 是另一种情况：它存在，但没有任何 shipped 装配挂它，见下面第 3 条。）

### 证据

1. **包都在 npm 上，且都声明了 public**。当前检出里这 9 个包的 `publishConfig.access` 全是 `"public"`：`dsh-storage`、`dsh-storage-domain`、`dsh-storage-json`、`dsh-storage-sqlite`、`dsh-credentials`、`dsh-credentials-local`、`dsh-settings`、`dsh-settings-file`、`dsh-home-paths`。registry 上 `@deepseek-ai/dsh-storage` 从 `0.0.1-rc.1` 一路发到 `0.2.1-alpha.2`（dist-tag `next` = `0.2.0-rc.2`），`dsh-storage-domain`、`dsh-credentials`、`dsh-settings`、`dsh-settings-file`、`dsh-home-paths` 同样都已发布。
2. **装着的运行时里就有它们，且类型齐全**。`~/.dsh/profiles/node_modules/@deepseek-ai/` 下有 `dsh-storage`、`dsh-storage-domain`、`dsh-storage-json`、`dsh-credentials`、`dsh-credentials-local`、`dsh-settings`、`dsh-settings-file`、`dsh-home-paths`、`dsh-invariants`（全部 `0.2.0-rc.2`），都是软链到 dsh 安装里。每个包的 `exports` 是 `"."` + `"./src/*"` + `"./package.json"`（`dsh-credentials` 另加 `"./types"`，`dsh-storage-domain` 加 `"./invariant"`），并随包发布 `lib/types/*.d.ts`（实测 `dsh-storage-domain/lib/types/` 下有 `domain.d.ts`/`spec.d.ts`/`error.d.ts`/`events.d.ts`/`index.d.ts`）。所以 TypeScript 直接有类型。
3. **构建产物只依赖公开包**。`dsh-storage-domain/lib/index.js` 的头两行是 `import z from "@deepseek-ai/schemastery"` 与 `import { UNIT_NAME_RE, storageBackendServiceKey } from "@deepseek-ai/dsh-storage"`；`dsh-credentials/lib/index.js` 头两行是 `import { Service } from "@deepseek-ai/cordis"` 与 `import { brandString } from "@deepseek-ai/dsh-brand"`。没有任何仓库内相对路径或私有构建产物。
4. **`zod` 是单一副本**：`~/.dsh/profiles/node_modules` 顶层（经软链）装有 `zod@4.6.5`，满足 storage-domain 的 `zod ^4.4.3`。
5. **端到端存在性证据**：仓库外插件真的用这套落过盘（`~/.dsh/storages/multi_root_workspace.json`，见「内置消费者」一节）。

### 与 14 篇 `ctx.remote` 那类限制的对比

14 篇撞到的限制是**浏览器半**：`window.__ModuleLoader__.load({ id, factory })` 这个产物契约由仓库内的 tsdown `clientBundle` 预设实现，预设不随 npm 发布，仓库外的包必须自己复现（见 [[dsh 插件开发学习/14-让别人自己配插件|14 篇]] 的 `tsdown.config.ts`）。

本篇三块**全是 Host 侧**，形态完全不同：

- Host 半走源码直载（tsx 钩子），不需要打包步骤；
- 服务由 `dsh-base` 提供，插件只 `inject`；
- 要用的包都发布了 `lib/` + `lib/types/`。

所以**没有「只有仓库内构建管线才走得通」的限制**。

### 但要提醒的三件事

1. **`latest` dist-tag 指向远古版本。** `@deepseek-ai/dsh-storage`、`dsh-storage-domain`、`dsh-credentials`、`dsh-settings` 的 `latest` 都还停在 `0.0.1-rc.1`（`dsh-settings-file` 是 `0.0.1-rc.3`，`dsh-home-paths` 是 `0.0.1-rc.3`），而 `next` 才是 `0.2.0-rc.2` 线。**所以 `pnpm add @deepseek-ai/dsh-storage-domain` 会装到一个 API 完全不同的老版本**；必须显式写版本（`^0.2.0-rc.2`）或对齐 profile 里已装的版本。这一条是真实踩点，值得写进「注意事项」。
2. **peer 依赖交给 profile 满足。** `dsh-storage-domain` / `dsh-credentials` / `dsh-settings` 的 peer 里有 `@deepseek-ai/dsh-invariants`、`@deepseek-ai/dsh-storage`、`@deepseek-ai/cordis`、`@deepseek-ai/schemastery`、`@deepseek-ai/dsh-util-values`、`@deepseek-ai/dsh-brand` 等。profile 的策略是 `autoInstallPeers: false` + `nodeLinker: hoisted`（见 [[dsh 插件开发学习/参考/profile与插件包结构|profile 参考]]），这些包在 `profiles/node_modules` 里都在，解析得到。插件**不需要**、也不该自己再装一份（会出「两份实例」）。这条是静态推断，**未实机验证**。
3. **`storage-sqlite` 不在任何 shipped 装配里**，本机 `~/.dsh/profiles/node_modules` 里也没有它。想用 sqlite 后端，得自己在 profile patch 里加一行挂载 + 配 `path`，并把 domain 的 `routes` 指过去。**这也让「换个后端」成了本篇一个自然的小节**：`storage-domain` 的 `Config.routes` 就是干这个的。

## demo 设计建议

**插件名**：`dsh-note-hits`（Host-only，无浏览器半）

**要体现的两件事**：

1. **状态落盘**：自己声明一个 domain，每次启动把「启动次数」和「上次启动时间」写进它的全局单例；数据落在 `$DSH_HOME/storages/note_hits.json`，第二次启动就能看到计数变成 2。
2. **密钥存引用不存明文**：配置里只有环境变量名（`apiKeyEnv`），启动时用 `ctx.credentials.describe()` 打一层「配没配 / 来自哪层」，再用 `resolve()` 真的取一次值来证明它可用——**终端只打来源层，不打值**。

**`src/dsh-note-hits.ts`（约 90 行）**：

```ts
/**
 * 启动计数落盘 + 按引用取密钥。
 *
 * 状态走 ctx.storageDomain：本插件自己声明一个 domain，数据落在
 * $DSH_HOME/storages/note_hits.json，不碰别人的 domain。
 * 密钥只存引用：配置里写的是环境变量名，值由 ctx.credentials 的
 * 凭据库（$DSH_HOME/.credentials.yaml）或进程环境提供；本插件从不
 * 把明文写进任何配置文件。
 *
 * 07 篇说过 ctx.logger 不往终端打，所以这里用 console 留证据。
 */
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'
import { z } from 'zod'
import { defineDomain } from '@deepseek-ai/dsh-storage-domain'
import { credentialRef } from '@deepseek-ai/dsh-credentials'

export const name = 'dsh-note-hits'

/** domain 数据面是必需的；设置服务是可选依赖，用 ctx.inject 等它出现。 */
export const inject = ['storageDomain']

/** 全局单例槽：从没写过时读 initial，第一次 set 才落到介质上。 */
const bootState = z.object({
    boots: z.number().int().nonnegative(),
    lastAt: z.string(),
})

/**
 * 本插件独占的 domain。名字会变成落盘单元名，所以带前缀避免撞车；
 * version 变了读的时候对不上，得自己迁数据。本插件没有表，只用全局槽。
 */
const bootDomainSpec = defineDomain({
    name: 'note_hits',
    version: 1,
    global: {
        schema: bootState,
        initial: { boots: 0, lastAt: '' },
    },
    tables: {},
})

/** 可配置项：密钥只放引用，不放明文。 */
export interface Config {
    /** 取密钥用的凭据引用（环境变量名）。 */
    apiKeyEnv: string
}

export const Config: Schema<Config> = Schema.object({
    // role('credential-ref') 让设置页把它渲染成引用选择器，而不是密码框。
    apiKeyEnv: Schema.string().role('credential-ref').default('DEEPSEEK_API_KEY'),
})

/**
 * @param ctx - 插件上下文，必须已注入 storageDomain。
 * @param config - 已校验的配置。
 */
export async function apply(ctx: Context, config: Config): Promise<void> {
    const domain = await ctx.storageDomain.open(bootDomainSpec)
    // 句柄归自己：插件卸载时先关 domain，别把单元漏在外面。
    ctx.effect(() => () => domain.close(), 'note-hits.domainClose')

    const state = domain.global.get()
    await domain.global.set({ boots: state.boots + 1, lastAt: new Date().toISOString() })
    console.log(`note-hits: 第 ${state.boots + 1} 次启动，状态落在 $DSH_HOME/storages/note_hits.json`)

    let current: () => Config = () => config

    /** 按引用取密钥：只打来源层和长度，永不打值。 */
    const reportCredential = async (): Promise<void> => {
        const ref = credentialRef(current().apiKeyEnv)
        const credentials = ctx.get('credentials')
        if (credentials === undefined) {
            console.warn(`note-hits: 没有凭据服务，${ref} 只能靠进程环境`)
            return
        }
        const info = await credentials.describe(ref)
        if (!info.configured) {
            console.warn(`note-hits: ${ref} 还没配（可在设置页填，或导出环境变量）`)
            return
        }
        const resolved = await credentials.resolve(ref)
        console.log(
            `note-hits: ${ref} 来自 ${resolved?.source ?? 'unknown'} 层，`
            + `值长 ${resolved?.value.length ?? 0} 个字符（值本身不打）`,
        )
    }

    // 设置服务在，就挂一个同名 namespace：页面改完引用，这里立刻重报一次。
    ctx.inject(['settings'], (settingsCtx) => {
        settingsCtx.settings.installSection(ctx, 'note-hits', Config, config, {
            setSource: (source) => {
                current = source
            },
            onChange: () => void reportCredential(),
        })
    })

    await reportCredential()
}
```

**`tsconfig.json`**（与 02 篇的 Host-only 插件一致，`module`/`moduleResolution` 指向 NodeNext，`noEmit`）。

**`install.sh`**：

```bash
#!/usr/bin/env bash
set -euo pipefail

DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

cd "$DIR"
pnpm install

cat > patch.yaml <<EOF
- insert:
    - id: dsh-note-hits
      name: '$DIR/src/dsh-note-hits.ts'
EOF

# 与 08/09 篇同一个 test profile；headless 也装一份，方便不看界面就验证。
for PROFILE in test headless; do
  dsh plugin --profile "$PROFILE" add "link:$DIR"
done

echo "装好了。验证：dsh --profile test --dump-config | grep -A3 'id: dsh-note-hits'"
```

**装法与验证命令**：

```bash
cd code/dsh_plugin/dsh-note-hits && ./install.sh

dsh --profile test --no-open        # 第一次：终端打「第 1 次启动」
cat ~/.dsh/storages/note_hits.json  # 看到 {"unit":{"name":"note_hits","version":1},"global":{"boots":1,...}}
dsh --profile test --no-open        # 第二次：终端打「第 2 次启动」，文件里 boots 变成 2
```

密钥那一半的验证：

```bash
# 没配时
dsh --profile test --no-open        # note-hits: DEEPSEEK_API_KEY 还没有配

# 走引用：只在 shell 里导出，插件配置一个字没动
DEEPSEEK_API_KEY=sk-demo dsh --profile test --no-open
# note-hits: DEEPSEEK_API_KEY 来自 env 层，值长 7 个字符（值本身不打）

# 换来源：把引用改成别的名字，配置文件里也只改名字
```

**为什么这个 demo 讲得清**：

- `cat ~/.dsh/storages/note_hits.json` 一眼看到「单元头 + version + global」的落盘格式，正好对上「机制说明」里 domain 的那几条。
- 第二次启动计数 +1，是**跨进程**可见的状态，比进程内变量有说服力。
- 密钥那半只打来源层和长度，把「引用在配置里、值在别处」讲死了。
- 用户的 `apiKeyEnv` 写在 profile 的 `cordis.patch.yml` 里（组合层），页面上改就进 `settings.yaml` 的用户层——顺手把 settings 的三层解析演示了。

**注意（demo 层面）**：

- `dsh --profile test --no-open` 的形式沿用 [[dsh 插件开发学习/14-让别人自己配插件|14 篇]]，**本篇未实机跑过**。
- 演示代码**故意不用 `ctx.logger`**：07 篇已经确认 `ctx.logger` 不往终端打，要肉眼可见的证据就得 `console.log`。这里直接用 `console`，省得读者以为没生效。
- 第一次跑之前 `~/.dsh/storages/note_hits.json` 不存在是正常的：`single` 布局的 materialization 推迟到第一次写。
- `tables: {}` 是允许的：只用全局单例、不要表的 domain 是合法声明（`tables` 必填但可以是空对象，见 `packages/storage/storage-domain/src/spec.ts:70-71`）。
- `dsh --dump-config` 的形式与 [[dsh 插件开发学习/14-让别人自己配插件|14 篇]] 的验证命令一致。

### 值得写进正文的三个「反直觉点」

1. `$DSH_HOME/.credentials.yaml` 是**明文**，「存引用不存明文」说的是配置文件那一侧。
2. domain 名和 settings 命名空间用的是**两套相反的命名语法**：domain 是 `^[a-z][a-z0-9_]*$`（下划线，无连字符），settings 命名空间是 `^[a-z][a-z0-9-]*$`（连字符，无下划线）。
3. domain **不是隔离机制**：没有所有者检查，名字撞了就读到别人的数据（版本/schema 对不上则整个 open 失败）。
