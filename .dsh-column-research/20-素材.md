# 第 20 篇素材包：别让模型乱动我的文件

对象：DSH 的沙箱策略（`ctx.sandbox` / `ctx.sandboxPolicy`）、fs 观察策略、权限预设。
仓库：`local/deepseek-harness/`。下面所有 `路径:行号` 都相对该仓库根。

## 机制说明

本篇要讲清一件事：**「模型不能乱动文件」在 DSH 里不是一条规则，而是三层彼此独立的东西**。12 篇（[[12-拦住模型乱来]]）只给了它们各挂在哪，本篇把每层的真实语义、取值、失败行为摊开。

三层分别是：

1. **沙箱（能/不能）**——进程沙箱 seam。`ctx.sandbox`（抽象 Service Definition，`packages/sandbox/sandbox/src/index.ts:158`）把一段子进程 argv 包成「在某个文件效果策略下执行」的 argv；`ctx.sandbox-local` 提供平台 runner 链（Linux bwrap/Landlock、macOS Seatbelt、Windows ACL restricted token）；消费者是 `bash-sandbox`/`pwsh-sandbox`（包住子进程）和 `fs-sandbox`（围住进程内写文件）。
   关键点：策略只管「文件效果」。`SandboxMode` 就三个值 `read-only | workspace-write | danger-full-access`，网络与进程可见性明确不在这个词汇表里（`docs/subsystems/sandbox.md:11`，`packages/sandbox/sandbox/src/index.ts:24-29`）。
2. **观察策略（读过没有）**——这不是「观测/审批/影子」三档模式，而是 `dsh-fs-observation-policy` 这个 **event-only 插件**：它不注册任何服务、不做任何文件 I/O，只在 `fs/write-intent` / `fs/edit-intent` 两个单槽瀑布上回答「这次写/改该怎么设防」，并把 `fs/observed` 记进自己的一张 `WeakMap`（`packages/fs/fs-observation-policy/src/index.ts:21-28`、`README.md:62-63`）。它做的是「先读后写」：编辑一个没读过的文件直接被拒，读过之后版本变了也拒。
3. **权限预设（怎么打包给人的一个开关）**——把两个互相独立的旋钮 `sandbox/mode` 与 `approval/policy` 打成一个具名预设，供客户端一个下拉框切换。它**不执行任何策略**，只负责「记录选择 + 通过各旋钮自己的写路径改值」（`packages/interaction/permission-presets/src/index.ts:1-11`，`docs/subsystems/permission-presets.md:5`）。

挂到读者已有心智模型上：第 08 篇（[[08-同一能力换个供应商]]）已经把「服务定义 / 提供方 / 消费者」讲透了——沙箱正好是同一形状（`ctx.sandbox` 是定义，`sandbox-local` 是提供方，bash/fs 是消费者），所以 20 篇可以直接说「沙箱就是又一个 capability seam，只不过它围的是子进程」。第 12 篇的 `guard()` 是策略层（插件说「不该做」），沙箱是系统边界（内核/围栏说「做不了」），两者互补，这个对立面要保留并展开。

策略的解析优先级是这一篇的主线之一：**已批准的显式 mode（升级重试）> 会话日志里最后一条 `sandbox/mode` 事件 > 部署默认**（`packages/sandbox/sandbox-policy/src/index.ts:155-169`）。其中会话覆盖不是存在配置文件里的，而是「会话日志本身当存储」：切模式就 append 一条 `sandbox/mode` 事件，重放即恢复（`packages/sandbox/sandbox-policy/src/session-mode.ts:1-12`）。这一点要先把「realm / 会话日志」这类内部词铺垫掉再讲：读者已经知道会话日志（09/10 篇的事件都是往日志里写），所以可以说「模式是一次事件，不是一个设置项」。

还有一个反直觉但必须讲的点：**部署默认的 fail-safe 值是 `read-only`**（`packages/sandbox/sandbox-policy/src/index.ts:112` 的 schema default，以及 `docs/config-catalog.md:1826-1833` 的注释），而 base profile 显式把它改成 `workspace-write` 并配 `ask`（`packages/bundle/base/cordis.patch.yml:208-241`）。「默认收紧、要放开必须显式」是这段的设计意图。

**2. `workspace-write` 到底能写哪几个目录**（`packages/sandbox/sandbox/src/roots.ts:43-55`）

```ts
/**
 * The roots one confined execution may WRITE under — the mode's meaning as a
 * canonical, deduplicated allow-list. `read-only` allows nothing;
 * `workspace-write` allows the policy's workspace root, the host `/tmp`, and
 * the per-user platform temp dir (`os.tmpdir()` — the real temp area for
 * mkstemp-family tools; omitting it would deny what the mode promises).
 * @param policy - the file-effect policy to derive the allow-list from.
 * @returns the canonical writable roots; empty exactly under `read-only`.
 */
export function writableRoots(policy: SandboxExecutionPolicy): string[] {
  if (policy.mode !== 'workspace-write') return []
  return [...new Set([policy.workspaceRoot, '/tmp', tmpdir()].map(canonicalPath))]
}
```

**3. 策略优先级（本篇主线）**（`packages/sandbox/sandbox-policy/src/index.ts:154-170`）

```ts
  /**
   * Resolve the complete policy for one capability call. An approved explicit
   * mode outranks the session's last `sandbox/mode` event, which outranks the
   * deployment default. A session cwd is its workspace-write boundary; the
   * configured root is the fallback for agentless calls and sessions without a
   * cwd.
   * @param request - optional session and approved mode override.
   * @returns the fully resolved per-call mode and absolute workspace root.
   */
  resolve(request: SandboxPolicyRequest = {}): SandboxExecutionPolicy {
    const { session } = request
    return {
      mode: request.mode ?? (session === undefined ? undefined : this.overrideOf(session)) ?? this.defaultMode,
      workspaceRoot: resolveWorkspaceRoot(session?.header.cwd ?? this.workspaceRoot),
      ...session === undefined ? {} : { sessionId: session.id },
    }
  }
```

**4. macOS 的围栏长什么样（SBPL profile）**（`packages/sandbox/sandbox-local/src/profiles.ts:43-58`）

```ts
/**
 * Build the sandbox-exec arguments and SBPL profile for one policy. The
 * writable roots come from the shared {@link writableRoots} helper (canonical,
 * deduplicated) so the Seatbelt grant and the in-process fs fence
 * (`@deepseek-ai/dsh-fs-sandbox`) can never drift apart.
 * @param policy - file-effect policy to express as an SBPL profile.
 * @returns sandbox-exec arguments before the trailing separator and command argv.
 */
export function seatbeltProfileArgs(policy: SandboxPolicy): string[] {
  const forms = ['(version 1)', '(allow default)', '(deny file-write*)', `(allow file-write* (literal ${sbplString('/dev/null')}))`]
  const roots = writableRoots(policy)
  if (roots.length > 0) {
    forms.push(`(allow file-write* ${roots.map(root => `(subpath ${sbplString(root)})`).join(' ')})`)
  }
  return ['-p', forms.join(' ')]
}
```

**5. 观察策略的两个决定**（`packages/fs/fs-observation-policy/src/index.ts:61-88`）

```ts
  /**
   * Decide the write intent: unseen or confirmed absent ⇒ `createIfAbsent`;
   * confirmed present ⇒ `replaceIfVersion` at the observed version.
   */
  writeIntent(target: FsTarget, actor: object | undefined): FsWriteIntent {
    const owner = this.owner(actor)
    const prior = owner ? this.get(owner, target.targetKey) : undefined
    return prior?.kind === 'present'
      ? { kind: 'replaceIfVersion', version: prior.version }
      : { kind: 'createIfAbsent' }
  }

  /**
   * Decide the edit version guard: unseen rejects with `FS_NOT_OBSERVED`,
   * confirmed absence rejects with `FS_NOT_FOUND`, and presence supplies the
   * observed version as the CAS basis.
   */
  editIntent(target: FsTarget, actor: object | undefined): { version: FsVersion } {
    const owner = this.owner(actor)
    const prior = owner ? this.get(owner, target.targetKey) : undefined
    if (!owner || prior === undefined) {
      throw new FsError(`edit requires reading "${target.displayPath}" first`, 'FS_NOT_OBSERVED')
    }
    if (prior.kind === 'absent') {
      throw new FsError(`cannot edit "${target.displayPath}": not found`, 'FS_NOT_FOUND')
    }
    return { version: prior.version }
  }
```

**6. 进程内围栏：检查过的路径就是要写的路径**（`packages/fs/fs-sandbox/src/index.ts:122-144`）

```ts
  private async checkedTarget(target: FsTarget, sandboxPolicy?: SandboxExecutionPolicy): Promise<FsTarget> {
    const policy = sandboxPolicy ?? this.ctx.sandboxPolicy.resolve()
    const { mode } = policy
    if (mode === 'danger-full-access') return target
    if (mode === 'read-only') {
      throw new FsError(`cannot write "${target.displayPath}": file access denied under read-only mode`, 'FS_SANDBOX_DENIED')
    }
    // workspace-write: containment on the FRESH canonical path (catches a
    // symlink ancestor swapped since the tool resolved this target), and the
    // mutation delegates with THIS fresh target — never the stale one.
    const fresh = await this.resolve(target.displayPath)
    let contained = false
    for (const root of writableRoots(policy)) {
      if (await isPathUnder(fresh.targetKey, root)) {
        contained = true
        break
      }
    }
    if (!contained) {
      throw new FsError(`cannot write "${target.displayPath}": file access denied under workspace-write mode`, 'FS_SANDBOX_DENIED')
    }
    return fresh
  }
```

## 失败模式与坑

- **没有任何 runner 可用 = 命令不跑，不是「不围就跑」**。`chainVerdict()` 走到 `'unavailable'`，`selectRunner()` 抛 `SandboxUnavailableError`（`packages/sandbox/sandbox-local/src/index.ts:492-510`）。错误信息是上面片段 1 的原文，最后一段会带上 `Runner failure: …`。Linux 上表现为：没装 bwrap 且内核不支持 Landlock 时，一切需要围栏的 bash 都被拒。
- **「静默不围」是明文禁止的**：Service Definition 的注释写着 `silent unconfined passthrough is forbidden`（`packages/sandbox/sandbox/src/index.ts:153-157`，`docs/subsystems/sandbox.md:156`）。
- **「拒绝」和「跑不起来」必须分开报**：`bash-sandbox` 先判 runner 失败再判拒绝，因为「runner 失败意味着命令根本没跑」（`packages/shell/bash-sandbox/src/index.ts:108-114`）。`ConfinedArgv` 里两套 stderr 词表也是为此：`denialSignatures` 是围栏生效的指纹（bwrap 的 EROFS、Landlock 的 EACCES、Seatbelt 的 EPERM），`runnerFailureRules` 是 runner 自己崩了的证据（`packages/sandbox/sandbox/src/index.ts:100-115`）。
- **`partial` 不是「差不多」**：`SandboxEnforcement = 'full' | 'partial'`，Windows ACL runner 恒为 `partial`，原因是 `WRITE_RESTRICTED` 必须保留 Everyone，且 NTFS 硬链接会绕过一个文件对象的路径（`packages/sandbox/sandbox-local/src/index.ts:15-19`；`docs/subsystems/sandbox.md:30`）。要求绝对边界的消费者必须自己拒绝 partial。
- **fs 围栏不是安全边界，只是策略围栏**：包注释直说 `This is containment, not a security boundary`，并且明确接受「祖先符号链接在复核与 syscall 之间被换掉」的残余 TOCTOU（`packages/fs/fs-sandbox/src/index.ts:10-18`）。要隔离不信任的**代码**，那是 `ctx.shell` 的事。这个区分要留在文章里，否则读者会以为 `write` 工具是沙箱。
- **观察策略的四处已知限制**（`packages/fs/fs-observation-policy/README.md:119-129`）：① 观察状态不跨会话恢复，resume 后必须重新读；② 没有 agent session 的调用永远满足不了编辑条件（写永远是 `createIfAbsent`）；③ 绕过工具直接调 `ctx.fs` 的读不发 `fs/observed`；④ 授权标准是「版本新鲜」而非「看全」——窗口读也能授权整文件覆盖。
- **两个单槽瀑布是「先注册者赢」，不是不变量**：`fs/write-intent` / `fs/edit-intent` 各只有一个决策者，插件一旦占槽就不调 `next()`；文档明确这是部署约定（`docs/subsystems/filesystem.md:185`，`README.md:76-78`）。想加一层权限/审计/沙箱拦截，正确的位置是 `tools/execute` 瀑布，而不是去抢这两个槽。
- **`fs/observed` 的监听器必须同步、且不能抛**：它走 `ctx.emit`，工具不兜这个 emit；抛异常会让工具变 `isError`，但写操作早已落盘（`packages/fs/fs-observation-policy/src/index.ts:124-129`；`packages/fs/tool-fs/tests/integration.spec.ts:507-510` 有一条测试正是描述这个）。
- **模型看到的文案是两层**：越界写抛 `FS_SANDBOX_DENIED`，tool 层把它换成共享标记 `[sandbox: file access denied under … mode]` 并附上同轮升级提示 `[sandbox: escalation available — …]`（`packages/fs/tool-fs/src/sandbox.ts:124-129`）。观察策略的两个码则被规范成给模型看的补救句：`cannot modify "<path>": file has not been read — read the file, then retry`、`<原因> — re-read the file, then retry`（`packages/fs/tool-fs/src/error.ts:23-31`）。
- **升级不是无限次**：`sandbox_permissions` 必须与 `justification` 成对且理由非空（`packages/sandbox/sandbox/src/escalation.ts:51-61`），目标模式必须**严格更宽**才算数，否则直接抛错、根本不问人（:162-164）。schema 里的枚举是闭集 `['workspace-write','danger-full-access']`，但严格更宽是执行期按当次有效模式判的（:22-31）。
- **会话模式的写路径只有一条**：`setSandboxMode` 之外没有任何东西改模式状态（`packages/sandbox/sandbox-policy/src/session-mode.ts:44-55`）；不变量会拒绝词表外的模式值：`sandbox/mode carries unknown mode …`（`packages/sandbox/sandbox-policy/src/invariant.ts:18-20`）。
- **`--dump-config` 能看到什么**：CLI 确实有 `--dump-config` 模式，会把 profile 装配后的配置转储（`apps/cli/tests/args.spec.ts:72-87`）。转储里应能看到 sandbox-policy 的 `mode`/`workspaceRoot`、sandbox-local 的 `runnerCommand`/`probeTimeoutMs`、permission-presets 的 `presets` 表——这些字段本身的权威定义在 `docs/config-catalog.md:1786-1845` 与 `1597-1634`。**未确认**：转储的具体输出格式与字段顺序（本次调研只读源码与测试断言，未执行 `dsh`）。
- **文档与代码的一处偏差**：`docs/subsystems/sandbox.md:11` 说 POSIX runner 会额外授予 `/dev/null`；代码里显式的 `/dev/null` 授权出现在 Seatbelt（`packages/sandbox/sandbox-local/src/profiles.ts:52`）和 Landlock（:31 的 `readWrite = ['/dev/null']`），bwrap 靠 `--ro-bind / /` 覆盖，没有单独的 `/dev/null` 项（:17）。讲的时候按「各 runner 有自己的拼法」表述即可。

## 外部插件可行性

**结论：可行，而且这是本篇最省事的演示方向——但「围栏本身」不能由外部插件凭空造出来。**

证据：

1. 相关包全部是 npm 公开包：`packages/sandbox/sandbox`、`sandbox-policy`、`sandbox-local`、`fs/fs-sandbox`、`fs/fs-observation-policy`、`fs/tool-fs`、`interaction/permission-presets` 的 `package.json` 都只有 `publishConfig: { "access": "public" }`，**没有 `private: true`**；`name` 均为 `@deepseek-ai/dsh-<name>`。
2. 已有外部插件就从 npm 装这些包：`code/dsh_plugin/dsh-event-log/package.json` 的依赖是 `@deepseek-ai/dsh-user-approval: ^0.1.7-rc.1`、`@deepseek-ai/dsh-tools`、`@deepseek-ai/dsh-session` 等（不是 `link:`/`workspace:`），其 `node_modules/@deepseek-ai/dsh-user-approval/package.json` 实测版本 `0.1.7-rc.2`。仓库里的 `0.1.5-rc.2` 只是源码快照版本，npm 上的发布版本更高。
3. 沙箱是宿主侧服务，插件要读它就走常规注入：`inject = ['sandboxPolicy']` 或 `ctx.get('sandbox')`。语言层面只依赖 `@deepseek-ai/dsh-sandbox` / `@deepseek-ai/dsh-sandbox-policy` 的类型。

外部插件**能**做：

- 读当前会话的有效策略：`ctx.sandboxPolicy.resolve({ session })`（需要 `inject: ['sandboxPolicy']`）。
- 订阅 `sandbox/mode` 事件与会话投影 key `sandboxMode`，做自己的审计/提示。
- 挂 `fs/observed` 记录观察事实；给 `fs/write-intent` / `fs/edit-intent` 装自己的一层（但注意是单槽先到先得，抢内置策略的槽会覆盖它）。
- 顶替 `ctx.sandbox` 提供自己的 runner：继承 `SandboxProvider` 并注册（第 08 篇的换供应商套路），或更省事地只配 `runnerCommand` + `runnerFailureSignatures`（`packages/sandbox/sandbox-local/src/index.ts:44-65`、:317-323）。

外部插件**不能 / 不该**做：

- 不能绕过「宿主没装围栏」这个事实：`ctx.get('sandbox')` 可能是 `undefined`，此时任何「我用沙箱兜住了」的说法都是假的；只能 fail-closed 或显式降级。
- 不能靠 fs 围栏当安全边界（同上一条坑）。
- 没有「只有仓库内构建管线才走得通」的限制：本篇涉及的全部 API 都在 host 侧运行时包里，普通 npm 依赖 + `apply(ctx)` 即可。对比 14 篇遇到的 `ctx.remote`（那是浏览器/远程边界的东西，需要客户端半与聚合），20 篇的 demo 是纯 host 插件，不需要任何仓库内构建管线。

## demo 设计建议

插件名：`dsh-fs-write-watch`（`dsh-` 前缀，与既有 demo 一致）。

目录结构（对齐 `code/dsh_plugin/dsh-event-log` 的既有写法）：

```
dsh-fs-write-watch/
├── package.json      # private + dsh.bundle.patch 指向 patch.yaml，依赖 @deepseek-ai/cordis、@deepseek-ai/dsh-tools
├── patch.yaml        # - insert: - id: dsh-fs-write-watch name: '<绝对路径>/src/dsh-fs-write-watch.ts'
├── install.sh        # dsh plugin --profile test add "link:$DIR"
└── src/
    └── dsh-fs-write-watch.ts
```

核心骨架（约 70 行，4 空格缩进、单引号、无分号、中文 JSDoc）：

```ts
/**
 * 文件边界观察器：把「这次写能不能落盘」的三层事实摊给用户看——
 * 沙箱模式与可写根（能/不能）、每个文件是否被读过（观察策略）、
 * 当前会话选中的权限预设（人选的旋钮组合）。
 *
 * 只读不改：不注册任何拦截器，不抢 fs/* 的单槽决策。
 *
 * @module dsh-fs-write-watch
 */
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'
import type {} from '@deepseek-ai/dsh-sandbox-policy'

export const name = 'dsh-fs-write-watch'
export const inject = ['tools', 'sandboxPolicy']

/** 每个会话观察到的文件：displayPath → 版本或 'absent'。 */
const observed = new WeakMap<object, Map<string, string>>()

export function apply(ctx: Context): void {
    // fs/observed 是记录型事件：必须同步、不许抛，所以这里只做一次 Map.set。
    ctx.on('fs/observed', (target, observation, actor) => {
        const session = (actor as { agent?: { session?: object } } | undefined)?.agent?.session
        if (session === undefined) return
        const byPath = observed.get(session) ?? new Map<string, string>()
        byPath.set(target.displayPath, observation.kind === 'present' ? `v:${observation.version}` : 'absent')
        observed.set(session, byPath)
    })

    // sandbox/mode 是 log-only 事件：切模式只进会话日志，重放即恢复。
    ctx.on('session/event', (session, event) => {
        if (event.type !== 'sandbox/mode') return
        console.log(`[${name}] ${session.id} 文件效果模式 -> ${event.data.mode}`)
    })

    ctx.tools.register(defineTool({
        name: 'policy_report',
        description: '报告当前会话的文件边界：沙箱模式、可写根、已观察文件、权限预设。',
        // 无参数工具：parameters 给空映射（defineTool 要求该字段存在）。
        parameters: {},
        output: {
            schema: {
                type: 'object',
                additionalProperties: false,
                properties: {
                    mode: { type: 'string', required: true },
                    workspaceRoot: { type: 'string', required: true },
                    observedFiles: { type: 'number', required: true },
                },
            },
            render: (_args, value) => [{ type: 'text', text: JSON.stringify(value) }],
        },
        execute(_args, exec) {
            // 有效模式 = 已批准升级 > 会话最后一条 sandbox/mode > 部署默认。
            const policy = ctx.sandboxPolicy.resolve(exec.agent === undefined ? {} : { session: exec.agent.session })
            const files = exec.agent === undefined ? undefined : observed.get(exec.agent.session)
            return { mode: policy.mode, workspaceRoot: policy.workspaceRoot, observedFiles: files?.size ?? 0 }
        },
    }))
}
```

装法与验证（沿用既有 demo 的脚本习惯）：

```sh
cd code/dsh_plugin/dsh-fs-write-watch
pnpm install
dsh plugin --profile test add "link:$PWD"
# 会话里让模型调 policy_report；再把模式切到 read-only，观察 write 被拒后的 [sandbox: …] 标记
```

验证点：① `policy_report` 的 mode 与界面上权限选择器一致；② 同一文件先 `read` 再 `edit` 成功、跳过 `read` 直接 `edit` 得到 `file has not been read` 的补救句；③ 切到 `danger-full-access` 后越界写不再有标记（说明围栏确实来自那两处，不是工具自带）。
