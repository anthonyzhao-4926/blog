## 机制说明

### 1.1 这篇要讲清的到底是什么

「会话一长就爆」这句需求，其实混了**五件互不相同的事**。它们共享同一条事件日志，但各自触发的时机、动的是哪份数据、可逆不可逆都不一样。素材包开头必须先把这个分层立住，否则读者一定会把「压缩」和「裁剪」和「排水」当成一件事，把四种「checkpoint」当成一个词。

一句话总纲：**会话日志（append-only 的 `SessionEvent` 序列）是唯一真相；其它全部是围绕它的落盘、派生读模型与上下文收缩。**

### 1.3 四个「checkpoint」不是一回事（这篇最容易讲错的地方）

仓库里 `checkpoint` 出现在四个完全不同的位置，必须逐一点名区分：

| 叫法 | 是什么 | 在哪 |
| --- | --- | --- |
| `compactCheckpointSource(compactionId)` | 压缩产生的那条**替换用 `user/message`** 的来源标记，用来让消费者认出「这条消息是一次压缩的检查点」。是表面节点，不是文件 | `packages/compaction/compaction/src/index.ts`（docs/subsystems/compaction.md:69 描述） |
| `dsh-session-checkpoint-policy` | **持久性检查点**：在 `llm/stream` 之前、`tools/execute` 之前、`agent/pre-step` 里 `ctx.sessions.flush()`。失败 fail-closed —— 模型请求或工具体根本不会被调用 | `packages/session/session-checkpoint-policy/src/index.ts:72-92` |
| `ctx.sessionProjectionCache` | **投影检查点**：把每个投影单元的状态按 session 落盘，是「fold 捷径」，可能旧但永不错 | `packages/session/session-projection-cache/src/index.ts` |
| 投影缓存的三个强制写入点 | 会话创建、`turn/end`、会话销毁（live→cold 的那一刻），是策略不是旋钮 | `packages/session/session-projection-cache/src/index.ts:55-62` 注释 |

正文建议：先立「持久性检查点」与「投影检查点」两条线，再一句话点出压缩那条 checkpoint 只是消息来源标记，不要展开。

### 1.4 挂到读者已有心智模型上

读者已经会的东西 → 这篇的新东西：

- **09 篇订阅 `session/event` 做统计** → 同一个 `session/event`，但这次是**内置消费者**在订：`session-projection` 注册表只订一次，然后把事件折进各个域单元。读者手写的「自己订阅 + 自己累加」在这里被框架化了：域插件只写 `apply(state, event)`，不写订阅。
- **08 篇服务定义 / provider / 消费者三件套** → `ctx.sessionPersistence`、`ctx.compaction`、`ctx.spillStore`、`ctx.sessionQuery` 全是同一套三件套。第一次能用 08 篇的骨架直接套上。
- **05 篇 `ctx.effect` / 生命周期** → 投影单元的注册就是 effect：`register()` 返回 disposer，插件卸载后这个 key 从快照里消失，客户端把它读成「能力不在」。
- **15 篇 `/api` 路由 + slot** → 会话列表那一列走的是投影缓存的零 I/O 读，不是每次去扫日志正文。这正是 15 篇「在界面上看自己的数据」在 DSH 内置功能里的同一套做法。
- **14 篇 host + client 两半** → 只有 `SessionProjectionMap`（wire 那半边）里的 key 才需要客户端那一半；`SessionProjectionStateMap` 里的 host-only key 不需要。这个区分对 demo 很关键。

### 1.5 「这块有哪些独立机制、彼此怎么接」的判据

判断两个机制是不是独立的，看**输入**和**落点**：

- spill 的输入是「刚产生的工具结果文本」，落点是「模型看到的结果被换掉」；它发生在结果进日志之前。
- pruner 的输入是「表面上的 `tool/result` 节点」，落点是「新追加一条替换节点 + 前一条 `compaction/prune` 标价」；它发生在结果已经在日志里之后。
- compaction 的输入是「一段表面区间」，落点是「一条摘要 `user/message` + `surfaceOp: replace`」。
- projection / query / token-meter 都不改日志，只读。

所以正确的因果链是：**spill（产生时） → 进日志 → pruner（压力逼近时） → compaction（越阈值时）**。

### 3.4 持久性检查点（fail-closed）

`packages/session/session-checkpoint-policy/src/index.ts:72-92`（节选，含 `afterCheckpoint`）

```ts
function afterCheckpoint(
  ctx: Context,
  session: Session,
  next: () => AsyncIterable<StreamChunk>,
): AsyncIterable<StreamChunk> {
  return (async function* (): AsyncIterable<StreamChunk> {
    await ctx.sessions.flush(session)
    yield* next()
  })()
}
```

```ts
export function apply(ctx: Context): void {
  ctx.on('llm/stream', (options, next): AsyncIterable<StreamChunk> => {
    if (options.sessionId === undefined) return next()
    const session = ctx.sessions.get(options.sessionId)
    return session === undefined ? next() : afterCheckpoint(ctx, session, next)
  })

  ctx.on('tools/execute', async (exec, next): Promise<ToolExecutionResult> => {
    if (exec.agent === undefined || exec.parent !== undefined) return next()
    await ctx.sessions.flush(exec.agent.session)
    if (exec.signal.aborted) return abortedBeforeDispatchResult()
    return next()
  })
```

讲法：`flush` 失败时 `next()` 根本不会被调用 —— 这是「fail-closed」，一个真实副作用旁边必须有持久化承诺。

### 5.2 invariant 与 fail-closed 行为

- **持久性检查点 fail-closed**：`llm/stream` 前 flush 失败 → 下游 adapter 不被调用；`tools/execute` 前 flush 失败或被 abort → 返回 `isError` 结果，工具体不被调用。文案 `'Error: tool call aborted before dispatch'` / `message: 'tool call aborted before dispatch'`（`packages/session/session-checkpoint-policy/src/index.ts:44-52`）。
- **格式拒绝是 fail-closed 的**：`docs/subsystems/persistence.md:345` —— 「reads validate current-format records only and refuse unknown vocabulary fail-closed」。当前格式修复会保留装了扩展的未知事件（带 `ignorable: true`），但**历史 v0/v1/v2 迁移即使标了 ignorable 也会拒**（`persistence.md:189`）。
- **未来代际一律拒**：`persistence.md:189` —— 「A future highest generation refuses even when an older readable generation remains」。
- **写所有权防并发修复**：一个活会话的写 handle 被它的生命周期所有者拿着，所以并发的 `open(id,'write')` 会以 `SessionAlreadyOwnedError` 被拒，而不是让修复和活跃 turn 赛跑（`persistence.md:112`）。只读观察者（session-query）在内存里做同样的 closers 平衡，**不写回**（`persistence.md:112`）。
- **投影单元必须同步、状态必须是纯 JSON**：`docs/subsystems/session-projection.md:15-21` —— 异步单元会撕裂 carrier 的一致性割面；非 JSON 状态会破坏持久化缓存前提。
- **单元对不关心的事件必须返回同一个引用**（`Object.is`）：否则下游每次都做无用功（`session-projection.md:39-43`）。
- **重复 key + 不同 `stateVersion` 会抛**；同版本注册者共享一个单元并计数（`session-projection.md:106`、`:205`）。所以同一个工具包在 N 个 agent preset 里挂载会注册 N 次，key 要等最后一个卸载才消失。
- **投影缓存写入全部 fail-soft**：失败只 `logger.warn`，下次写自愈（`packages/session/session-projection-cache/src/index.ts:6-11`、`docs/subsystems/session-projection.md:120`）。
- **`ver` 不匹配就丢行，不迁移**（同上）。
- **spill 保存失败不把调用变 error**：`docs/subsystems/spill.md:92` —— 「a save failure keeps the original inline result rather than turning a successful call into an `isError`」。
- **spill 策略有一条不变式**：替换文本**永不大于** `maxInlineBytes`；若光告知就超预算（`maxInlineBytes` 太小或 spill root 路径太长），就放弃替换、保留原文（`packages/spill/spill-policy/src/index.ts:171-178`）。
- **压缩锁**：`compaction/start` 先落，`compaction/end` 最后落，这样中途崩掉留下的是「可检测的孤儿锁」而不是「谎称完成的 end」（`docs/subsystems/compaction.md:19`）。**一个未配对的 start 会挡住所有入口**；但在更新的 `session/end-seed` 之前的未配对 start 属于上一轮生命周期的陈旧证据，会被忽略（`compaction.md:21`）。
- **压缩区间边界保持工具调用/结果配对，但不保持整轮**（`compaction.md:86`）。
- **单个超大保留单元或请求信封无法靠表面压缩修好**（`compaction.md:139-140`，`compactIfNeeded` 的 JSDoc）—— 这条很重要：压缩不是万能的，此时要靠 pruner 或 spill。

### 5.3 常见误用

1. **把「压缩」当成删历史**。事实上原事件都还在日志里，只是被 `surfaceOp: { op:'replace', startSeq, endSeq }` 遮蔽；`SessionEventSurface` 因此有 `'current' | 'shadowed' | 'log-only'` 三态（`docs/subsystems/session-query.md:15`）。
2. **用 seq 大小当表面顺序**。替换节点会让可见 seq 非单调：`shadowedRange` 是**表面位置跨度不是数值区间**，`start` 可能大于 `end`（`docs/subsystems/compaction.md:44-52`）。`TokenSurfaceNode` 的注释同样提醒「replacement nodes can have higher durable seqs than later positional nodes」（`docs/subsystems/token-meter.md:54`）。
3. **以为 base profile 就有全文检索**。不是，`openAt: never`（`:129-132`）。
4. **以为 session-query 会改写日志**。不会：它做的是只读观察 + 内存里补 closers（`persistence.md:112`）。
5. **在 read handle 上调 append**。一个 handle 类型服务两种访问，运行时抛 `SessionReadOnlyError`，没有编译期区分（`persistence.md:11`）。
6. **自己写投影单元时把它做成异步 / 返回非 JSON**。
7. **靠 `sizeBytes` 判断该不该打开会话**。`stat`/`list` 的 `eventCount`/`sizeBytes` 是「后端能便宜给出时才有」的可选字段（`persistence.md:311-321`），不是保证。
8. **在 `--dump-config` 里找搜索为什么不能用**。`openAt: never` 是合法配置，dump 出来是对的；真正的表象是搜索工具调用返回 `SESSION_QUERY_SEARCH_DISABLED`。

### 5.4 `--dump-config` 与日志里能看到的表象

- `--dump-config` 确实存在，是 CLI 的一种 mode（`apps/cli/tests/args.spec.ts:72-87` 断言 `parse([...])` 得到 `{ mode: 'dump-config', … }`）。仓库里已有的 demo 验证命令就是 `dsh --profile test --dump-config | grep -A3 'id: dsh-note-search'`（`code/dsh_plugin/dsh-note-search/install.sh`）。所以：**改配置、挂插件是否生效，第一站是 `--dump-config`；但它只告诉你装配成什么样，不告诉你运行时行为。**
- 运行时表象走 logger：
  - `compaction (step pressure): shadowed N surface nodes (seqs A-B, ~T tokens)`（`packages/compaction/compaction-basic/src/index.ts:141-145`，`ctx.logger.info`）
  - `step compaction failed: <msg>; continuing the turn`（同文件 `:161-162`，`ctx.logger.warn`）
  - `spill-policy: saveText failed for <tool>: <err>; keeping the inline content`（`packages/spill/spill-policy/src/index.ts:151-153`）
  - `spill-policy: no session owner for <tool> <label>; keeping the inline content`（同文件 `:126-128`）

### 6.2 有没有「只有仓库内构建管线才走得通」的限制

逐条排查，**没有发现 14 篇 `ctx.remote` 那种硬限制**，但有三处需要注意：

1. **声明合并要求类型图能看见**。投影单元要把 key 合进 `'@deepseek-ai/dsh-session-projection/types'`；`SessionProjectionMap` 在 `'@deepseek-ai/dsh-session-projection/types'`（见 token-meter 的 `declare module '@deepseek-ai/dsh-session-projection/types'`，`packages/llm/token-meter/src/projection.ts:65-72`）。外部插件写同样的 `declare module` 即可，前提是本包 `tsconfig` 的 `moduleResolution` 能解析到那个包的类型出口 —— 那是普通 npm 依赖解析，**不是仓库专属机制**。
2. **`./src/*` 导出是给仓库自己用的**。所有包都导出了 `"./src/*": "./src/*"`，但 `files` 字段只发布 `lib/*`（例如 `packages/session/session-projection/package.json`：`exports` 有 `./src/*`，`files` 只含 `lib/*`）。也就是说**外部插件不要 import `@deepseek-ai/dsh-xxx/src/...`** —— 包根 / 公开子路径（`./client`、`./types`、`./checkpoint`、`./invariant`）才是契约。这一点仓库内部反而随意用 `./src/*`，容易被误抄。
   - 已核实的公开子路径：`@deepseek-ai/dsh-token-meter` → `./client`、`@deepseek-ai/dsh-compaction` → `./types`、`./checkpoint`、`./invariant`、`@deepseek-ai/dsh-session-projection` → `./types`、`@deepseek-ai/dsh-session-stats` → `./types` 与 `./client`（`packages/session/session-stats/package.json` 的 `exports` 为 `['.','./types','./client','./src/*','./package.json']`）。这三种包的 `files` 都只发布 `lib/*`，`./src/*` 不在发布内容里。
3. **`inject` 必须是编译期能解析的服务名**。`ctx.sessionProjections` / `ctx.sessionQuery` / `ctx.sessionPersistence` / `ctx.compaction` / `ctx.spillStore` / `ctx.toolResultPruner` 都通过 `declare module '@deepseek-ai/cordis'` 的 `interface Context` 声明，随包类型一起发布。所以外部插件写 `export const inject = ['sessionProjections','tools']` 能通过类型检查。

### 6.3 一条务实的建议（写给读者）

「回查几天前聊过什么」最好的做法**不是**写插件，而是两行配置：在 profile 的 `cordis.patch.yml` 里把 `session-query-sqlite` 的 `openAt` 改成 `startup`（或 `first-search`）并给个持久 `path`，然后加一行挂 `@deepseek-ai/dsh-tool-session-query`。base bundle 的注释（`packages/bundle/base/cordis.patch.yml:120-128`）自己就写了这个做法。

### 7.3 核心代码骨架（约 78 行）

```ts
/**
 * 给当前会话记一本「被压缩过几次、被裁剪过几次」的流水账，
 * 再开一个工具让模型能读这本账。
 *
 * 记账用 session-projection：我们只写一个纯函数（apply），
 * 订阅 session/event 是框架的事。这叫 host-only 单元——
 * 它的 key 只出现在 SessionProjectionStateMap 里，不进客户端快照，
 * 所以不需要写客户端那一半。
 */
import type { Context } from '@deepseek-ai/cordis'
import { z } from 'zod'
import type { SessionEvent } from '@deepseek-ai/dsh-session'
import type {} from '@deepseek-ai/dsh-session-projection/types'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'dsh-session-digest'

/** sessionProjections 是必需依赖；没有投影注册表本插件不启动。 */
export const inject = ['tools', 'sessionProjections']

const digestSchema = z.object({
    compactions: z.number().int().nonnegative(),
    prunes: z.number().int().nonnegative(),
    lastShadowedTokens: z.number().int().nonnegative(),
})

type DigestState = z.infer<typeof digestSchema>

declare module '@deepseek-ai/dsh-session-projection/types' {
    interface SessionProjectionStateMap {
        /** 本会话的压缩/裁剪流水账。 */
        sessionDigest: DigestState
    }
}

const zero: DigestState = { compactions: 0, prunes: 0, lastShadowedTokens: 0 }

const definition = {
    key: 'sessionDigest' as const,
    // 折叠语义一变就把这个版本号加一，旧的持久化行会被丢掉而不是接着用。
    stateVersion: 1,
    stateSchema: digestSchema,
    init: (): DigestState => zero,
    // 纯函数：不关心的事件必须返回同一个引用，下游才不会白算。
    apply: (state: DigestState, event: SessionEvent): DigestState => {
        if (event.type === 'compaction/end' && event.data.error === undefined) {
            return { ...state, compactions: state.compactions + 1 }
        }
        if (event.type === 'compaction/prune') {
            return {
                ...state,
                prunes: state.prunes + 1,
                lastShadowedTokens: event.data.shadowedTokenCount,
            }
        }
        return state
    },
}

export function apply(ctx: Context): void {
    // 注册本身就是 effect：卸载时这个 key 从快照里消失。
    ctx.sessionProjections.register(definition)

    ctx.tools.register(defineTool({
        name: 'session_digest',
        description: 'Report how many times this session was compacted or had tool results pruned.',
        parameters: {},
        output: {
            schema: { type: 'string' as const },
            render: (_args: unknown, value: string) => [{ type: 'text' as const, text: value }],
        },
        isConcurrencySafe: () => true,
        execute: (_args, exec) => {
            const session = exec.agent?.session
            if (session === undefined) return 'no agent-bound caller'
            const state = ctx.sessionProjections.stateOf(session, 'sessionDigest')
            return JSON.stringify(state ?? zero)
        },
    }))
}
```

> `package.json` 依赖：`@deepseek-ai/cordis`、`@deepseek-ai/dsh-session`、`@deepseek-ai/dsh-session-projection`、`@deepseek-ai/dsh-tools`、`zod`、`@deepseek-ai/schemastery`。仓库里 `SessionProjectionStateMap` 的 schema 一律用 `zod`（v4），而插件 `Config` 用 Schemastery —— 两个库别混。

### 7.4 装法与验证

```sh
# 装（沿用 08/09 篇的 test profile，脚本照 dsh-note-search/install.sh 的写法生成 patch.yaml）
bash code/dsh_plugin/dsh-session-digest/install.sh

# 1) 先看装配对不对
dsh --profile test --dump-config | grep -A3 'id: dsh-session-digest'

# 2) 造一个大工具结果，看 spill 是否生效（默认 maxInlineBytes 是 50000，可先在 profile 里改小）
dsh --profile test "读一下仓库里最大的那个文件，把前 200 行贴出来"

# 3) 手动压缩一次，看 compaction 事件
#    在会话里输入 /compact

# 4) 让模型读账本
dsh --profile test "调 session_digest 看看这个会话被压缩过几次"
```

预期：第 1 步能看到本插件行与 `Config`；第 2 步在会话记录里能看到「预览 + 一段告知 + 文件路径」；第 3 步日志里出现 `compaction (…) shadowed N surface nodes (seqs A-B, ~T tokens)`；第 4 步工具返回 `{"compactions":1,"prunes":0,"lastShadowedTokens":…}`。

### 7.5 讲课时要点的三个「原来如此」

1. `register()` 返回 disposer，但这里故意不手动调 —— 它已经挂在调用方 fiber 上，卸载时自动清（05 篇的知识在这里复用）。
2. `stateOf()` 会把该单元**当场补算**到会话当前游标（懒建 cell），所以「单元注册晚于事件」也能得到正确结果。
3. 日志里的 `compaction/summary`、`compaction/prune` 都是 **log-only** 事件：它们永远不进模型上下文，只给记账用（`docs/subsystems/compaction.md:11`）。
